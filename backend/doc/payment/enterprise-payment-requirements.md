# 企业付款模块需求文档

## 1. 引言

### 1.1 背景
为满足"危废再生资源全流程追溯SaaS平台"中企业间及企业对个人支付结算的需求，规范支付流程、提高结算效率、确保资金安全并符合合规要求，特规划企业付款模块。该模块将支持多种支付场景，包括企业对个人（B2C）的付款（如向产废个人支付回收款）、企业对企业（B2B）的对公转账，以及与此相关的发票管理和对账功能。

### 1.2 目标
- **核心价值**：
    - 实现高效、安全、合规的企业级支付功能。
    - 支持多样化的支付方式，满足不同业务场景需求（如工行反向开票、其他第三方支付、对公转账）。
    - 简化企业财务操作，提高对账和结算效率。
    - 确保支付与发票信息的准确性和可追溯性。
- **用户收益**：
    - **回收企业**：便捷地向产废方（个人或企业）付款，高效管理发票，简化财务对账流程。
    - **产废企业/个人**：及时、安全地收到款项，方便地获取支付凭证和发票。
    - **物流公司**：清晰记录代付款项，方便与回收企业对账。
    - **平台管理员**：有效监控支付流程，管理支付渠道和相关配置。

### 1.3 名词解释
- **反向开票**：由付款方（采购方）辅助或代收款方（销售方，尤指个人）发起开票申请的流程。
- **B2C支付**：企业向个人消费者/用户的支付。
- **B2B支付**：企业向企业的支付。
- **对公转账**：通过银行等机构进行的企业账户间的资金转移。
- **电子发票**：数据电文形式的收付款凭证。

## 2. 产品范围

### 2.1 核心功能
企业付款模块的核心功能点源自 `prd.md` 中"支付结算"模块及 `user-story.md` 中的相关用户故事，主要包括：

1.  **多渠道支付能力**：
    *   **对个人付款 (B2C)**：
        *   集成工商银行"反向开票"接口，实现向个人付款并自动生成发票 (参考 US-007)。
        *   支持通过其他第三方支付渠道向个人银行卡或零钱付款 (参考 US-012)。
        *   支持配置付款后自动向上游（如产废联系人）发起支付 (参考 US-012)。
    *   **对企业付款 (B2B)**：
        *   支持记录对公转账信息，并上传付款凭证 (参考 US-030)。
2.  **发票管理**：
    *   **反向发票管理**：
        *   与工行接口联动，获取并管理反向开票生成的电子发票 (参考 US-007, US-008)。
        *   支持用户下载电子反向发票 (参考 US-008)。
    *   **常规发票协同**：
        *   支持产废企业上传其开具给回收企业的发票 (参考 US-016, US-030)。
        *   发票与订单、付款记录自动关联和匹配。
        *   标记发票状态（如"已开票"、"已收票/验票通过"） (参考 US-030)。
3.  **资金与账户管理**：
    *   **收运员承包账户管理**：支持为收运员创建独立子账户，核算其收支流水 (参考 US-014)。
    *   **多门店资金归集**：支持多门店产废企业的收款统一归集到总部账户 (参考 US-015)。
4.  **对账与凭证**：
    *   **对账单生成**：产废企业在线下载收款凭证和对账单 (参考 US-013)。
    *   **企业间对账**：回收企业与产废企业就对公付款及发票进行对账 (参考 US-030)。
    *   **物流代付款项对账**：回收企业与物流公司就代垫款项进行对账 (参考 US-031)。
5.  **支付监控与管理**：
    *   **支付状态跟踪**：实时同步和查询支付状态 (参考 US-012, US-018)。
    *   **临时订单支付监控**：监控临时订单支付状态，处理超时未确认订单 (参考 US-019)。
    *   **支付渠道配置**：后台管理和配置可用的支付渠道及其参数。

### 2.2 用户角色与需求
（参考 `prd.md` 第3节 目标用户 及 `user-story.md`）

*   **回收企业用户（财务、运营、管理员）**：
    *   需求：高效、准确地完成对个人和企业的付款；便捷管理各类发票；清晰地进行财务对账；配置和管理支付规则。
*   **产废企业用户（管理员、财务）**：
    *   需求：及时收到应收款项；方便地获取和管理发票；在线核对账务。
*   **个人收款用户（如产废个人、收运员）**：
    *   需求：安全、便捷地收款；获取收款凭证和发票。
*   **物流公司用户（调度员、财务）**：
    *   需求：清晰记录代付款项；与回收企业便捷对账。
*   **平台系统管理员**：
    *   需求：监控支付系统运行状态；管理支付渠道配置；处理支付相关的申诉与异常。

## 4. 非功能性需求
（参考 `prd.md` 第5节 及 `工行反向发票开发需求文档.md` NFR部分）

*   **NFP-001 安全性**：
    *   严格遵守支付安全规范，如PCI DSS（若适用）。
    *   支付相关的敏感数据（如银行账号、API密钥）必须加密存储和传输。
    *   与第三方支付网关的交互必须使用HTTPS，并进行严格的签名验证。
    *   详细的权限控制，确保用户只能访问其授权的支付和发票数据。
    *   防范常见的Web攻击（SQL注入、XSS、CSRF等）。
    *   支付操作需有二次确认或MFA（视敏感度而定）。
*   **NFP-002 可靠性与可用性**：
    *   支付核心服务SLA承诺达到99.95%或更高。
    *   支付指令处理确保幂等性，避免重复扣款或支付。
    *   与外部支付系统交互失败时，应有合理的重试机制（遵循外部系统指导）和明确的错误处理。
    *   关键支付数据应有备份和恢复机制。
*   **NFP-003 性能**：
    *   核心支付请求（如发起支付、查询状态）响应时间应在约定时间内完成（例如，API调用<1s，用户界面操作<3s）。
    *   系统能处理预期的并发支付请求量。
*   **NFP-004 合规性**：
    *   遵循《网络安全法》、《个人信息保护法》等。
    *   电子发票的生成、流转和存储需符合税务及电子凭证相关规定。
    *   跨境支付（如果涉及）需符合外汇管理规定。
*   **NFP-005 可扩展性**：
    *   支付渠道应采用可插拔式设计，方便未来集成新的支付方式。
    *   模块化设计，易于功能扩展和维护。
*   **NFP-006 数据一致性**：
    *   确保本系统支付状态与第三方支付平台状态的最终一致性。
    *   采用可靠的消息队列或分布式事务方案处理跨系统状态同步。

## 5. 集成点

*   **用户模块 (yudao-module-system, yudao-module-member)**：获取企业用户信息、个人用户信息、权限信息。
*   **订单模块 (假设存在)**：关联支付与具体业务订单，获取订单金额、商品信息等。
*   **物流模块 (假设存在)**：获取物流状态，触发自动付款等。
*   **工行聚富通接口**：用于反向开票和支付。
*   **其他第三方支付网关**：如微信支付、支付宝等。
*   **电子签章服务 (e签宝)**：若支付凭证或合同需要电子签名。
*   **国家固废系统/税务系统**：发票信息可能需要与这些系统同步或校验。
