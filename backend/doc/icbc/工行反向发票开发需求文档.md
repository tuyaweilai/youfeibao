# 工商银行反向开票业务开发需求文档

## 1. 项目背景与目标

本项目旨在通过对接工商银行（ICBC）提供的聚富通相关API接口，实现企业（作为付款方/采购方）向个人（作为收款方/销售方）采购商品或服务后，由企业方辅助或代为个人发起开票申请，并完成后续的支付、发票下载等全流程业务。这种模式通常被称为"反向开票"或"帮开票"。

**核心目标：**

*   实现平台与工行系统的无缝对接，支持反向开票的各业务环节。
*   确保交易数据的准确性、安全性、以及符合工行接口规范。
*   提供稳定、高效的接口调用服务。
*   满足业务对账、日志审计的需求。

## 2. 业务流程概述 (推断)

基于提供的接口文档，推断出的核心反向开票流程可能如下：

1.  **收方（个人销售方）入驻管理 (可选，但通常需要)：**
    *   **收方信息新增：** (`/jft/api/user/edpreceive/add/V1` - 聚富通智慧清分收方新增接口V1) - 如果个人销售方尚未在工行系统或合作方平台录入，可能需要先进行信息登记和审核。
    *   **收方信息查询：** (`/jft/api/user/edpreceive/query/V1` - 聚富通智慧清分收方查询接口V1) - 查询已入驻的收方信息及状态。
    *   **收方信息修改/审核回调：** (`智慧清分收方审核回调示例文档.md`) - 处理收方信息变更及工行审核结果的异步通知。
    *   **再生资源场景下的收方入驻：** (`聚富通再生资源收方入驻结果查询数据接口V1.md`) - 针对特定业务（如再生资源）的收方管理。

2.  **开票信息预下单：**
    *   (`聚富通开票信息预下单接口V1 1.0.2.md` - `/ui/jft/ui/invoice/pre/order/V1`)
    *   **目的：** 企业（付方）提交包含订单、商品、收方（个人销售方）、付方（企业采购方）等详细信息的开票请求。
    *   **交互：** 此接口通常为UI接口，调用后会引导至工行页面，由个人销售方进行信息确认。
    *   **关键信息：** 合作方订单ID、收方编号、付方编号、订单金额、商品明细、发票类型、收方个人信息、付方企业信息、特定要素（如农产品收购、报废产品收购）等。
    *   **通知：** 需要配置发票状态变更通知地址 (`invoiceNotifyUrl`) 和自然人确认成功返回页面地址 (`invoiceJumpUrl`)。

3.  **开票信息预查询 (状态跟踪)：**
    *   (`聚富通开票信息预查询接口V1 1.0.4.md` - `/jft/api/invoice/queryInvoiceInfo/V1`)
    *   **目的：** 在个人确认后或支付完成后，查询预开票的状态、发票信息（如发票号码、开票日期）、支付状态、缴税状态等。
    *   **关键信息：** 合作方订单ID、红冲流水号 (如果查询红票)。

4.  **付方支付 (企业向个人付款)：**
    *   (`聚富通开票付方支付接口V1 1.0.0.md` - `/ui/jft/ui/invoice/pay/V1`)
    *   **目的：** 企业（付方）通过此接口向个人（收方）支付货款。
    *   **交互：** 此接口通常为UI接口，调用后会引导至工行企业支付页面。
    *   **关键信息：** 合作方订单ID、收方编号、付方编号。场景支付时可能需要 `verifiedCode` (机构编码) 和 `ukeyId` (U盾ID)。

5.  **发票下载：**
    *   (`聚富通发票下载接口V1 1.0.1.md` - `/jft/api/invoice/download/V1`)
    *   **目的：** 在开票成功后，下载电子发票文件（通常为PDF）。
    *   **关键信息：** 合作方订单编号、红冲流水号 (下载红票时)、红蓝标识。
    *   **返回：** 发票的字节流数据 (`byteData`)，需要进行Base64解密。

6.  **回调处理：**
    *   多个接口都提到了回调地址（如 `invoiceNotifyUrl`，`智慧清分收方审核回调`）。
    *   需要开发接口接收工行发送的异步通知，并进行验签、业务处理和状态更新。

## 3. 功能需求

### 3.1 统一接口层封装

*   **SDK开发：** 开发一个Java SDK用于封装所有与工行接口的交互。
    *   统一处理通用请求参数的构建 (`app_id`, `msg_id`, `timestamp`, `sign` 等)。
    *   实现对 `biz_content` 的JSON序列化。
    *   实现AES加密/解密逻辑（根据接口是否要求）。
    *   实现RSA/RSA2签名生成与验签逻辑。
    *   封装HTTP请求的发送与响应接收。
    *   定义清晰的请求DTO和响应DTO。
    *   统一的异常处理机制，将工行错误码转换为业务可理解的异常。
*   **配置管理：** 敏感信息（密钥、`app_id`等）和环境URL应通过配置中心或安全配置文件管理。

### 3.2 收方管理模块 (如果适用)

*   **F3.2.1 新增收方信息：**
    *   调用工行"聚富通智慧清分收方新增接口"。
    *   记录请求与响应，更新本地收方状态为"审核中"。
*   **F3.2.2 查询收方信息：**
    *   调用工行"聚富通智慧清分收方查询接口"。
    *   展示收方审核状态、可用状态等。
*   **F3.2.3 处理收方审核回调：**
    *   提供公网可访问的回调接口，接收工行审核结果。
    *   对回调请求进行验签。
    *   根据回调结果更新本地收方状态（通过/拒绝）。
    *   确保回调处理的幂等性。

### 3.3 开票预下单模块

*   **F3.3.1 构建预下单请求：**
    *   根据业务数据组装"聚富通开票信息预下单接口"所需的 `biz_content`。
    *   调用SDK生成完整的POST表单参数或重定向URL。
    *   前端引导用户跳转至工行页面进行确认。
*   **F3.3.2 处理预下单回调/通知：**
    *   提供公网可访问的回调接口 (`invoiceNotifyUrl`, `invoiceJumpUrl`)。
    *   处理工行关于发票状态变更的通知，更新本地订单/发票状态。
    *   处理用户在工行页面操作完成后的跳转。

### 3.4 开票状态查询模块

*   **F3.4.1 查询预开票信息：**
    *   定期或在特定业务节点调用"聚富通开票信息预查询接口"。
    *   获取并更新订单的支付状态、开票状态、发票号码、红冲信息等。

### 3.5 付方支付模块

*   **F3.5.1 构建支付请求：**
    *   根据业务数据组装"聚富通开票付方支付接口"所需的 `biz_content`。
    *   调用SDK生成完整的POST表单参数或重定向URL。
    *   前端引导企业用户跳转至工行支付页面完成支付。
*   **F3.5.2 支付结果同步：**
    *   支付结果可能通过回调或后续查询接口（如预查询接口中的支付状态）获取。

### 3.6 发票下载模块

*   **F3.6.1 下载电子发票：**
    *   在确认发票已成功开具后，调用"聚富通发票下载接口"。
    *   传入订单号等必要参数。
    *   接收返回的 `byteData`，进行Base64解密，并保存为PDF文件。
    *   提供用户下载发票的功能。

## 4. 非功能需求

*   **NFR4.1 安全性：**
    *   严格保护私钥和AES密钥，避免硬编码。
    *   所有与工行的通信必须使用HTTPS。
    *   日志中对敏感数据（身份证、银行卡号、手机号等）进行脱敏处理。
    *   回调接口必须进行严格的签名验证，防止伪造请求。
*   **NFR4.2 可靠性：**
    *   接口调用失败时，应有合理的重试机制（需注意工行文档中关于特定错误码不能重试的说明）。
    *   对于需要轮询查询状态的场景，应设计合理的轮询间隔和退出机制。
    *   确保回调处理的幂等性，防止重复处理导致数据不一致。
*   **NFR4.3 日志与审计：**
    *   详细记录所有接口的请求、响应（脱敏后）以及处理过程中的关键信息。
    *   日志中应包含工行返回的 `msg_id`、`return_code`、`return_msg`，以及系统内部的Trace ID。
    *   日志格式应易于查询和分析。
*   **NFR4.4 性能：**
    *   接口调用应设置合理的超时时间。
    *   对于大量发票下载等场景，考虑异步处理或批量处理（如果工行支持）。
*   **NFR4.5 易用性 (SDK)：**
    *   SDK应提供简洁易懂的API，隐藏底层的复杂交互逻辑。
    *   提供清晰的文档和使用示例。

## 6. 风险与依赖

*   **依赖工行接口稳定性与文档准确性：** 项目成功高度依赖工行接口的稳定运行和接口文档的实时准确。
*   **网络环境：** 需要确保应用服务器与工行服务器之间的网络通畅。
*   **密钥安全：** 密钥泄露将导致严重安全风险。
*   **业务流程理解：** 对工行反向开票的具体业务流程和规则理解不充分可能导致对接失败或业务错误。
*   **接口变更：** 工行接口可能升级或变更，需要预留应对方案。

## 7. 名词解释

*   **反向开票：** 通常指由采购方（付款方）代销售方（收款方，尤指个人或小微企业）在合规前提下发起开票申请的流程。
*   **biz_content：** 工行接口中用于承载核心业务数据的JSON字符串参数。
*   **msg_id：** 消息通讯唯一编号，用于追踪请求。
*   **付方：** 在此场景中通常指企业采购方。
*   **收方：** 在此场景中通常指个人销售方。
