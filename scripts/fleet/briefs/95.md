# #95 合同组电子签署：两份文书一次签完、协议落「待签署」

议题正文即 spec（`gh issue view 95 --comments`）。相关 ADR：0036（框架收购协议走第三方电子签章——本票是它的落地）、0037（端口）、0018（五流与门禁）、0022（异议与版本留痕）。

## 前置已合并在 main 上

#91 的五步向导与 #92 的电子签章配置 / 开通 / 回调入口都已合并。你要做的是把向导第 5 步从「存一条协议记录」换成**真的发起签署**，并把状态与证据链接上去。

## 端口契约（已冻结，按它接）

- `initiate(tenantId, request)`：`request` 里是 `payeeId`、`groupName`、`documents`（每份带 `name` / `templateId` / 变量 map）、`signer`（自然人）。**回收企业是发起方、用租户级企业印章，不在签署方列表里**（ADR 0036 决策 5）。
- `createSignUrl(tenantId, signTaskId, signer)`：**现生成现用、不存不复用**（第三方默认 30 分钟）。「本人在页面上点『去签署』才生成」这个时序在本票。
- `listSignedDocuments(tenantId, signTaskId)`：已签文书，挂证据链用。
- `parseCallback(...)` 返回归一化的 `EsignCallback`：`tenantId`、`signTaskId`、`finished`（合同组**整体**签完才算，不认单份）、`unfinishedReason`、`signedAt`。
- **端口不承载协议状态**：待签署 / 生效 / 作废仍在 `icbc_framework_agreement` 上。

如果实现中发现端口**必须**加东西（比如要拿合同组流程号），可以扩展 `service/esign/EsignPort` 并同步改 `StubEsignPort`——但先确认没有别的办法，并在报告里说明为什么。

## 范围

- 两份文书（框架收购协议 + 反向发票合规告知函）装进**一个合同组**，一个签署链接、必须整体签署。**同归合同流、沿用既有证据类型 `FRAMEWORK_AGREEMENT`，不新增证据类型、不新增第六流。**
- 发起后协议状态落「**待签署**」（字段取值注释里本来就留着 0）；开票门禁给出的原因要准确（「未签署生效的框架收购协议」而不是含糊的缺失）。**门禁不应需要改动**——生效协议本来按 `status = 1` 过滤，待签署天然不满足。真需要改门禁就说明口径没对上，写进报告。
- 回调把状态推到生效并盖 `signedAt`；**重复回调不产生第二次副作用**（幂等键 / 状态机自检，照仓库里 `CallbackNotifyServiceImpl` 的既有做法）。
- **签署顺序：企业先盖章、自然人后签署**（那个自然人在我们的页面上点「去签署」）。
- 租户未开通时：`EsignPort.isAvailable(tenantId) == false` → 协议落 `PAPER`，向导照常走完，**给出可读的说明**（ADR 0036 决策 7）。
- 模板由**平台**维护、托管在第三方，租户只能填变量——模板不给租户编辑权。
- 重签与作废保持既有留痕规则：新协议生效时旧生效协议作废、历史可查。
- 已签署的文书能查询与下载，并挂进该出售者的证据链。

## 测试

全部用 mock 端口，不触网。重点：待签署状态与门禁原因、回调幂等（同一条通知重放两次只有一个副作用）、未激活降级到 `PAPER`、重签时旧协议作废。
