# #94 修票（第二轮）：处理复审的 BLOCK

分支上现有两个提交（`#94` 实现 → 上一轮修票）。**上一轮的租户收口、AC1 入口、幂等等都真修了**，复审逐条核过；但它找到一条**本票新引入的**阻断项。报告全文：`@@ROOT@@/.fleet/gates/94.review.md`（第一轮的报告已被覆盖，两份的判断都在下面）。

**先认一件事**：上一轮的派工书说「把本次本人确认过的字段（含卡号）更新上去」，**这个说法是错的**——它没说清「生效中的卡」的边界，你照着做了，所以这一处是我给错的方向，不是你乱写。这一轮要把边界划对。

**做法**：在当前分支上**再追加一个提交**，不要 `amend` / `rebase` / 改历史。

## 必修一：已入驻的档案不许直写「生效中的卡号」（ST-1）

`OnboardingWizardServiceImpl#updateArchive` 对既有档案**无条件**写 `bankCardNo` / `bankName` / `accountCode`。但仓库对这件事有明文口径（`PayeeBankCardChangeService` 类注释：「**三条硬规则都落在这里，别的调用方不要各写一套判断**」；`CONTEXT.md`「收款账户变更」；`SellerOnboardingServiceImpl` 的「换卡：收方档案里的卡**一条都不动**」）：

- 收方档案里的 `bankCardNo` 是**唯一生效中的卡**；新卡要进工行收方修改、复审通过才搬过去；
- 你的路径对已 `READY` / `PENDING` 的收方**不进工行、不复审、不查在途换卡**；而 `submitOnboarding` 遇到 `READY` 会直接 `return payee`，**永远不会**把向导写进去的卡送去工行 → 档案里的卡与工行登记的卡**静默不一致**，证据链记的是没被银行验过的卡；
- 此人若正有一笔在途换卡（变更单有 `oldCardTail`），你的写入会把档案改到变更单基准之外，`applyOnboardingResult` 收敛时对不上；
- 最要紧的是**这条路径不需要登录**：持链接者随时可写。

→ **首卡与换卡分开**：向导只负责**首卡**（还没入驻 / 还没绑卡的档案），收款账户一旦生效，**卡号 / 行名 / accountCode 一个都不许由本路径改写**。要改就走 `PayeeBankCardChangeService`（换卡单 + 工行复审）。
→ 有在途换卡时（`hasPending(payeeId)`）明确拒绝或忽略卡变更，并给**可读**提示。
→ 补测试：**`READY` + 已有卡的档案**走自填壳提交后，**卡一个字段都没变**、且没有绕开任何既有口径。这正是上一轮漏掉的那一支（现有测试只用「建档未完成 → 补首卡」的档案，`READY + 有卡` 零覆盖）。
→ 报告里说清「本人自己拍一张新卡」这个场景你怎么处置的——如果它该走换卡单，就写清走哪条路；如果本票不做，就如实标成缺口。

## 必修二：把链接锁到人身上（ST-1 的结构根因）

复审指出：派工书写「绑 `BusinessKeyType.PAYEE`」，你改了 `ONBOARDING_INVITE`（绑链接本身）。那个理由（PAYEE 绑定强迫先建 stub ⟂ 不产生半成品）**只对「待建档」成立**——**「已建档」时 `payeeId` 是已知的**，完全可以绑 PAYEE。

→ 已建档就给令牌绑 PAYEE（链接锁到那个人身上），待建档才用现在的「绑链接」形态。这样「持链接者可改本租户任意已知身份证的档案」这个面就不存在了。两条路径的取舍写进报告。
