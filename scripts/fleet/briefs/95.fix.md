# #95 修票：处理独立评审的 BLOCK

分支上已有一个提交（`#95` 的实现），**过了全量测试闸门（795 通过），但独立评审给了 `REVIEW_VERDICT: BLOCK`**。报告全文：`@@ROOT@@/.fleet/logs/95.review.log`——**先读完它**。

评审自己说得很准：核心状态机、门禁、事务边界、迁移脚本都是对的且测试为真；**问题出在「只做到后端」**——两条 AC 的一半没有任何客户端在交付。

**做法**：在当前分支上**追加一个提交**，不要 `amend` / `rebase` / 改历史。

## 必修一：「点去签署 → 生成链接并跳转」在任何一个客户端上都不存在（SP-1）

后端 `/icbc/public/agreement/sign-url` 是真的，但**全仓库没有任何调用方**：

- 现场端 `yudao-ui-field-uniapp/src/pages/payee/wizard.vue` 第 5 步只有 `PAPER` 分支的文案；`ELECTRONIC` 分支渲染 `协议已按 {{ draft.signMethod }} 建档`——**会把裸枚举 `ELECTRONIC` 显示给本人**，且半个字不提「待签署 / 去签署」。（这行在你这一票之前是死代码，现在被你变成活的。）
- `field-shared/src/api/wizard.ts` 的类型注释还写着「本票未开通电子签章时恒为 PAPER」。
- 自然人端 `SellerPortalServiceImpl.toPendingAgreement` 造出的「待签框架收购协议」条目没有可点的去处（`SellerPendingItemVO` 无 url / action 字段）。
- `#94` 的工作树里也没有这个调用——**那张票也以为是你做**。

→ 让**至少一个**客户端真的能走完这件事，并且把「谁承接签署页」写清楚：
  - 现场端第 5 步：`ELECTRONIC` 分支渲染「待签署」+ 一个真正的「去签署」入口（不能显示裸枚举）。注意**现场端拿不到自然人签署链接**（那是本人身份的事）——想清楚现场端给的是「二维码 / 可复制链接」（这正是 #91 已有的 `useHandoffLink` 干的事），由自然人端页面承接跳转。
  - 自然人端：`/icbc/public/agreement/sign-url` 由**本人点击**时调用、拿到一次性链接后跳转，页面上的「待签框架收购协议」条目要可点。
  - 两处的类型注释、`handoff.md` 里「前端按钮 / 页面不在本票」那句一并改对。
- 「签署链接只能现生成现用、不通过短信发」这条不变。

## 必修二：告知函没有单独进证据链（SP-2）

`InvoiceEvidenceServiceImpl` 只放一条 `sourceType=FRAMEWORK_AGREEMENT`、`url = agreement.getFileUrl()`，而 `pickPrimaryDocumentUrl` **刻意只取框架收购协议**那一份；告知函既不进链也不落库。

这与 **ADR 0036 决策 3** 直接冲突——那条决策否决「两份拼成一个 PDF」的理由就是「证据上两份文书要能**分别引用**」；`CONTEXT.md` 也写「反向发票合规告知函…同归合同流」。

→ 让两份文书各自成条进证据链（同归 `FRAMEWORK_AGREEMENT` 这一流/类型，**不新增证据类型、不新增第六流**），并把「主文书」的选定口径写清、写进注释。如果按现有表结构做不到各自成条，**把结构与口径说清楚**再动手，不要自行改 ADR。

## 顺手（评审点名的，逐条回应）

- **S-2（硬，与本仓库先例同一条：名字骗人比没测更糟）**：`FrameworkAgreementEsignServiceImplTest` 里 `testListSignedDocuments_onlyForEffectiveElectronicAgreement` 只验了正例，**从没构造纸协议 / 空任务号去断言那个 `only`**。补负例或改名。
- **S-3（硬）**：`handoff.md` 写「全量 icbc 794 通过」，实际 **795**（778 + 17），且同一段里 794 与 778+17 自相矛盾。改对，并把新增用例清单补全（漏了 `EsignTenantServiceTest` 的 `consumeContract`）。
- **SP-4（闸门没关）**：`/agreement/create` 手送 `signMethod=ELECTRONIC&status=1` 仍会当场盖 `signedAt = now`——**正是 #81 Problem Statement 点名的那件事**。默认路径已修好，但闸门没关；更新分支还能把一行改成 `PENDING` 却不发起，之后「去签署」必然报 `ESIGN_SIGN_TASK_ID_MISSING`。两条都堵上。
- **SP-5（幂等与文件地址耦合）**：`applyFinished` 先判「已生效即返回」再写 `fileUrl`；若回调早于文件可查，协议已生效而 `fileUrl` 为 null，幂等短路让任何重放都不会再取 → 证据链**永久缺 URL**。另外幂等只靠状态自检、无条件更新/唯一键兜底，同通知并发两次会双双通过检查。处理掉，写清取舍。
- **S-1**：同包内第三份逐字相同的 `inTenant`（`PublicEsignServiceImpl` / `PublicAccessServiceImpl`），框架里已有 `TenantUtils.execute(tenantId, Callable)`。收一处。
- **S-5**：`PublicEsignServiceImpl` 的注释与测试都强调「链接生成成功后才占用令牌次数」，但**没有用例断言失败路径没 consume / 成功路径 consume 了**。断言掉。
- **S-4**：`initiate` 里回写 `signMethod = ELECTRONIC` 是不必要的写入（调用方已保证）。删或说明。
