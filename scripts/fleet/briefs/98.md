# #98 平台访问日志的 PII 面级收口

议题正文即 spec（`gh issue view 98 --comments`），里面记了发现经过与三选一的备选。**口径已经定了**（写在这份派工书里），不要重新论证选哪条。

## 事实（我已经查过，直接用）

- PII 请求体**不是 icbc 的问题，是全平台的**：请求 VO 里带 `idCardNo` / `idNo` / `mobile` / `bankCardNo` / `email` 这类字段名的文件，icbc 22 个、`system` 17 个（`UserSaveReqVO` 就是 `mobile`）、`member` 12 个、`erp` 6 个；粗估 **34+ 个 `/admin-api` 接口**的请求体进 `infra_api_access_log`。
- `@ApiAccessLog` **本来就有** `sanitizeKeys()`（每个方法可指定）；全局那份名单是 `ApiAccessLogFilter` 里写死的 `SANITIZE_KEYS = {password, token, accessToken, refreshToken}`。
- 脱敏**是递归的**（`sanitizeJson(JsonNode, keys)` 会走数组与嵌套对象），所以加进默认名单就对全平台、对嵌套结构生效。
- 那个框架文件**自并入仓库以来零本地改动**（`git log -- .../apilog/` 只有代码并入那一次）。

## 要做的（按定下的口径）

1. **改默认脱敏名单**：在 `ApiAccessLogFilter.SANITIZE_KEYS` 里加上 PII 字段名 —— `idCardNo` / `idNo` / `mobile` / `bankCardNo` / `address` / `imageBase64`。具体加哪些你按上面的名单核对代码后定，但**不许加 `name`**（太通用，商品名 / 企业名 / 菜单名都叫 `name`，加了会把访问日志废掉）。
   - 加注释说明这是**有意为之的本地偏离**（上游默认名单不含 PII 是上游的问题，这条本身值得提 PR），并指向本 issue。
2. **保留现有的 `requestEnable = false`**：向导 4 枚、本人自填壳 4 枚、`signUrl` 1 枚（共 9 个）。两个机制管的不是一件事——`requestEnable = false` 治「整段别记」（证件影像 10MB 的解析开销、`signUrl` 的令牌在**查询串**里），默认名单治「记了也不出 PII」。**不要为了统一而撤掉它们。**
3. **加一条平台级守卫测试**：凡 `/admin-api` 控制器方法带 `@RequestBody` 且其 DTO 命中 PII 字段名单，就**必须**满足二者之一——该字段名在默认脱敏名单里，或该方法 `requestEnable = false`。
   - 枚举范围（只扫 icbc / 扫全平台）你判断并写理由；仓库有反射式一致性测试的先例（`RecyclingPermissionAnnotationConsistencyTest`、`IcbcUniqueKeySchemaParityTest`）。
   - **这条测试在加默认名单之前必须是红的**——先用一个现有接口验（比如 `POST /icbc/payee-info/create` 的 `PayeeInfoSaveReqVO` 带 `idCardNo`/`mobile`/`bankCardNo`/`address`）。把「红 → 绿」的实测输出写进报告。**一条永远不会红的守卫测试等于没写。**
4. **给「脱敏真的生效」的证据**：不要只断言注解存在或名单里有字符串。要么真调 filter 的脱敏路径、要么把那几个 private 方法提到可测的位置（怎么做得体你判断）。报告里要有**实际输入 → 实际输出**的片段，证明 `idCardNo` 那一项被去掉了、而 `name` 还在。

## 收尾

- 全量测试绿（`@@TEST_CMD@@`，一条 reactor，**不要 `mvn install`**）。
- 报告逐条对账 + common.md 那五面透镜的答案，外加三件必须直说的：
  - **框架本地偏离**：改了哪个上游文件、为什么值得提 PR；
  - **已知残留**：`name` 不脱敏 → **姓名仍会进访问日志**（不假装解决了）；
  - **运维代价**：以前有人可能靠访问日志查某个手机号/身份证去排障，改完之后查不到了——这条要不要在 handoff 里给运维留一句话，你判断。
