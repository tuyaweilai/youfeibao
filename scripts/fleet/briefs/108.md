# #108 证据档案节点化：六节点 + 缺件清单 + 链式视图（含 5 流齐备率收紧）

议题正文即 spec（`gh issue view 108`），**总规格是 #107**（`gh issue view 107`——节点表、弹窗内容表、明确不做的那几条，都以它为准）。相关 ADR：0021（只讲可核验的事）、0018（五流与门禁）、0038（一期不允许分批开票付款——节点 5 按票计数就靠它）。

`CONTEXT.md` 的「证据节点」「缺件清单」两个词条是本票的词汇表，先读它们。

## 你要改的那段代码现在长什么样（先把这三条后果看懂再动手）

`InvoiceEvidenceServiceImpl.assembleChain` 今天做的是「**收集已有的来源，然后看列表空不空**」：

```java
if (StrUtil.isNotBlank(acquisition.getWeightTicketNo())
        || StrUtil.isNotBlank(acquisition.getWeightTicketImageUrl())) {
    flowSources.get(EvidenceFlowEnum.GOODS).add(source);   // 有就挂一条
}
...
boolean present = CollUtil.isNotEmpty(sources);            // 「齐备」= 至少挂上了一条
```

1. **它答不了「缺什么」**：缺的东西从来没有被表示过——**缺件不是一条记录，是「没有记录」**。
2. **「齐备」能被一条证据骗过**：只要磅单号非空，货物流就 `present = true` 显示齐备，哪怕车尾照片、车牌、司机、结算重量全没有。
3. 所以 5 流齐备率这个**对客户承诺的交付指标现在是松的**。

本票要把它换掉：**声明固定清单 → 遍历清单逐项判定 → 缺失项即缺件清单**。

## 每个节点的固定清单（判断部分，按这个定；判定规则只用现有字段）

清单项写成枚举（key / 名称 / 归属对象 / 判定规则），别散在 if 里。下面每一项都对应仓库里已有的字段，**不要新增表、不要新增查询**。

- **节点 1 出售者档案**：收方档案存在；姓名；证件号；手机号；银行卡；住址；职业；收方入驻状态；实名（平台级自然人主体的实人认证）；框架协议生效；企业授权。归属对象是人（这页一票一人）。
- **节点 2 货单**：收购单存在；品类；毛重；皮重；净重；扣杂；结算重量；单价；金额；磅单号；磅单影像；车头照片；车尾照片；车牌；司机。归属对象是**收购单**（一票一单），除了「车次」类项要能定位到具体车次（`icbc_handover_batch` 上的车次/批次号）——参考件的「车次#0 缺司机」就是这个粒度。
- **节点 3 运输**（条件节点）：交接登记存在；运输任务存在；车牌；司机；五类运输节点（到达提货点 / 交接完成 / 起运 / 到达场站 / 卸货完成）各自的上报（时间 + 位置 + 照片，照片必填的两类按 `LogisticsTransportNodeTypeEnum` 的既有口径）。归属对象是**停靠点 / 车次**。
- **节点 4 合同**：框架收购协议文件；反向发票合规告知函文件；单笔收购确认书；结算确认（含线下签字件的确认结论）。归属对象是**出售者 / 协议**。**不显示「生效期」**（表里没有这个字段），改显示「回收期次 + 签署时间」。
- **节点 5 资金**：付款单存在；收款人姓名；收款卡号；金额；回单号；回单文件；支付状态为成功。归属对象是**付款单**（一票一单，ADR 0038），文案要能写成「马新博：缺银行回单」。**摘要按票计数**（「本票付款 1 笔•已留回单 0/1」），**不要引入结算单做分母**。
- **节点 6 收款确认**：`seller_received_confirmed_at` 是否已确认。**未确认不是「缺失」**——文案是「等出售者本人确认」（ADR 0021：银行受理与本人确认是两件事，不可合并、不可互相替代）。

**节点 2 与节点 3 的分界 = 场站的门**：门内（过磅、卸货、进出场与磅秤照片、车牌、司机）归节点 2，门外（提货点、交接、起运、位置、途中照片、轨迹）归节点 3。到场自送的单子 `logistics_handover_id` 为空 → 节点 3 `applicable = false`。

## 三件容易做错的事

1. **不适用 ≠ 缺件**。自送单的完整度分母是 5，节点 3 显示「不适用」，且**不能被「仅看缺件」筛出来**。
2. **「仅看缺件」的分页**。完整度在 Java 里算，直接在 SQL 里加条件会把 `total` 算错。建议：把判定抽成一个纯函数/组件（`EvidenceCompletenessEvaluator` 之类），「仅看缺件」走「按原条件取（带一个明确上限，比如 2000 票）→ 逐票判定 → 过滤 → 分页」的路径，`total` 用过滤后的真实数；超上限时在响应里带一个标志、页面提示「结果可能不完整」。**必须有一条测试钉住 `total` 正确**。别用「本页过滤后凑下一页」那种把复杂度摊进分页循环的写法。
3. **齐备率收紧的口径**：`present`（某一流齐备）改成「**该流下所有节点的清单全命中**」；`missingFlows` 仍是流名，保持不变。数字会掉——提交报告要写明「这是变更，不是退步」。

## 前端（链式视图）

只有一种排布，**不做星链图**。名字叫「链式视图」，**不要叫「线路图 / 路线图」**（本项目「线路/路线」已被运输路线占用，而且这页里就有「物流轨迹」，两个词并列没人分得清）。

- 改的就是现有页面 `/views/icbc/evidence/index.vue`（菜单 5151），**不新增菜单、不新增权限**。
- 节点可点开；弹窗外壳沿用参考件形态：右上角 `n/6` 页码、缺件清单、摘要（一句话 + 计数 + 合计）、明细表；键盘 `←` `→` 切节点、`ESC` 关闭，并有「上一节点 / 下一节点 / 关闭」按钮。
- **不做二级抽屉**：点证据项直接开文件，或跳到已有页面——按菜单名去找路由，别自己拼：节点 1 → 出售者档案 / 建档；节点 2 → 收购登记（改照片走既有的 correct 通道）；节点 4 → 电子签章协议 / 结算单；节点 5 → 付款记录；节点 6 无跳转（那是出售者端的动作）。**人工补录类**的缺件项走本页已有的 5152「补录证据」弹窗，**不要新做上传弹窗**。
- 节点 2 **不许出现「物流合规」「轨迹匹配正常」这类结论词**（参考件有这一栏，明令不抄）——一期只有司机上报的一次性定位快照，两个点之间的连线不是真实路径（CONTEXT「轨迹」）。换成可核验的计数：「运输节点 5/5 已上报（含位置与照片）」。
