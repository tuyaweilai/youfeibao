# #97 收方档案的唯一键补 tenant_id

议题正文即 spec（`gh issue view 97 --comments`）。相关：ADR 0017、`CONTEXT.md` 的「收方档案 / 自然人主体」两条（收方档案是「自然人 × 回收企业」这一层）。

## 口径已经定了（不要再纠结这一层）

仓库里已有的三条事实，决定了这是个**很小的放开**：

1. `icbc_payee_info` **不在** `yudao.tenant.ignore-tables` 里 → MyBatis-Plus 的租户插件已经在给它的查询加 `tenant_id` 条件。
2. 服务层的 `PayeeInfoServiceImpl#validateIdCardNoUnique` / `#validateMobileUnique` 走的是 `selectByIdCardNo` / `selectByMobile`，**已经是租户级的**（同一套插件）。也就是说「本租户内一张身份证一份档案」这条业务规则**已经实现了**，只有 DB 的键没跟上。
3. 现有的键 `(id_card_no, deleted)` / `(mobile, deleted)` **严格强于** `(tenant_id, id_card_no, deleted)` / `(tenant_id, mobile, deleted)` —— 所以**放宽键不可能产生违法行**，迁移是纯放开。（本地库实测：3 行、1 个租户、同租户内无重复身份证/手机号。）

**要做的**：把两个键改成含 `tenant_id` 的版本。

## 具体要求

1. **建表脚本**（`backend/sql/mysql/icbc_payee_info.sql`）：`uk_id_card_no` → `(tenant_id, id_card_no, deleted)`，`uk_mobile` → `(tenant_id, mobile, deleted)`。
2. **迁移脚本**：新起一个文件（`backend/sql/mysql/icbc-payee-unique-key.sql`），照 `icbc-payee-account-code.sql` / `icbc-wallet-columns-drop.sql` 的幂等写法（`information_schema` 判存在 + `PREPARE`/`EXECUTE`，首行 `SET NAMES utf8mb4;`，`--` 后必须跟空格）。**先 DROP 旧键再 ADD 新键**，两个键都要幂等，重复跑不出错。
   - 注意 `icbc-wallet-columns-drop.sql` 踩过的坑：那份文件的守卫按 `DATABASE()` 判存在，**不带库名跑会静默不干活**，所以它加了硬失败守卫。你这个文件要不要同样的守卫，你判断——但必须**在文件头写清怎么跑**，并且**真的在 MySQL 上跑过两遍**（本地 13308 是活的，用**临时库**，跑完删掉，别动共享的那个库）。
3. **测试建表**（`.../test/resources/sql/create_tables.sql`）**对齐到与生产完全一致**：现在是 `(tenant_id, id_card_no)` / `(tenant_id, mobile)`，**少了 `deleted`**。这个不一致正是这条 bug 藏了这么久的原因（单测在含 `tenant_id` 的测试 schema 上跑，生产是不含的）。
4. **补一条**真会红的**回归测试**。注意这里有个陷阱：单测跑在测试 schema 上，而测试 schema 本来就有 `tenant_id`，所以「跨租户建档成功」这种用例**修之前就是绿的**、抓不到任何东西。**要抓的是两份建表脚本的键不一致**。所以请写一条**比对两份建表脚本**的测试（解析 `backend/sql/mysql/<表>.sql` 与测试 `create_tables.sql` 里同一张表的唯一键列集合，断言一致）——
   - 它**在修之前必须是红的**（先用 `git stash` 或临时改回去验一遍，把这一步写进报告）；
   - 范围你定：只钉 `icbc_payee_info`，还是把所有两份文件里都存在的 `icbc_*` 表的键都比一遍（后者更有价值，但可能撞上既有的合法差异——撞上了就把差异列进白名单并说明理由）。
   - 另外补一条行为用例：**同一身份证在租户 1 与租户 2 各建一份档案，两边都成功、且各自只看到自己那份**（`IcbcTenantTestConfiguration` 打开租户拦截器，别在同租户里自证）。
5. **`docs/agents/handoff.md`** 追加本票的段；`backend/sql/mysql/README.md` 的导入顺序追加一行（放在 `icbc_payee_info.sql` 之后，字母取下一个空位）。

## 明确不改，但要在报告里写清判断

- **`icbc_payer_info` 的 `uk_credit_code` / `uk_tax_no` 不含 `tenant_id`**：同一法人在这套模型里能不能在两个租户下各有一份付方档案？（演示租户 + 客户真租户这种场景会不会撞？）**本票不要改它**，只给出判断与依据。
- 我扫过全部 icbc 建表脚本，31 个「租户级表 + 不含 tenant_id 的唯一键」里绝大多数是**合理的全局键**（我们生成的单号 `acquisition_no` / `station_code` / `payee_no`、工行的 `msg_id` / `notify_id`、`jti` 等）。报告里说明你的比对测试是怎么把这些排除掉的（白名单还是规则），别把噪音当问题。
- `deleted` 进唯一键有个**既有**的毛病：同一租户同一个人「软删 → 重建 → 再软删」时，第二次软删会撞键（两条 `deleted=1`）。你**不要改键的语义**去绕它（那是另一件事），但在报告里如实点出来，并说明这次改动的语义与改之前**完全一致**。
