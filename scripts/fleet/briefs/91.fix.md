# #91 修票：处理独立评审的 BLOCK 与同批发现

这个分支上已经有一个提交（`#91` 的向导实现），它**过了全量测试闸门，但独立评审给了 `REVIEW_VERDICT: BLOCK`**。评审报告全文在 `@@ROOT@@/.fleet/logs/91.review.log`（也可以看 `.fleet/gates/91.review.md`）——**先把它读完**，下面是我按优先级排的处理清单。

**做法**：在现有分支上**追加一个提交**，不要 `amend`、不要 `rebase`、不要改历史——评审要能看清「第一版是什么样、修了什么」。

## 必修（不改不算完成）

**SP-1 证件有效期没有落在自然人主体**（这就是 BLOCK 的理由）
`#91` 验收与父票 #81 decision 5、`CONTEXT.md:68` 都要求「姓名、证件号、证件有效期」由**自然人主体**持有，但 diff 只写进了 `icbc_payee_info`。补齐：

- `icbc_natural_person` 加 `id_sign_date` / `id_validity_period`（`varchar(10)`，语义与收方档案同名列一致：`yyyy-MM-dd`，长期 `9999-12-30`）。
- 增量迁移 SQL **新起一个文件** `backend/sql/mysql/icbc-natural-person-id-validity.sql`，照 `backend/sql/mysql/icbc-payee-account-code.sql` 的幂等写法（`information_schema` 判存在 + `PREPARE`/`EXECUTE`，`SET NAMES utf8mb4;`，头注写清为什么）。同时同步 `icbc-natural-person.sql` 的建表语句（新库直接是最终形状）、`backend/sql/mysql/README.md` 的导入顺序、测试 `src/test/resources/sql/create_tables.sql`。
- `IcbcNaturalPersonDO` + 两个字段（注意 `varchar(10)` 与 `@Size` 的对齐，`PayeeInfoServiceImplTest` 踩过 Podam 撞列宽的坑）。
- `NaturalPersonRegisterReqVO` + 两个入参；`NaturalPersonServiceImpl.register`：**创建时写入，复用时只在空缺处回填**（不覆盖既有值——与 `reuse` 那条「不覆盖」的精神一致，理由写进注释）。
- `PayeeInfoServiceImpl.registerNaturalPerson`（4 个调用点：`createPayeeInfo` / `updatePayeeInfo` 等）把这两个值带上。
- 测试：断言向导提交后**自然人主体**上有这两个值，以及「第二家回收企业复用同一主体、已填的值不被覆盖」。

**ST-1（评审说是硬伤）换卡后档案上的 `accountCode` 与真卡脱节**
`PayeeBankCardChangeServiceImpl.promoteCard` 搬了新卡的卡号 / 行名 / 支行 / 证件日期，**唯独没搬 `accountCode`**；而本票把 `SellerOnboardingServiceImpl` 改成「入驻发起优先取 `payee.getAccountCode()`」。于是换卡审核通过后，档案里仍是旧卡的值，下次重发入驻会把旧结论报给工行，后台表单也显示假值。
→ 让 `promoteCard` 一并同步 `accountCode`（档案是权威），并补一个测试。如果修的过程中发现「让 `submitOnboarding` 认档案副本」本身就是错的，那就改掉那条、并在报告里说明。

**SP-3 第 1 步的硬拦可以被重拍绕过**
`wizard.vue` 里人像面与国徽面把结果写进**同一对** `idWarnings / idBlockReasons`，后者覆盖前者，而放行只看 `idBlockReasons`。于是「临时身份证」这种硬拦只要再拍一张干净的国徽面就没了。端口契约写明 `blockReasons` 非空即不可继续。
→ 正反面各自保留一份，放行时两边都看。补前端断言做不到，就在报告里说清你靠什么验的。

**SP-5 草稿会串到下一位出售者 / 同一租户第二次建档被硬拒**
草稿是**单一 key**，建档结束或换人时不清，下一位出售者会看到上一位的照片与字段。另外同一自然人在**同一租户**第二次建档会被 `PAYEE_ID_CARD_EXISTS` 硬拒，向导没有「此人已有档案」的分支。
→ 至少把 key 与本次建档绑定（带上身份证号或 payeeId），并在建档结束 / 「换一位出售者」时清干净。第二次建档那条，如果本票内不便做完整分支，至少给出**可读的提示**而不是一句错码，并在报告里标出来。

**SP-2 `accountCode` 的「只在空缺处回填」是死路**
草稿初值是 `'1'`、提交时恒为 `'0'/'1'` 从不留空，所以后端 `pick(人工值, 识别值)` 永远命中人工分支，识别结果**永远回填不进这个字段**；这也让「从此不是猜的 1」变成空话。
→ 初值留空表示「未确认」，提交时按 `人工值 → 识别值 → 缺省` 三级取，让这条口径在这个字段上真的成立。

**T-1 / T-2 测试不实**
- `testSubmit_sameIdCardReusesExistingNaturalPerson` 名字声称「第二家回收企业」，实际在 `tenantId = 1` 内跑，跨租户那条**没有被真正执行**。要么真的跨租户验，要么把命名与断言改成它实际验的东西——**名字骗人比没测更糟**。
- 补一条「端口全空 → 仍能 submit 落库且落库形状与识别成功时同形」（这是 #91 验收里明写的一条，现在只是间接代表）。

**ST-3 顺手清掉**
`OnboardingWizardServiceImpl` 里那份 `DEFAULT_ACCOUNT_CODE = "1"` 与 `SellerOnboardingServiceImpl` 的重复；`PayeeAddReqVO` 里与本票无关的 `@Schema` 文案改动还原掉。
