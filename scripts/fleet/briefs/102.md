# #102 异常日志里的 PII 值：C（治源头）+ D（权限收口）

议题正文即 spec（`gh issue view 102 --comments`）。**口径已经选了 C + D**，不要再论证 A/B。

`#98` 治的是「按字段名删键」，`#101` 把异常日志的请求体接进了同一份名单。**本票治的是「值」**：键名脱敏管不到 message 里被拼进去的值。

## 事实（已核）

`GlobalExceptionHandler.buildExceptionLog`（`yudao-framework/yudao-spring-boot-starter-web/.../web/core/handler/`）往日志行里写**三个**带文本的字段：

```java
errorLog.setExceptionMessage(ExceptionUtil.getMessage(e));
errorLog.setExceptionRootCauseMessage(ExceptionUtil.getRootCauseMessage(e));
errorLog.setExceptionStackTrace(ExceptionUtil.stacktraceToString(e));   // 栈里含同一段文本
```

而 MySQL 的唯一键冲突报文**自带键值**：

```
Duplicate entry '1-110101199001011299-0' for key 'uk_id_card_no'
```

所以**身份证号会明文进 `infra_api_error_log`**（三个字段都带）。`#100` 只把 `icbc_payer_info` 那一处换成了可读文案，别的表照旧。

## C：从源头治

**要求（可验证的）**：那一行里的 `exception_message` / `exception_root_cause_message` / `exception_stack_trace` **都不再出现 PII 值**，并且仍然**能定位是哪个约束/哪里出的问题**（约束名、类名、栈帧都是安全的，只有**值**要去掉）。

已知的值来源与做法（机制你定，但要说清为什么）：

1. **DB 约束报文**（`DuplicateKeyException` / `DataIntegrityViolationException`）——最常见的主源，必须治。注意**别只治 `exceptionMessage` 那一栏**：`rootCauseMessage` 与 `stackTrace` 里是同一段文本，三个都要处理。
2. **我们自己的 `exception(CODE, 值)`**：grep 一遍把 **PII 值**拼进消息的地方（`idCardNo` / `mobile` / `bankCardNo` / 住址，不只 icbc，`system` / `member` 也看），改成不带值、或只留尾号（仓库已有 `MaskUtils.cardTail` 这类先例）。
3. **不要引入面向所有消息的通用正则脱敏**——那是被否掉的 B。要治的是**已知会带值的那几类**，在它们各自的位置治。
4. **`@Valid` 那条路径核一遍**：`GlobalExceptionHandler` 用的是 `getDefaultMessage()`（我们自己写的文案，不含 `rejectedValue`，从代码看是安全的），但要确认**没有别的分支**把 `rejectedValue` 拼进消息或日志。
5. **测试**：真造一次撞键（挑一个**带 PII 的键**，比如 `icbc_payee_info` 的身份证号 / 手机号），断言传给 `ApiErrorLogApi#createApiErrorLogAsync` 的 DTO 里**三个字段都不含那个值**（照 `#101` 的做法——断言在写库行的载荷上，不是断言「没抛异常」）。**改之前必须是红的**，红→绿输出写进报告。

## D：查看权限收口到平台运营

`infra:api-access-log:*` / `infra:api-error-log:*` 的菜单**现在在回收企业套餐里**（实测 id 1082–1089；套餐 200 的 `menu_ids` 是 `system_menu` 根 `(1, 2, 5200..5209)` 的递归闭包，`2` 就是基础设施，所以整套基础设施都进去了）。

- **错误日志**必须收口：把它的**页面菜单 + 按钮**从套餐 200 里排除，并写清为什么（行里是请求体与异常原文）。
- **访问日志**要不要一并收口，你判断并写理由：它已经过 `#98` 的脱敏，但仍含 `name` 等未脱敏字段。倾向一并收口（同一类「请求/异常原文」），但如果你发现有正当的租户自服务需求，说出来。
- 平台运营自己**不受影响**（它在系统租户，菜单全量）——**只动套餐 200**。
- 改的是 `backend/sql/mysql/icbc-menu.sql`（那个文件会重建套餐 200）。要求：**幂等**、别破坏它既有的「整份重建」语义、排除用**显式 id 或显式条件 + 注释**（不要模糊匹配）。
- 验收方式要给出：**租户 admin 登录后看不到那两个页面**（能实测最好；做不到就说清验到哪一层——`menu_ids` 的实测输出 + 为什么它决定可见性，参考 `#41` 时期对套餐收敛的验证方式）。

## 报告

逐条对账 + common.md 那五面透镜的答案，外加：

- **三个字段各自怎么处理的**（这一栏是 message、那栏是栈，分别怎么保证不带值）；
