# #101（只做①）异常日志不再整段记 body

议题正文即 spec（`gh issue view 101 --comments`）。**口径已经选了 A：抽出共用的 sanitizer，让异常日志也走同一份脱敏名单。**不要再论证 A/B。

**本票只做①。**②（`name` / `code` 这类通用字段名进不了名单）是「字段名粒度的天生上限」，**不在本票**——只在报告里如实记一句。③（闸门不编框架模块）**已经在主分支上修掉了**（`fix(agents): 闸门要编到改动真正碰过的模块`），本票不必再管，但注意闸门的 reactor 现在会按 diff 把 `yudao-framework/yudao-spring-boot-starter-web` 一起编进来，所以你改框架会被真的编译与测试。

## 问题

`GlobalExceptionHandler.buildExceptionLog` 把 `query + body` **原样**写进 `infra_api_error_log`：

- 既**不经** `@ApiAccessLog` 的任何开关（`requestEnable = false` 对它无效）；
- 也**不走** `ApiAccessLogFilter` 的那份脱敏名单。

所以**任何抛异常**的请求，请求体会整段落库——包括证件/银行卡影像 base64（截 8000 字符后照样写）。`#98` 只堵了正常路径与访问日志表，异常路径一点没动。

## 要做的

1. **抽一份共用的 sanitizer**，让 `ApiAccessLogFilter` 与 `GlobalExceptionHandler` 用同一份口径（名单只留一处）。位置你定，但要说明为什么放那儿（`framework/apilog` 下的东西被 `framework/global` 引用不一定合适）。
   - 注意 `#98` 已把 `ApiAccessLogFilter` 的脱敏方法从 `private` 改成**包级**（为了可测）——那是包级的，跨包用不了，所以「抽出去」这件事本身是对的。
2. **两个判断点，你要给理由**：
   - **`requestEnable = false` 的语义要不要在异常日志上生效？** 向导 4 枚、自填壳 4 枚关了访问日志的 body，但它们**抛异常时**错误日志照样会记。按 `#98` 定下的口径（那 9 处关掉是为了「证件影像 10MB 的解析开销」与「`signUrl` 令牌在查询串里」），异常日志**理应也尊重它**——你要不要在异常日志上读同一个注解？同意了就把理由写进报告与代码注释。（提示：`GlobalExceptionHandler` 能拿到 `HandlerMethod` 吗？拿不到就说明你怎么处理的。）
   - **`infra_api_error_log` 的 body 是怎么拼出来的**：确认它拼的形状（`query + body` 的拼接方式），别只脱敏一半（比如只处理了 JSON 那半、漏了查询串，或反过来）。
3. **测试**：
   - 行为测试要有**真实输入 → 实际输出**（照 `#98` 里 `ApiAccessLogFilterSanitizeTest` 的做法），证明顶层 / 嵌套对象 / 数组三层里的 PII 都没了，而 `name` 之类该留的还在；
   - 一条**能钉住「异常路径不再落 PII」**的用例——即真的抛一个异常、断言写进 `infra_api_error_log` 的内容里没有那些键。**这条在改之前必须是红的**，把红→绿的实测输出写进报告。
4. 全量测试绿（`@@TEST_CMD@@`，一条 reactor，**不要 `mvn install`**）；框架模块的测试也要跑（闸门现在会带上它，但你自己确认一遍）。

- `requestEnable` 那个判断的结论与理由；
- 红→绿证据；
