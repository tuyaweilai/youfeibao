# #99（只做①）测试建表与生产建表全对齐

议题正文即 spec（`gh issue view 99 --comments`）。**注意：本票只做「① 3 处建表差异全对齐」。** ②（`icbc_payer_info` 四个全局键属于哪一层）已经拆到另一张票去等一个领域答复，**本票不要碰 `icbc_payer_info` 的键**。

## 口径已定

**全对齐，最后 `KNOWN_DRIFT` 白名单必须是空的。**

理由：#97 的 bug 藏了那么久，根因就是测试 schema 与生产 schema 不是同一张表（单测绿是因为跑在含 `tenant_id` 的测试 schema 上）。留白名单等于「下一个同类差异只需再加一行」而不是修掉。`IcbcUniqueKeySchemaParityTest` 的白名单是**自清理**的（差异集合必须**恰好等于**白名单），所以「对齐完成」这件事**本身可验证**：白名单空了就是对齐了。

## 三处差异（我核过的形状）

| 表 | 生产 | 测试 | 方向 |
|---|---|---|---|
| `icbc_payee_info` | 另有全局 `uk_payee_no (payee_no)`、`uk_partner_payee_id (partner_payee_id)` | 没建 | 测试**更松** |
| `icbc_invoice_order` | 全局 `uk_partner_order_id (partner_order_id)` | `(tenant_id, partner_order_id)` | 测试**更松** |
| `icbc_payment_order` | `(partner_order_id, deleted, tenant_id)`、`(order_no, deleted, tenant_id)` | `UNIQUE (partner_order_id)`、`UNIQUE (order_no)`（无 `deleted`、无 `tenant_id`）| 测试**更严** |

## 硬要求

1. **不许把 schema 改松来迁就测试。**对齐的方向是**测试建表向生产看齐**，不是反过来。如果对齐后有测试红了，改的是**那条测试的数据**，不是 schema。
2. **每条改动的测试数据都要说明为什么。**已知会撞的一条：`#91` 的 `testPayeeSameNaturalPersonCanExistInTwoTenants` 在两个租户插入了**相同的**人工 `payeeNo` / `partnerPayeeId`——生产的全局键本会拒绝这个形状。按生产的真实行为（`generatePartnerPayeeId()` 是 `PAYEE_<毫秒>_<UUID8>`、`payee_no` 由工行返回），**两个租户各自生成一个不同的编号**才是真实形状。这类改动逐条列进报告。
3. **`icbc_payment_order` 那处方向相反**（测试更严）：对齐后测试会变**更宽松**。要确认没有测试在依赖「更严」的假设（比如靠全局唯一来断言「同一 `order_no` 不能落两条」——那是 `tenant_id` 维度的行为，生产本来允许跨租户重复）。
4. **白名单清空**：`KNOWN_DRIFT` 移掉，并确认那条测试的「差异集合必须恰好等于白名单」在空白名单下仍然成立（即差异集合为空）。
5. 全量测试绿（`@@TEST_CMD@@`，一条 reactor，**不要 `mvn install`**）。

## 报告

逐条对账 + common.md 那五面透镜的答案，外加：
- **改了哪几条测试的数据、各是为什么**（要能对上「生产真实形状」）；
- 白名单清空后那条比对测试的实测输出；
- 如果对齐过程中发现**新的**两侧差异（不只是这三处），一并列出并处理——这条测试的价值就在于它现在能看见全部差异了，别只盯着我列的三个。
