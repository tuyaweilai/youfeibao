# #100 修票（第二轮）：把「撞键给可读错误」补全，并改正 handoff 里那句错的理由

分支上现有两个提交。上一轮的 BLOCK-1（软删重建）已真修，复审独立复现确认；但它抓到**另一半**。报告全文：`@@ROOT@@/.fleet/gates/100.review.md`。

**做法**：再追加一个提交，不要 `amend` / `rebase`。

## 必修一：兜底只覆盖了 `credit_code` / `tax_no`，另两个键客户端也能触发

`icbc_payer_info` 有**四个**唯一键。上一轮把兜底回读做在 `credit_code` / `tax_no` 上，理由是「另两个是生成的、撞键不在业务射程内」——**这个理由只对 `addPayerToIcbc`（内部生成）成立，对 `create` / `update` 不成立**：

- `PayerInfoSaveReqVO.partnerPayerId` 标注 **`requiredMode = REQUIRED`** —— 管理员**确实要填**（它是与工行约定的子商户编号，`create` 只在它为 `null` 时才生成）。填重了就是裸 500。**所以「不接受客户端传值」这条走不通**，它是合法输入。
- `PayerInfoSaveReqVO.payerNo`（"工行付方编号"）**没有任何校验**，而 `addPayerToIcbc` 会**无条件**把它覆盖成 `generatePayerNo()` 的结果——也就是说它是**一个会撞键的死输入**。

**要做的**：

1. `partnerPayerId` 纳入预检 + 兜底回读，给**可读**文案（「该合作方付方编号已被占用，请换一个」一类；仍然不点名是哪家企业）。
2. `payerNo` **先判断它是不是死输入**（读一遍代码：除 `addPayerToIcbc` 的覆盖外，有没有任何路径读它 / 从工行回填它？）。判断结果决定做法：
   - 是死输入 → **从 VO 里去掉**（客户端填了也没用、还会撞成 500），报告里说明这是**收紧 API**而非放过；
   - 有读取路径 → 一并纳入预检与兜底。
   两种都要写清依据。
3. **把这张表的四个键逐个过一遍**，列一张表：每个键「客户端能不能触发撞键 / 现在撞了会发生什么 / 修完会发生什么」。这一轮要把它**补全**，不要再留「射程外」这种未核实的说法。
4. 补一条**能稳定复现** `partnerPayerId` 重复的用例（不需要并发），断言抛可读码而不是 `DuplicateKeyException`。

## 必修二：handoff 里那句错的理由要改正

`docs/agents/handoff.md` 里上一轮写了「另两个键是生成的，撞键不在业务射程内」——**这是编的**（`partnerPayerId` 是 REQUIRED 的输入）。复审把这条与上一轮的 BLOCK 归为同一类：**把没做到的写成已经做到**，而 handoff 正是下游票读的脊柱文件。

→ 让 handoff 上**当前**那句话与实现一致。注意 handoff 的约定是**只追加**（复审也点了上一轮的就地改写）——所以**追加一条更正**，不要继续改写历史。

## 记录即可（不单独拦）

`addPayerToIcbc`（`@Transactional`）里兜底回读处在 REPEATABLE READ 的一致性读快照下——并发方在预检之后提交的那一行**读不到**，兜底仍会 `throw cause`。`create` / `update` 不在事务里（autocommit），不受影响。**这条与仓库既有的 `NaturalPersonServiceImpl#register` 同病**，如实记进报告，本票不改。

## 收尾

- 全量测试绿（`@@TEST_CMD@@`，一条 reactor，**不要 `mvn install`**）。
- 报告逐条对账 + 五面透镜，外加：**四键表**（见必修一第 3 条）、`payerNo` 死输入的判断依据、handoff 更正那一句的前后对照。
