# 采购与仓储的对象模型：合同扩 ERP、交易对方双外键、库位与批次也扩 ERP、本期不做成本

[ADR 0025](./0025-引入-yudao-ERP-作为采购与库存底座.md) 定了启用 ERP 的哪几个域，本文定这些域里**要新增和改造哪些对象**。

**决策**

1. **采购合同新建 `erp_purchase_contract`，扩在 ERP 采购域**。粒度是「一个合同 → 多个采购订单 → 多次收货」，合同**需要审核**，审核通过前不得作为有效采购依据。**不动 `icbc` 侧的「框架收购协议」**：那是自然人出售者对开票与代办税费的授权附件，是**开票前置**；合同是**采购条款**。两个门禁服务不同目的，合并会互相污染。
2. **交易对方用双可空外键承载**：`erp_purchase_order` / `erp_purchase_in` / `erp_stock_in` 加 `counterparty_type`（自然人出售者 / 单位供货方）+ `payee_id`（指向 `icbc_payee_info`，可空）+ `supplier_id`（指向 `erp_supplier`，可空），用 CHECK 约束保证**恰好一个非空**。
3. **库位与批次也扩在 ERP 侧**：`erp_warehouse` 加 `station_id`（归属场站）；新建 `erp_stock_location`（库位）与 `erp_stock_batch`（批次）两张表；`erp_stock` 的索引从 `(product_id, warehouse_id)` 改为 `(goods_config_id, warehouse_id, location_id, batch_id)` 并**升级为唯一约束**（同时修掉上游"查不到就插一行 0"的并发缺陷）。
4. **本期不做成本核算**。库存只做**数量台账**，`erp_stock` / `erp_stock_record` 不带金额；经营报表按发票与结算的金额汇总，不从库存推成本。

**Considered Options**

- **交易对方用 `erp_supplier` 统一装两种**（加主体类型与 `payee_id`）。未采纳：那样一个自然人出售者会对应一条 `erp_supplier` 记录，等于**把自然人档案复制一份**，必须双写同步——正是 ADR 0018/0019/0021 一直在防的"两个事实源"。
- **新建统一的交易对方表，把 `icbc_payee_info` 也纳进来**。未采纳：自然人档案带实名认证、收方入驻、绑卡、企业授权等一整套字段与状态机，迁移代价远大于收益。
- **库位与批次建在 icbc 侧**。未采纳：库位与批次是**库存的维度**，与库存分家会让"货在哪"出现两个答案。
- **做成本核算（移动加权 / 先进先出 / 结算前暂估）**。未采纳：① ERP 的库存表与流水表**完全没有金额字段**，单价只存在于单据行，且是"单据存在即有金额"、无来源版本与确认标记，不满足 ADR 0021「金额与状态只讲可核验的事」；② **销项不做**，成本没有出口（没有销售收入、没有毛利），现在算出来的成本无人核对，等销项来了还要重做一遍。规划 M06 自己写了"正式成本核算策略另行定义"。

**Consequences**

- M06 的改造量级从"中–大"降到"中"。
- 与 M06 的文案约束一致：只有入库记录时，页面只能称**累计入库**，不能称**当前库存**；要称当前库存，必须同时有期初、出库 / 退货出库、盘点调整与跨仓调拨。
- "结算前为暂估、结算后调整"这一条本期不实现。库存数量不因结算而变。
- 采购合同审核、双外键的 CHECK 约束、`erp_stock` 的唯一约束，都需要在 `backend/sql/mysql/erp.sql` 之上叠加各自的增量 SQL 文件，不直接改上游 DDL（保持与上游可比对）。
