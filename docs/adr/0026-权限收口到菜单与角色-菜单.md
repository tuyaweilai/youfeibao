# 权限收口到菜单与角色-菜单，`RecyclingRoleEnum` 降级为生成种子

租户内权限将来只认一套：`system_menu.permission` + `system_role_menu`（即 yudao 原生的 `@ss.hasPermission`）。`RecyclingRoleEnum` 不再在运行时判权，而是作为**权限与角色的单一来源**，由一个幂等同步过程把它写成菜单权限行与角色-菜单种子。

**背景**

- 现在有两套判权并存：`icbc` 域全部走 `@icbc.hasPermission`，依据是 `RecyclingRoleEnum` 里写死的「角色 code → 权限集合」，与菜单数据无关；`erp` 域与 yudao 其余部分走 `@ss.hasPermission`，依据是数据库里的菜单与角色-菜单关联。
- `RecyclingPermissionChecker` 的类注释解释了当年的理由：回收企业的四个角色是"一套固定的、跟代码一起演进的角色策略"，不依赖菜单数据，所以新租户开出来天然就有权限。
- 代价是**菜单退化成显示层**：改菜单不影响谁能做什么，真正管权限的是那个 Java 枚举。两者能不一致（菜单看得见但接口 403，或反过来），引入 ERP 后这个裂缝会立刻放大。
- 这也让"回收企业租户的菜单应该和自己强相关"这句话在技术上不成立——除非菜单重新成为权限来源。
- 另一个事实：系统租户的 `super_admin` 走 `PermissionServiceImpl` 的全量分支，看到的是**全库菜单**（实测一级菜单 18 个，只有 3 个是回收业务）。所以"平台运营"这个前台在结构上并不存在。

**Considered Options**

- **全收口到菜单权限、废弃枚举**：把 `icbc` 的注解全量改成 `@ss.hasPermission`。改得干净，但丢掉"新增功能自动有权限"的性质——以后每加一个权限位，都要同步改租户套餐种子，漏了就 403。
- **维持两套，只用测试锁一致性**：改动最小，但两套来源会长期各自演进，ERP 与本仓库其余模块继续分叉。
- **混合：枚举保留为单一来源，由它生成种子与菜单权限行**。采纳。

**Consequences**

- 需要一个**幂等**的同步过程（启动时或迁移脚本）：读 `RecyclingRoleEnum`，确保对应的 `system_menu` 权限行与 `system_role_menu` 关联存在且正确，并保留管理员以外的角色按套餐裁剪的能力。
- 需要一条**一致性测试**：锁住枚举里的权限与代码上真实使用的注解一致（现在 `icbc` 侧注解里既有 `RecyclingPermission.*` 常量、也有写死的字符串字面量，两种写法并存，先统一成常量）。
- `tenant_package.menu_ids` 由此成为"不同回收企业拿到不同功能"的载体——这才是 ADR 0005 多租户 SaaS 想要的形态。
- 平台运营与回收企业租户的菜单必须**分开**：平台运营是系统租户（`packageId = TenantDO.PACKAGE_ID_SYSTEM`，菜单全量），回收企业是租户套餐。收敛后这套机制才真正生效，而不是靠 `icbc:platform:*` 前缀区分。
