# 自然人侧零录入：采集责任归回收企业，一期只服务专业散户

收购业务的全部数据录入由**回收企业的收货员**在手机/平板上完成。自然人出售者在系统里只做**一次**动作——在工行页面上确认开票信息，不装 App、不填单。平台一期只服务**高频重复出售的专业散户**，不做偶尔卖一次废品的普通居民。

**Considered Options**

- **让司机或自然人自行填报**。未采纳：他们是回收企业的供应商，不是平台的客户，把录入成本转嫁给最没有动力配合的一方，就是数据造假风险的来源。且完成一套「实名 + 人脸活体 + 银行卡 + 收方入驻 + 分行审核」对一次性出售者的成本高到不可能完成。
- **采集归回收企业雇员，自然人零录入**。采纳。

**Consequences**

- 数据质量的激励对齐在回收企业身上：收货员填错，票开不出来，直接影响他自己的活。
- 出售者的定位是**专业散户**——天天往回收站送货的个体收废品者。依据：资环链金披露的 2.3 万自然人出售者对应 48 家回收企业，人均关系稳定（≈480 人/企业），不是随机流量。
- 因为只做一次，注册流程**可以做重**：身份证 OCR、银行卡识别、活体核验、收方入驻、分行审核都放在首次；此后每笔交易无感。
- 出售者的 500 万额度会真的被撞到，额度监控与跨企业合并计算是必备功能，不是边界情况。
- **一次性出售的居民一期不做。** 若将来要做，需要另一条更轻的通道（例如不经反向开票，走自然人税务代开），不能复用本流程。
- 出售者侧不安装任何东西，因此不能设计依赖客户端推送的交互；状态回传只能靠短信或工行页面跳转。
- 补充（见 ADR 0011）：自然人不能用浏览器直接打开工行 H5，因此「在工行页面上确认」是由**平台自建的 uni-app 客户端（微信小程序 / H5）承载**，页面本身仍来自工行；自然人同样不需要安装独立 App 或关注公众号。

**补充（#81，2026-09-21）：本条否决的是「让本人补录业务数据」，不是「本人自己拍证件」**

「零录入」的本意是**责任归属**——品类、重量、价格、结算方式这些业务字段只有回收企业雇员能录。它不约束**采集形式**：本人在现场、收货员在旁、拍的是他自己的身份证与银行卡，这与「把录入成本转嫁给最没有动力配合的一方」不是一回事。

因此自然人建档向导有两种壳，同一套向导、同一份档案：

- **代录（默认）**：收货员在现场端完成身份证正反面与银行卡的拍摄与识别结果确认。**实名与电子签署仍只能由本人在自己手机上完成**，现场只负责把一次性链接交给他（二维码 / 短信）。
- **自填**：收货员把同一枚免注册一次性链接交给本人，由他在自己手机上完成拍摄、确认与实名。

两条路写入的字段、后端接口完全一致。**业务数据仍然只有收货员能录**，本条不松口（见 ADR 0036、0037）。
