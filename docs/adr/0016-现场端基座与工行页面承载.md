# 现场端基座：新建最小 uni-app，工行 UI 页面走新窗口承载

**状态**：已定（#22）

**背景**

ADR 0011 定了收货员现场端用 uni-app、一期发 H5，但没有定基座来源，也没有定工行「UI 页面接口」返回的自动提交表单在 H5 里怎么承载。仓库里 `backend/yudao-ui/` 下的 `yudao-ui-admin-uniapp`、`yudao-ui-mall-uniapp` 都只有一份 README，没有可跑的工程。

**决策**

1. **基座**：新建最小 uni-app（vue3 + vite + TS + pinia），目录 `backend/yudao-ui/yudao-ui-field-uniapp/`。不裁剪官方 mall / admin-uniapp——它们带大量与现场收货无关的页面与导航模型，裁剪成本高于重建；现场端只有「收购登记 / 出售者建档 / 我的收购单」三块。
2. **工行 UI 页面承载**：实人认证、收方入驻等自动提交表单由后端下发（ADR 0009），H5 下用**新窗口 / 新标签**打开，前端不拼工行 URL。不用 iframe——工行页面可能 `X-Frame-Options` 拒绝，且表单自提交容易被容器拦截。跳回后由后端数据接口收敛状态（ADR 0011）。`web-view` 承载留到小程序渠道。
3. **身份证带档**：一期只做「手输身份证号或手机号 + `/icbc/seller-onboarding/returning-customer`」。H5 没有 NFC / 原生扫码，「扫身份证」不在一期承诺内，待小程序 / App 渠道再补。
4. **弱网暂存**：H5 用 IndexedDB 存照片 blob、localStorage 存草稿（对应 #7 的离线补传）；实测不达标则升级小程序 / App——同一套 uni-app 代码发不同渠道。
5. **请求与租户**：走 `/admin-api/**`，请求头 `tenant-id` + 收货员 token（`recycling_receiver` 角色），与 PC 后台同一套 yudao 鉴权；不新建鉴权体系。

**Consequences**

- 现场端与 PC 后台是两套独立前端工程，各自构建；共享的只有后端 API 与权限模型。
- H5 的能力上限（相机、离线存储、无 NFC）就是一期边界；升级小程序 / App 时同一套代码换渠道发布。
- 工行 H5 的域名白名单只影响小程序渠道，不影响一期 H5。

**未决 / 触发重议**

- 工行若要求动态活体（仅 App 渠道），现场端不受影响，自然人端（#19）需重议（ADR 0011 已记）。
- H5 离线实测不达标时，现场端提前升级小程序。
