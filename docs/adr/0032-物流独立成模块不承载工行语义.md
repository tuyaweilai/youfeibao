# 物流独立成模块，不承载工行语义

**状态**：已定（2026-09-20）

`yudao-module-icbc` 是工行相关业务（反向开票、付款、发票、主体准入）的落点。车队与运输是**回收企业自己的经营作业**，不管有没有工行都能独立存在；把它塞进 icbc 会让模块职责随工行适配一起漂移。仓库里另有一份随 `tuya-saas-java` 快照并进来的 `yudao-module-logistics`（94 个文件、6 个域、含整套设计文档与建表 SQL、已编进 `yudao-server`），但它的口径与本项目多处冲突。

**决策**

1. **物流建独立模块**（车辆、司机、承运商与承运合同、运输任务与节点、运费对账），按本项目的口径重写；**不在 icbc 内临时落代码再择机剥离**——剥离成本随代码量单调增长，而模块现在还是空的，搬一次最便宜。
2. **依赖方向**：物流**不**编译依赖 icbc，只在单据上存 icbc 侧的编号（场站、交接批次、采购订单）。追溯方向反过来：`icbc` 经物流的查询接口把运输节点与凭证拉进一票一档。
3. **不使用那份 vendored 的 logistics**：它是「危废订单 + 物流公司 + 过磅推送 + 现金代付」口径，`waste_code` / `waste_name` 自由文本与 ADR 0028（品类权威是 `goods_config_id`）冲突，`TemporaryOrder`（司机现场现金收购、可转正式订单）与 `CashAdvance`（司机现金代付）的现金支付与 ADR 0006（不垫资、不代收代付）、ADR 0010（货款只走公对私到出售者本人卡）冲突。
4. **`yudao-module-waste` 与 vendored 的 `yudao-module-logistics` 一并从 pom 停编、代码留库**。`waste` 含竞价报价撮合，与 ADR 0004 冲突，且已经造成过两次 bean 名冲突（`AppointmentServiceImpl`、`appointmentMapper`）。
5. **一任务即一次执行**：运输任务 = 一车 + 一司机 + 一次执行（含若干停靠点），一期**不建独立的「车次」实体**；「一个任务派多车」到二期再做。
6. **轨迹一期只有上报时的一次性定位快照**。演示用的模拟轨迹必须可识别来源（标记为模拟）且**不进一票一档**——税总 5 号公告第十七条把「运输发票或凭证」列为业务真实性材料，在证据链里放一条假路径违反 ADR 0021「只讲可核验的事」。也不把两个点的连线当作真实路径。
7. **司机与车牌在交接批次上引用 + 快照并存**（存 id 同时留姓名/车牌文本）：引用让「这台车跑了多少趟」算得出来，快照让一票一档不被档案改名或删档污染。

**Considered Options**

- **建在 icbc 内，日后剥离**。否决：现在搬零成本，将来搬要动追溯、菜单、权限与既有单据；而且「临时」这件事一旦没有判据就永远不会还。
- **直接复用 vendored 的 logistics 与它的建表脚本**。否决：口径冲突见上，等于把已定的 ADR 反过来。
- **一期就建独立「车次」**。否决：在没有「一任务派多车」的真实场景前，车次只会让每个查询多绕一层。

**Consequences**

- PC 后台新增一级**「物流管理」**；司机角色**不进 PC 菜单**，只有司机端。
- 司机端是**独立 uni-app 工程**（不是收货员现场端的角色分支）：它是高频、长流程、弱网的现场作业，与收货员端的建档/登记几乎无共享页面；共享的只有基建与「自然人准入四步」页面能力，抽成共享包。
- `backend/doc/logistics/` 那份设计文档与建表 SQL 降级为**历史参考**，不是实施依据。
- 停编 `waste` / `logistics` 之后，icbc 侧为绕开 bean 名冲突而做的改名（`icbcAppointmentServiceImpl`、`icbcAppointmentMapper`、`icbcPurchaseContractMapper`）**保留**：改名本身是对的，不该在依赖变化时回退。
