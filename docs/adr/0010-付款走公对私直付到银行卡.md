# 付款走公对私结算直付到出售者银行卡，不做电子钱包、不做资金清分

工行付款指令上送 `payChannel=05 公对私结算`，货款从回收企业的对公账户直接结算到**出售者本人银行卡**。平台**不使用工行电子钱包**，也**不依赖智慧清分**。出售者首次建档只做：实名认证 → 绑定银行卡 → 收方入驻 → 签署框架收购协议与首次授权。

**Considered Options**

- **走智慧清分、给出售者开电子钱包**。未采纳：电子钱包是工行「收方入驻页面」（`edpopenacct`）随附的开户动作，只在资金清分链路上才有意义；本项目付款是公对私直接结算到银行卡，钱包既非必需，也给自然人侧平白多加一次开户。工行侧 `payChannel=05` 就是公对私结算。
- **公对私结算直付到银行卡**。采纳。

**Consequences**

- 出售者入网（#6）不出现「钱包开户」这一步。工行接口返回的 `openacctStatus`（开户状态）与 `mediumId`（电子账户账号）**按接口原样接收、原样透传**，只作为「工行侧账户登记状态」这一不透明字段，**不解释为钱包**，也不围绕它设计业务步骤。
- 付款（#9）：平台代回收企业发起「开票付方支付接口」，货款从回收企业对公账户直接到出售者本人银行卡，回单归档为资金流证据。平台不落地资金，与 ADR 0006 一致。
- 领域语言里不再使用「电子钱包」。`智慧清分` 保留为**未采用**的备选能力，仅在引用工行文档时出现。
- 实名认证（实人认证 H5，`authScene=01`）与钱包无关：它只锚定 `outUserId` 的真实身份。
- 待工行书面确认的仍有一件：`payChannel=05` 公对私结算的合规边界（见技术/业务问卷）。**但它不再影响我们的收款模型**——无论清分是否可用，我们都走公对私直付。
