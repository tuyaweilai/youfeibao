# 结算确认完成后自动预下单，工行自然人确认页面在同一次会话里交给本人

**状态**：已定（2026-09-22）

现在结算确认（`POST /app-api/icbc/seller/settlement/confirm`）只写结算单，一个工行接口都不调；预下单由开票员在 PC 上手点，而预下单返回的那段「自然人确认页面」HTML 只有开票员打得开（`views/icbc/invoiceApplication/index.vue` 的「打开自然人确认页面」）。可这一步按法定义务必须由出售者**本人**做——开票员拿到页面不等于本人确认。同时结算确认与预下单之间被人为隔了两次点击，谁都不知道「确认完了之后呢」。

**决策**

1. 结算确认成功后**自动发起预下单**，并把工行返回的确认页面**在同一次会话里接着打开**：自然人一次点开链接，先确认计量与计价事实（结算确认），再确认开票信息（工行页面），中间不换入口、不换人。
2. 预下单仍受全部门禁约束（三层资质、出售者就绪、额度、结算确认、品类编码、收购单要件）。任何一项不过就停在原地，把原因与补齐方式回给自然人 / 收货员，不静默吞掉。
3. 开票员保留「发起开票申请」入口作为**兜底**（异常重发、线下签字确认后补发起），但不再是主路径。
4. 工行预下单是 UI 表单接口（沙箱不支持），自动发起后页面必须落到浏览器里打开；承载方式沿用 ADR 0016。

**Considered Options**

- **(a) 保持开票员人工发起，只补一条「把确认页面转达给自然人」的通道**。否决：等于把一项法定义务的落点留在开票员手上——他打开页面就跳过了本人确认。
- **(c) 预下单仍人工、但增加授权转达**。否决：多一次人手传递，而这一次点击不含任何业务判断。

**Consequences**

- 结算确认这个端点的语义从「只写结算单」变成「写结算单 + 出站调工行」，因此需要**幂等**（同一结算单版本只发一次预下单，重复确认不重复下单）与**失败不连坐**（预下单失败不能让已经落库的结算确认回滚）。
- 自然人侧要能渲染工行下发的表单：小程序 `web-view` / H5 新窗口已有承载，但确认与开票两次跳转要在同一条会话里接上，令牌用途需要相应扩展。
- 现场端「复制确认链接」转达就不再只是「让他确认一下」，而是一次走到底的入口；文案要跟着改。
