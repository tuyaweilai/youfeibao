# 收购现场识别单列一个端口，不混进 IcbcGateway

收购登记要「拍磅单照片由系统识别回填毛重/皮重/净重与车牌，识别结果可人工修正」（#7）。识别能力来自第三方 OCR / 车牌识别服务，与工行的银税通道是两回事。

**决策**

- 新增出站端口 `AcquisitionRecognitionPort`（`service/acquisition/recognition`），只覆盖两件事：识别磅单、识别车牌。默认实现 `StubAcquisitionRecognition` 不触网、返回空结果。
- 业务层只依赖端口；接入真实服务时替换 Bean，业务代码不动。
- **不**把它塞进 `IcbcGateway`：后者是「平台对工行的唯一出站端口」（ADR 0009），塞进去会让「工行」这条变更隔离带混入非工行依赖，破坏那条 ADR 的单一职责。ADR 0009 的「一条缝」限定的是**工行**侧，不排斥其他外部系统的独立端口。
- 识别是**可失败**的：端口返回空结果时，收购登记照常进行，由收货员手工补录，不阻断现场作业。

**Considered Options**

- **并入 `IcbcGateway`**：否决。工行适配层的签名、加解密、幂等重试逻辑与 OCR 无关；合并后换 OCR 供应商要动工行封装。
- **识别放现场端（uni-app）本地做**：一期可行，但识别口径不可控、结果无法留痕在平台侧，且「系统识别」的验收会落空。端口化后现场端与后端都可用（后端识别填补空缺），保留升级空间。
- **单列端口、默认空实现**：采纳。

**Consequences**

- 测试可以用 mock 端口断言「识别结果只在空缺处回填、人工值优先」，不触网。
- 一期没有真实 OCR 供应商，默认实现返回空，磅单与车牌需手工录入；接入供应商是独立的后续工作，不改业务层。
- 车牌比对（磅单车牌 vs 车辆照片车牌）留在业务层，与识别来源无关：任一侧缺失时结论是「无法比对」，与「比对不一致」区分开。

## 修订（#112，2026-09-22）：入参改收图片字节，识别搬到拍照那一刻

四条更正。「单列端口」「失败不阻断」「人工值优先」三条不变；「默认空实现」的含义变了。

1. **入参从 `imageUrl` 改成 base64**，两个方法都是。原表述假定「识别服务能按地址取到那张照片」，而照片存在本机文件服务里（`infra_file_config.domain` 开发环境是 `127.0.0.1:48080`），厂商必然下载不到；要按地址回填就得后端先按客户端给的地址出站回取字节，那等于白开一个 SSRF 面。识别只该依赖「手里有没有这张图」——现场弱网下照片上传失败是常事，而那正是最需要识别的场景。口径与 ADR 0037 的 `CardRecognitionPort` 一致（理由不同：那边是「影像不留存所以没有 URL」，这边是「识别不该依赖图片存在哪儿」）。
2. **「默认实现 `StubAcquisitionRecognition` 返回空」改成「一枚常驻实现按运行期配置判定供应商」**：照 ADR 0037 的 `TencentCardRecognition` 先例，`provider=stub` 或密钥未配置时它自己返回空结果、不触网。多一枚 stub Bean 会让按类型注入直接炸，`AcquisitionRecognitionPortResidentBeanTest` 钉住只有一枚常驻 Bean。
3. **提交路径上的静默回填（`AcquisitionServiceImpl.fillByRecognition`）删掉**：识别改成现场端**拍照那一刻**调（`POST /icbc/acquisition/recognition/plate`，权限复用 `icbc:acquisition:create`）。图片字节只在现场端手上，提交路径上没有它；而且只有当场回显，识别结果才有被核对的机会——原实现把结果直接写进单据，收货员从来看不到。
4. **「人工值优先」的落点从服务端移到现场端**：现场端在「框里已有车牌、且不等于上一次识别回填的值」时不调识别。这条仍是两端共用的一句话，只是执行点在谁手里看得见那个输入框，就落在谁手里。

一期落地的供应商是腾讯云 OCR 的 `LicensePlateOCR`，与卡证识别共用一份平台配置（见 ADR 0037 的更正）。**磅单字段识别仍未接**（腾讯没有磅单专用产品，要定模板做结构化抽取），`recognizeWeightTicket` 保留为端口方法。

## 修订（#113，2026-09-22）：磅单字段识别接入，解析口径落在平台侧

`recognizeWeightTicket` 从空实现变成真的：**通用印刷体识别（`GeneralBasicOCR`）+ 平台侧的解析规则**（`TencentWeightTicketParser`）。四条决策与一条实测否掉的方案：

1. **不采用厂商的结构化抽取**。同一产品下的 `SmartStructuralOCR` 支持调用时传 `ItemNames`、直接返回 `Name/Value`，看着最省事，但 2026-09-22 用真实磅单（`参考/过磅模版.jpg`）实测：它把**车号与总重丢了**、把净重读成单位「Kg」、把 `19130` 挂到了「备注」上。而通用印刷体把这 33 行连坐标读得干干净净，解析后 `32220 − 13090 = 19130` 与单子上的净重完全自洽。**误配比人工慢更糟**，所以这个方案否掉；证据留在票 #113 与解析器测试里，免得半年后再被提一遍。
2. **解析必须是平台侧的纯函数**。通用印刷体只给「文字行 + 坐标」，把它变成字段这一步只能是我们自己的代码；而磅单格式因磅房而异（这张单子上「毛重」印的是「总重 GROSS」），关键词与坐标口径要能拿真实磅单当测试用例反复迭代。规则与厂商解耦：换识别接口不影响规则。
3. **不做单位换算**。磅单上印 `Kg`，回填的就是磅单上的数字本身——平台对重量没有单位概念（`结算重量 × 单价 = 金额` 是裸乘）。照抄才与收货员手输的口径一致；同一张单「识别填的」与「手填的」不是同一个数是最难查的错。磅单上的「扣率 DISCOUNT %」是百分数，按 ADR 0019 的 `RATIO` 口径换成 0~1 的比例。
4. **读不出来就留空，绝不猜**：净重以磅单印的为准（不被「毛−皮」覆盖），三个重量不自洽时照填 + 告警；车号可能只读到一部分（真实样本 `05648`），提示「可能只读到一部分」，但**不放宽 `plateMatched` 的三态语义**——比对结论是证据链的一环，放宽会造出假的「一致」。原始文字行一并回给现场端核对，且**不落库**（照本文件与 ADR 0037 的「识别完即弃」）。
