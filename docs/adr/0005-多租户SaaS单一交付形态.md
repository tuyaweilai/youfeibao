# 一期只提供多租户 SaaS，不做按回收企业私有化部署

平台以单实例多租户形态交付，回收企业注册即可使用。不给单个回收企业做私有化部署。

**Considered Options**

- **按企业私有化部署**。未采纳：每家回收企业会成为各自独立的接入实体，要各自与工行签约、各自开立子商户档案、各自走一遍准入——平台作为「合作方」的规模价值随之消失。
- **多租户 SaaS**。采纳。

**Consequences**

- 每个回收企业是独立租户，各自拥有独立的主体资质、票种（简易计税仅普票 / 一般计税可开专票）、发票额度、纳税信用等级，全部分开建模与校验。
- 工行侧对应关系：一家回收企业一个**子商户档案**（`archiveType=01`），平台持有 `appId`。
- 竞品开灵科技对外提供「私有化独立部署」，那是因为它不持有开票接入角色；本项目不适用同一个选择。
- 为地方政府或园区做专有部署是另一件事，不在此决策范围内，后续另议。

---

> **边界（2026-09-21 补）**：多租户的前提是「**一家公司只能是一个租户**」——不会出现同一家公司开多个租户。因此付方档案（开票主体）的**统一社会信用代码与纳税人识别号是全局唯一**的：一家公司在平台上只可能有一份付方档案，它在第二个租户下建不出来。
>
> 付方档案的四个唯一键（`payer_no` / `partner_payer_id` / `credit_code` / `tax_no`）**保持全局，不按 `tenant_id` 放宽**——这正是上面「一家回收企业一个子商户档案」的必然结果。`credit_code` / `tax_no` 撞上唯一键时给**可读错误**（不是裸 500），且文案**不点名是哪一家企业**：跨租户只暴露「这个信用代码 / 税号被占用了」这一条业务事实，不泄露别家企业的存在与身份；要处理只能走平台运营。
>
> **软删的后果（2026-09-21 补，#100 修票）**：`uk_credit_code` / `uk_tax_no` **不含 `deleted`**（生产建表脚本 `backend/sql/mysql/icbc_payer_info.sql`），所以软删一条付方档案会**永久占住**那个信用代码 / 税号。服务层预检按「唯一键实际覆盖的集合」判重（含软删行，见 `PayerInfoMapper#selectByCreditCodeIncludeDeleted`），命中软删行给的是「该统一社会信用代码曾在本平台登记过付方且已删除，如需恢复请联系平台运营」，与「已被另一家企业登记」区分开。要允许「删掉再登记」，得给这两个键加上 `deleted`——那是另一个决定，不在 #100。
