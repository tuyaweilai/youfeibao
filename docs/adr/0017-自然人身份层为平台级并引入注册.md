# 自然人身份层升为平台级，并首次引入注册

**状态**：已定（2026-09-19）

自然人出售者是**跨回收企业的同一个人**，但现实现把身份切碎了：`PayeeInfoServiceImpl` 为每条收方档案随机生成 `partnerPayeeId`，并只在本租户内校验身份证/手机号唯一，而这个值就是工行的 `outUserId`（实人认证、收方入驻、预下单都传它）。于是同一个人在两家回收企业卖货 = 两个自然人身份、两次实名、两次收方入驻，交易历史与 500 万额度也无从归属。同时 ADR 0011 明确「不为自然人建账号」，导致他连自己的历史都查不了。

**决策**

1. **引入平台级「自然人主体」**：新增非租户表（登记进 `yudao.tenant.ignore-tables`），以身份证件号码为唯一锚点，持有唯一的平台级外部用户编号（工行 `outUserId`）；各租户的收方档案（`icbc_payee_info`）挂靠到它下面。
2. **引入注册，但只承载两件事**：登录凭证与自助查看（历史交易、收款记录、发票与税费）。登录凭证复用 `yudao-module-member`（手机号 + 短信验证码；微信登录后补为绑定项），**身份锚点自建**——登录凭证会换、会注销，身份不能因此漂移。
3. **注册不设入口墙**：扫码进来先看匿名摘要，只在「确认结算 / 有异议」这一步要求手机号验证，验证即建档。既有的短期单用途令牌路径（`PublicTokenPurposeEnum` 五类）**全部保留**，定义为「免登录只读 / 单次」，注册不能成为任何既有通道的门槛。

**Considered Options**

- **维持每租户一份自然人档案**。否决：同一人 N 个身份、N 次实名，且额度与历史无法归属；这是现状的既存缺陷，不是取舍。
- **把自然人建成各租户的 `member_user`**。否决：`member_user` 是租户内的会员语义（积分/等级/商城），跨企业身份锚点塞进去会被两个模型撕开。
- **只做平台级主体、不做注册**。否决（用户决定）：他无法自助查看历史与凭证，这件事只能靠回收企业代查。
- **扫码即注册墙**。否决：他的动机是「这一车货要结钱」，不是「我想注册」；入口墙会砍掉大部分扫码的人，而农村专业散户的转化率最脆弱。
- **注册时采集姓名 + 身份证号**。否决：这两个字段首次卖货时反正要采（建档、报税），放在注册时采就是把同一次工作做两遍——正是本次升级要消灭的重复填写。

**Consequences**

- 工行侧的 `outUserId` 从「每条收方档案一个」改为「每个自然人主体一个」。**但受一条未决事实制约**：`IcbcSdkGateway.submitPayeeOnboarding` 传的子商户是全局配置 `icbc.out-vendor-id`，而预下单/付款传的是租户付方档案的 `partnerPayerId`；工行口径是「子商户 = 回收企业，子商户档案之间互相看不到数据」。因此落地形态有两种可能，**需向工行书面确认**：收方与实人认证若为平台级，则「一次实人认证 + 一次收方入驻」；若收方必须按子商户隔离，则「一次实人认证 + 每企业一次收方入驻」。无论哪种，平台级自然人主体都是必需的。
- 与 ADR 0011「不为自然人建账号」冲突的部分，以本决策为准。ADR 0007「采集责任归回收企业」**不变**——注册只解决身份与查看，不采集任何业务数据。
- 跨租户读取只发生在此处（与额度台账同一模式：`TenantUtils.executeIgnore`），且只对自然人本人开放；回收企业侧不可见，与工行子商户隔离保持一致。唯一例外是销售额额度的「已用 / 余量」，因法定义务必须跨企业合并。
- 「注册量」不是本决策的目标，不引入任何拉新机制（邀请有奖、积分、分享裂变）。
- 一期只做 H5 短信验证码登录，不等待微信小程序上线；小程序 `appid` 仍为空，注册、备案与业务域名白名单是独立的交付前置。
- **数据归属拆分**：**实人认证结果归自然人主体**（跨企业复用），**收方入驻状态归收方档案**（收方入驻是与子商户绑定的动作）。这是唯一现在就必须改的归属。
- **收方入驻的子商户不一致要先修**：`submitPayeeOnboarding` / `queryPayeeOnboarding` 当前传全局配置 `icbc.out-vendor-id`，而预下单/付款传租户付方档案的 `partnerPayerId`；应先统一为后者——无论工行对子商户隔离的答复是哪一种，这一步都是对的。
- **实人认证没有电子替代**：工行的活体核验是 `outUserId` 锚定的唯一方式，产品上**不提供第二种电子验证**（拿三要素或银行卡四要素充数只会让企业在工行侧被拒）。替代路径是**转人工**：反复失败 → 留联系方式（`CONTACT_LEAD`）→ 企业侧线下跟进。
- **硬边界**：没有实人认证 ⇒ **既不能反向开票，也不能走平台付款**（付款要求收方入驻，收方入驻前置就是实人认证）。也就是说这笔生意不属于平台流程，而不是「稍后重试」；文案必须说清楚「这一步由银行完成、我们无法替代」。
- **注册的时机与免登录边界**：注册发生在「确认结算 / 有异议」这一步，不做入口墙；扫码进入后的首屏只有公开信息（回收企业、场站、地址），不含任何个人数据。
- **注销只杀登录凭证，不杀身份与交易**：注销/解绑的对象是**登录凭证**（手机号、微信），**自然人主体与交易记录永久保留**（交易记录是税务凭证，追溯期远长于任何账号的生命周期）。产品文案必须直说「**注销账号不等于删除交易记录**」。
- **同一身份证已有主体时不覆盖、不自动合并**：身份登记发现该身份证已建档且绑着不同手机号，只提示「该身份已建档，请用原手机号登录或联系客服」；**自动合并等于让任何人接管他人的身份与收款**。他本人忘了手机号是常态，所以必须有出口：**平台运营侧的「身份认领与解绑」人工处理**（复用跨租户视角，人工核实）——自动化流程只负责拒绝，不负责裁决。
