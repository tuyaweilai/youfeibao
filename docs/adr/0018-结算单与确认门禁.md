# 结算单：一次到场批次一次确认，未确认不得发起开票

**状态**：已定（2026-09-19）— 「允许分批开票付款」一条于 2026-09-22 被 [ADR 0038](./0038-收购进度由开票单四条状态线派生.md) 取代（一期一张收购单只对应一张票、一笔付款；其余决策不变）

现状是一品类一张收购单（`icbc_acquisition` 只有单个 `goodsConfigId`），一车混合废料就是两三张单，自然人要被要求确认两三次；而开票员在现场登记完成后就能发起预下单，自然人的认可只发生在**工行页面上那一步**（`confirmStatus`）。反向开票的证据链要求「出售者对计量与计价事实的认可」**在不可逆动作（付款、票上传税局）之前**成立——事后只能红冲，成本已在 #14 见过。

**决策**

1. 新增 **结算单**（`icbc_settlement`），按「一次到场批次」聚合同一出售者、同一场站的若干张收购单。**确认与异议都发生在结算单上**；付款与开票仍按收购单逐笔进行（工行一票一付）。
2. 结算单确认是**开票申请（预下单）的硬前置**：pre-check 新增一项，与 `SELLER_QUOTA` 并列，未确认不下发工行预下单。
3. **结算单由收货员显式生成**：登记完最后一张收购单后点「结束本次收货」；系统的时间窗（同一出售者 + 同一场站 + 同一班次，默认 4 小时可配）只能用来**建议**把哪几张并在一个结算单里，**不自动合并**。现场动作是唯一可信的批次边界。
4. **生成后不得再往结算单里加收购单**（否则会出现「确认完又冒出一张」），要加只能新建结算单；离线场景现场端在本地用同一个 `batchKey` 标记同一批，补传后由服务端按 `batchKey` 归入同一结算单（复用现有 `client_request_id` 幂等模式）。
5. 保留**留痕逃生门**：自然人长期不确认时，企业上传带签字的纸质确认书并标注办理人，等价于确认。
6. 确认锁定的是**计量与计价事实**（结算重量、单价、调整项）。确认之后对已确认事实的任何修改都产生**新版本并重新确认**，前后版本都留痕；**已开票后不得修改，只能红冲**。异议的表达方式见 ADR 0022。

**Considered Options**

- **不做聚合、一单一确认**。否决：混合品类场景下确认次数本身就是劝退点。
- **确认只做记录、不做门禁**。否决：不可逆动作已经在确认之前发生，确认就失去意义。
- **超时自动替自然人确认**。否决：等于替自然人做出认可，一旦出争议无法向稽查解释。宁可让企业侧承担催办成本。

**Consequences**

- 结算单与收购单是**多对一**；一张收购单只属于一个结算单，改挂需留痕。
- 结算确认记录（含线下签字件）作为**合同流**的签署证据附件进一票一档，**不新增第六流**——五流由税总 5 号公告第十七条定义。
- **允许分批开票付款**：确认表达的是对事实的认可，不是对付款节奏的承诺。长期不开票的收购单需要**作废**，作废必须留原因，且对自然人可见（货已经收了，作废是敏感动作）。
- 异议不是拒收/退货：拒收发生在货物流层面（现场就不收），不进平台流程。
