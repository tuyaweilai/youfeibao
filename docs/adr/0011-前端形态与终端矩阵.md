# 前端形态与终端矩阵：后台 PC、现场 uni-app H5、自然人零自建

平台有五个使用面：回收企业的管理员 / 开票员 / 财务、现场收货员、平台运营、自然人出售者。本决策定它们各自的形态，以及页面入口怎么到自然人手上。

**决策**

- **回收企业后台（管理员 / 开票员 / 财务）与平台运营**：PC Web，基于 yudao 官方管理后台（`yudao-ui-admin-vue3`）在本仓库自持一套。
- **收货员现场端**：手机 / 平板，用 **uni-app 一套代码**，一期只发 **H5**（浏览器打开，「添加到主屏幕」即可用）；微信小程序 / App 是同一套代码的后续渠道，本期不做。
- **自然人出售者**：**不自建面向自然人的任何客户端**——无 App、无独立小程序、无公众号。其全部交互发生在**工行 H5 页面**；平台只负责下发入口、收敛状态、交付发票。
- **前端代码并入本仓库自持**（沿用 ADR 0008），放在 `backend/yudao-ui/` 下，替换现有只含 README 的占位。

**背景**

- ADR 0007：收购数据录入归收货员；自然人只做「在工行页面上确认」一次动作，不装 App、不填单；状态回传只能靠短信或工行页面跳转。
- 税总规范（见 `docs/research/`）：**不得以提供涉税服务为由要求交易对象下载 App 或关注公众号**；个人受票优先**二维码下载、免费打印**，不得只给邮件。
- ADR 0009：预下单、付方支付、收方入驻、企业授权、实人认证都是**工行托管的 UI 页面**，平台只生成表单 / URL。
- ADR 0010：付款走公对私直付到银行卡，自然人侧没有电子钱包要开。

所以「自然人的前端」主要是工行的事；平台自建的部分很薄，且集中在**入口下发**与**发票 / 状态交付**两件事上。

**Considered Options**

- **给自然人自建微信小程序 / App / 公众号**：否决。与「不得强制下载 App 或关注公众号」直接冲突，且 ADR 0007 已定零录入；工行 H5 已覆盖实名、开票确认、收款。
- **只做一套 vue3 PC 后台，现场也用**：否决。现场要摄像头、扫码、弱网暂存，PC 后台在手机上的体验与能力都不够。
- **现场端用 uni-app，一套代码覆盖 H5 / 小程序 / App**：采纳。
- **自然人零自建，走工行 H5 + 二维码 / 短信**：采纳。

**Consequences**

终端矩阵：

| 角色 | 设备 | 形态 | 页面来源 |
|---|---|---|---|
| 管理员 / 开票员 / 财务 | PC | vue3 后台 | 本仓库自持 |
| 平台运营 | PC | vue3 后台（跨租户） | 本仓库自持 |
| 收货员 | 手机 / 平板 | uni-app，一期 H5 | 本仓库自持 |
| 自然人出售者 | 手机 | 工行 H5 | 工行托管 |

- **入口由后端下发，前端不拼工行 URL**：
  - 首次建档（#6）：收货员在自己的手机上打开实人认证 / 收方入驻工行 H5，**同屏递给出售者**本人完成人脸与短信验证。
  - 开票确认（#8）：开票员发起预下单取得工行自然人确认页面，生成**二维码**（出售者扫）或同屏递交；**短信短链**兜底。
  - 发票交付（#11）：工行只回 PDF。平台提供**带短期签名令牌的公开下载页 + 二维码**，可打印；不强制邮件或公众号。
- **后端契约（现在就要按此设计）**：需要一组**公开、免登录、带短期单用途令牌**的端点（发票 PDF、失败留联系方式、额度查询），登记进 `yudao.tenant.ignore-urls` 与安全白名单；令牌必须能解析出租户与业务单，**不能依赖 `tenant-id` 请求头**。令牌短期、单用途、绑业务单，**不为自然人建账号**。
- **状态回传**：短信或工行页面跳转；不做客户端推送（ADR 0007）。
- 自然人不装任何客户端，因此**任何「等待客户端回传」的设计都不成立**。

**未决 / 触发重议**

- **现场弱网暂存**（#7）：H5 的离线能力有限（IndexedDB 可行但不理想）。若实测废品堆场网络不可用，需把现场端升级到小程序 / App——uni-app 同代码，成本可控。
- **自然人是否最终需要微信小程序**：一期不做。若未来要求，必须先解决「不得强制关注公众号」的合规口径，且只能做成工行 H5 的薄壳。
- 前端是从 yudao 官方仓库 fork 后自持，还是内联进本仓库，另见后续决策。
