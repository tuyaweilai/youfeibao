# 前端形态与终端矩阵：后台 PC、现场与自然人各一套 uni-app

平台有五个使用面：回收企业的管理员 / 开票员 / 财务、现场收货员、平台运营、自然人出售者。本决策定它们各自的形态，以及工行托管的页面怎么进到自然人面前。

**决策**

- **回收企业后台（管理员 / 开票员 / 财务）与平台运营**：PC Web，基于 yudao 官方管理后台（`yudao-ui-admin-vue3`）在本仓库自持一套。
- **收货员现场端**：手机 / 平板，用 **uni-app 一套代码**，一期只发 **H5**（浏览器打开，「添加到主屏幕」即可用）；微信小程序 / App 是同一套代码的后续渠道，本期不做。
- **自然人出售者**：**自建 uni-app 薄前端**——一期 **微信小程序优先、H5 兜底**，只有动态活体被强制要求时才上 App。它承载：
  - 工行托管的**实名认证 / 开票确认 / 收方入驻**页面（在容器内打开，不让自然人面对一个裸的工行链接）；
  - **发票下载、额度查询、留联系方式**。
- **前端代码并入本仓库自持**（沿用 ADR 0008），放在 `backend/yudao-ui/` 下，替换现有只含 README 的占位。

**背景**

- 前提：**自然人不能用浏览器直接打开工行 H5**。所以自然人侧必须由平台自己的客户端承载。
- 但工行的实名认证 / 开票确认 / 收方入驻是 **UI 页面接口**：平台用 `buildPostForm` 生成自动提交表单，由浏览器 / 容器 POST 到工行网关，**不能当 REST 调**（ADR 0009）。因此平台自建的只是**承载容器**，页面本身仍来自工行——这一步没有 REST 替代方案。
- 税总规范（见 `docs/research/`）：**不得以提供涉税服务为由要求交易对象下载 App 或关注公众号**；个人受票优先**二维码下载、免费打印**。微信小程序不属「下载 App」或「关注公众号」，是自然人的合规首选；App 仅在别无选择时使用。
- ADR 0007：数据录入归收货员；自然人只做「确认」一次动作。ADR 0010：无电子钱包，自然人收款即本人银行卡。

**Considered Options**

- **自然人零自建、直接发工行 H5 链接**：否决。自然人不会 / 不能用浏览器直开（本决策前提）。
- **自然人用 App（集成聚富通 SDK 做动态活体）**：不作为一期首选。会撞上「不得强制下载 App」的合规口径，仅在工行要求动态活体且不接受小程序时才启用。
- **自然人用 uni-app（微信小程序优先 + H5 兜底）承载工行页面**：采纳。

**Consequences**

终端矩阵：

| 角色 | 设备 | 形态 | 页面来源 |
|---|---|---|---|
| 管理员 / 开票员 / 财务 | PC | vue3 后台 | 本仓库自持 |
| 平台运营 | PC | vue3 后台（跨租户） | 本仓库自持 |
| 收货员 | 手机 / 平板 | uni-app，一期 H5 | 本仓库自持 |
| 自然人出售者 | 手机 | uni-app，一期微信小程序 | 容器自持，**页面来自工行** |

- **信道**：`trxChannel` 按容器填（`05` 微信小程序、`03` H5、`01`/`02` App）。活体模式必须先与工行确认：**动态活体仅 App 渠道**（需集成聚富通 SDK）；小程序 / 公众号只能用**静态活体或无需活体**。这条直接决定自然人一期是「小程序」还是「必须有 App」。
- **前置技术确认**：微信小程序 `web-view` / 小程序内打开外部页面只能加载**已备案域名**，工行的 H5 域名需进白名单——**必须先与工行确认能否在小程序容器内打开**；不能则退回 H5 兜底或 App。
- **入口仍由后端下发**（自动提交表单 / 链接 / 二维码），前端不拼工行 URL。
- **状态收敛靠数据接口**：自然人确认 / 实名后，工行通过 `jumpUrl` / `failJumpUrl` 跳回我们的容器，平台再调 `开票预查询`、`收方入驻结果查询` 等 REST 接口取状态。
- **发票交付**：工行只回 PDF。平台在自然人小程序内直接下载，或提供**带短期签名令牌的公开下载页 + 二维码**，可打印；不强制邮件或公众号。
- **公开端点**：公开、免登录、带短期单用途令牌的端点（发票 PDF、失败留联系方式、额度查询）登记进 `yudao.tenant.ignore-urls` 与安全白名单；令牌必须能解析出租户与业务单，**不能依赖 `tenant-id` 请求头**，也不为自然人建账号。
- **状态回传**：短信或页面跳转；不做客户端推送（ADR 0007）。

**未决 / 触发重议**

- **活体模式**（动态 / 静态 / 无需）：决定自然人一期是小程序还是必须有 App。需工行答复。
- **工行页面能否在小程序容器内打开**：涉及域名白名单与该页面在容器内的可用性。不能则 H5 兜底——但本决策前提是自然人不用浏览器直开，需验证「微信内置浏览器打开我们的页、再跳工行页」是否可接受。
- **现场弱网暂存**（#7）：H5 的离线能力有限，若实测不行，现场端升级到小程序 / App（uni-app 同代码）。
- **前端自持已定**：PC 管理后台从 `tuyaweilai/tuya-saas-pc-vue3`（`enterprise-relation-type` 分支，commit `0d780bc`）快照并入 `backend/yudao-ui/yudao-ui-admin-vue3/`，由本仓库统一管理（见该目录 `PROVENANCE.md`）。收货员现场端与自然人端仍在选型/待建。

**工行答复（2026-09-19，更新本决策）**

- 实人认证：跳转工行 H5 页面做活体脸部识别，H5 与微信小程序 `web-view` 都可用，**不要求 App**（动态活体 SDK 不是必须）。原「动态活体仅 App」的担忧解除。
- 工行 H5 页面（实人认证 / 开票确认 / 收方入驻）**可在微信小程序 `web-view` 内打开**，自动提交表单能正常 POST 到工行网关。
- 白名单：我方域名 `yiyoubao.baibaitan.com` 已备案、与工行无关；工行页面域名是否需另加小程序业务域名白名单待确认。
- **回跳**：`jumpUrl` / `failJumpUrl` 可定制，但**不支持 scheme**；回跳只能用 https 页面（我们自己的域名），小程序在容器内打开后再由前端路由回具体页面。
- **容器顺序调整**：自然人端一期先 H5、随后补微信小程序，**不做 App**；同时一期不再要求「微信小程序优先」。
- 待确认：`trxChannel` 与容器、活体模式的一致性要求。
