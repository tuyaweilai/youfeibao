# 收购进度由开票单的四条状态线派生，且一期不允许分批开票付款

**状态**：已定（2026-09-22）— 其中「不允许分批」一条取代 ADR 0018 的「允许分批开票付款」

现状是收购单上挂着一个手写的单枚举（`AcquisitionStatusEnum`：已登记 / 待付款 / 已付款 / 已开票 / 已取消），由各处业务代码直接写：登记写「已登记」，预下单返回时 `linkInvoice` 就写「待付款」，付款成功写「已付款」。「已开票」的写入函数没有任何生产代码调用，所以它永远不会出现。于是两处会骗人：自然人还没在工行页面上确认的单子已经显示「待付款」（现场催单会催错对象），票已经开出来的单子还停在「已付款」。

**决策**

1. 收购单上只保留一个**派生**的进度，六档：**已登记**（无开票单）/ **待自然人确认**（有开票单，自然人或预开票未落定）/ **待付款**（预开票成功、付款未成功）/ **已付款**（付款成功、票未开出）/ **已开票**（票已开出）/ **已作废**。判定依据全部来自该笔的开票单（`icbc_invoice_order` 的 `confirmStatus` / `preInvoiceStatus` / `paymentStatus` / `invoiceStatus`）。
2. `icbc_acquisition.status` 退化为**缓存**，只在派生单点写；任何业务代码不得再手写它。判定规则集中在一处（对应 `AcquisitionProgressDeriver` 这样的单点），列表与详情共用。
3. 异常（预开票失败、开票失败、付款失败 / 冲正 / 退汇 / 部分成功、上传失败）以**叠加标注**呈现，**不替换**档位——ADR 0021 要求「已付款」不许把「开票失败」盖住。
4. 新增「**待自然人确认**」一档。把「等对方确认」与「等企业付钱」合成一个「待付款」，现场就分不清该催谁。
5. **一期一张收购单只对应一张票、一笔付款**：`icbc_acquisition.invoice_partner_order_id` 与 `icbc_invoice_order.partner_order_id` 保持唯一。ADR 0018 的「**允许分批开票付款**」一条**作废**——分批会让单枚举进度无法成立，也会让 `linkInvoice` 的幂等失效。

**Considered Options**

- **保留手写的单枚举、把漏掉的那几处补上**。否决：同一个事实在事件发生处和回调处各写一次，必然漂移（「已开票」缺失就是这次的样本）。
- **列表直接列四条状态线**。否决：现场端要回答的是「这一笔卡在哪一步」，四条线是详情页的事；链路与异常都在详情页看全。

**Consequences**

- 「待付款」的判定点从**预下单返回**挪到**预开票成功**，`linkInvoice` 的语义要改。
- 「已开票」必须由开票状态收敛处接上（`InvoiceOrderServiceImpl.applyInvoiceInfo`）。
- **红冲不回退档位**：红票开出后档位仍是「已开票」，红冲以标注呈现（「发票流：已红冲（原因）」）。理由是货款真的付了、蓝票真的开过，退成「待付款」是撑谎；但也不能让「已开票」盖住「这张票已作废」，所以它必须挂在异常标注上。
- **工行侧预开票取消**归入「已作废」，但它与企业主动作废是两件事，所以除了档位还要在异常标注里写明「预开票已取消」——作废不能没有来由（ADR 0018）。注意它的连带后果：`status = 9` 会被入库门禁与各类报表按「作废」对待。
- 现场端与 PC 端的收购单列表、详情页的文案要按六档重写；现在详情页那句「已开票：可在『我的收购单』看到发票号」是空承诺。
- 发票 PDF 的下载入口只在**已开票**时出现（票开出来就有原件，与「已上传税局」是两条线）。
