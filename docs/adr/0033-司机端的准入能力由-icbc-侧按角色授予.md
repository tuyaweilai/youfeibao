# 司机端的自然人准入能力，由 icbc 侧按角色 code 授予

**状态**：已定（2026-09-20）

司机上门收货时现场没有收货员（ADR 0030），他要在司机的手机上完成自然人**准入四步**（实名 / 收方入驻 / 框架协议 / 首次授权）。这四步的接口与权限都是 icbc 的（`/icbc/seller-onboarding/*`、`icbc:seller-onboarding:execute` 等），而**司机的角色定义在物流模块**——ADR 0032 又明确「物流不编译依赖 icbc」。于是「谁来把 icbc 的权限发给司机」没有现成答案。

**决策**

icbc 侧的权限同步（`RecyclingPermissionSyncService`）在同步角色时，**额外把准入所需的那几个 icbc 权限授予 {@code code = logistics_driver} 的角色**（若该角色在该租户还不存在则跳过）。

这是一处**有意的单向字符串耦合**：icbc 只知道一个角色 code，不知道物流模块的任何类型；方向与既有的「icbc 经 `logistics-api` 读运输凭证进一票一档」一致。物流侧**不出现任何 `icbc:*` 权限常量**（ADR 0032 的边界测试会继续守住这一点）。

**Considered Options**

- **logistics 侧写同名字面量**（在 `LogisticsPermission` 里再写一遍 `icbc:seller-onboarding:execute`）。否决：同一个权限串有了两个来源，改名或调整时必漏一边，而漏掉的表现是「司机端某个按钮点不动」——排查成本远高于这一处耦合。
- **司机端不做准入四步**（留给收货员）。否决：那样 ADR 0030 的核心结论落空——司机上门时现场根本没有收货员。
- **让 logistics-api 依赖 icbc-api 去引常量**。否决：直接违反 ADR 0032 的依赖方向，连编译期边界都破了。
- **在 icbc 侧新建一个「现场人员」角色**。否决：司机的角色应当是**一个**（`logistics_driver`），角色一多，权限面就分成两半，管理员在后台看到两个「司机」会无从下手。

**Consequences**

- 角色 code `logistics_driver` 成了 icbc 侧的一个**约定字符串**。改名必须同时改两边；因此它要有测试守着（icbc 侧一条断言：该 code 存在即授予、不存在不报错）。
- 司机因此同时拥有物流域（任务读取与节点上报）与 icbc 域（准入四步）两类权限，但**仍然没有**收购定稿、结算确认、付款与开票——现场不产生金额（ADR 0031），确认一律由出售者本人做（ADR 0030）。
- 将来若有第三个模块也要给司机发权限，照此办理：**由那个模块按角色 code 授予**，不要反过来让物流去依赖它们。
