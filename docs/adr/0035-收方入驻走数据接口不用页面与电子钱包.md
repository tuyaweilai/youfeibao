# 收方入驻走数据接口，废弃页面接口与电子钱包

**状态**：已定（2026-09-21）

ADR 0010 定了付款走公对私直付、不开电子钱包，但当时手上唯一的收方入驻入口是**页面接口**（`edpopenacct/submit`）——它把「收方入驻」与「电子钱包开户」串在一次页面调用里，于是钱包只能"按接口原样接收、原样透传"。工行后来给出同名的**数据接口**（`edpreceive/add`，`businessType=0004`），入驻可独立完成、与钱包无关。因此：**收方入驻改走数据接口，页面接口与整条电子钱包流程一并作废。**

## 决策

1. **入驻发起走数据接口**：`IcbcGateway` 上一个方法直接调用，不再生成任何工行页面表单。入参就是接口文档 `businessType=0004` 一节的必输集（收方户名、收方账号、是否我行用户、手机号、证件、证件签发/截止日期，自然人另需职业与住址）。
2. **实人认证仍是前置**：它仍是页面接口，`outUserId` 由它锚定（ADR 0017）。自然人"人不在场也能自己完成实名"的自助链路保留，但只承载实名，不再承载入驻。
3. **结果两条路**：异步回调为主（只带审核结果），主动查询兜底；查询沿用既有查询接口。
4. **状态机只剩审核一维**：已受理 / 通过 / 拒绝。开户成败这条线删除。
5. **换卡走收方修改接口**（`edpreceive/update`），业务规则一条不改——仍然一卡、仍然审核期间付款挂起。
6. **电子钱包从代码与领域语言里消失**：删掉工行账户标识与开户状态两列，「电子钱包」「电子账户」「开户状态」不再出现。
7. **交易渠道参数 `trxChannel` 随页面接口一起消失**；预下单那个同名字段（另一套字典、且从未真正上送）一并删。

## Considered Options

- **保留页面接口**。否决：页面接口的价值只在钱包开户与影像上传；不用钱包时它只剩 `corpNo`、`camsPublicKey`、预填信息这些额外必输项，以及"自然人做完人脸还要在工行页面上再点一遍"的多余动作。
- **数据接口发起 + 页面接口兜底**。否决：两条路对同一个 `outUserId` 会产生两种入驻形态，状态机与回调解析都要分叉，而页面接口已被明确作废。
- **把收方修改做成入驻方法的一个开关**。否决：另一条接口、另一套必输规则（付方编号非必输、只能改六个字段），合并会把两套规则揉成一个可选字段拼盘——正是这次要从页面接口里拆掉的债。
- **保留状态机里的开户维度**。否决：已经没有产生它的路径了，留着只是一条永远取不到值的分支。

## Consequences

- 端口 `submitPayeeOnboarding` 的返回从「页面表单」变成「受理结果」；假适配层与相关测试从断言 `formHtml` 改为断言**上送了哪些字段**。
- 一次性令牌与公开端点仍在，但只承载实人认证页面；自然人端「变更收款账户」不再需要令牌。
- 数据库去掉两列钱包字段，新增「是否我行用户」与「收方行号」；建表脚本与一份一次性迁移脚本同时更新，迁移不可逆。
- 为页面接口准备的 `corpNo` / `camsPublicKey` / 预填信息（含此前写错的字段名）不再需要。
- **待工行确认**（不改变本决策的形状）：① 实人认证 H5 文档的功能说明写「跳转到电子钱包账户开立页面」，而同一份文档的示例注释写「跳转到收方入驻页面」、配套的《合作方实人认证技术对接指导手册》写「跳转到融e聚实人认证H5页面」——以哪份为准，该页面在不使用电子钱包时能否单独使用；② 该手册另写「实人认证H5仅支持在微信公众号和微信小程序环境中唤起」，若属实，H5 渠道就唤不起实名；③ `businessType=0004` 的数据接口是否要求该付方**开启智慧清分**。
