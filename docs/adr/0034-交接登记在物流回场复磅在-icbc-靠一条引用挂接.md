# 交接登记在物流、回场复磅在 icbc，两侧靠一条引用挂接

**状态**：已定（2026-09-20）

ADR 0031 定了「现场只登记交接、回场复磅才定稿」，但没说这两件事分别落在哪个模块、两侧怎么接上；ADR 0032 又规定物流只存 icbc 侧编号、`logistics-api` 只暴露读取面。V6（#73）落地时必须在三条约束的交点上把接口定下来，否则很容易做成「司机端顺手把工行那层的批次也建了」。

**决策**

1. **现场交接登记落在物流**（`logistics_transport_handover`）：司机在一个停靠点上登记品类（icbc 侧 `goods_config_id` + 名称快照）、参考量、参考单价、凭证照片与要件状态。**它不产生金额、不产生收购单**，也没有任何收购 / 结算字段。
2. **回场复磅落在 icbc**：磅房在派单场站按某一条现场交接登记建**交接批次**（`icbc_handover_batch`）并落第一次磅次；批次把现场参考值、要件状态、司机与车辆（引用 + 快照）搬过来。**场站必填且是派单场站**，实际提货地址存 `visit_address`，再落到收购单的交易地址——不引入虚拟场站（ADR 0031）。
3. **两侧的挂接点只有一个，且是单向引用**：`icbc_handover_batch.logistics_handover_id`。物流**不**回写 icbc 状态（ADR 0032 的读取面约束）；icbc 反查物流的读取面取现场参考、凭证照片与运输节点。方向恒为 icbc → 物流。
4. **幂等落在 icbc 侧**：同一个 `logistics_handover_id` 只会建出一个批次（重复回场复磅返回既有批次）。物流侧的「最近登记的交接」只是**候选队列**，哪些已经复过磅由 icbc 过滤——物流不知道也不该知道这件事。
5. **单价默认取现场参考价**：现场谈好的就是默认成交价。显式改单价或改现场参考量**必须填原因**（`reference_fix_reason`），改动被解释而不是被抹平；参考值原值仍留档。
6. **「待补档」是一条状态，不是一次失败**：缺身份证或银行卡时交接与收购事实照记，`document_status = PENDING` 从交接登记 → 交接批次 → 收购单一路继承；**开票 precheck 与付款入口各拦一道**（付款这道是必要的：预开票可能是补档前就存在的历史单据），补档（`complete-documents`）留办理人与时间。待补档因此**不进开票申请、不进台账口径、不计入额度**。
7. **一车多停靠点各自成立**：每个停靠点各自交接、各自一个批次、各自一张收购单（ADR 0031 / #59 第 4 条）。同一趟任务的两条交接登记之间没有任何合并语义。

**Considered Options**

- **司机端直接建 icbc 交接批次**。否决：那是把工行那层的对象塞进现场登记，司机端会拿到「建批次」这种属于磅房的权限；也让「现场不知道回场复磅结果」这件事在模型上说不通。
- **物流侧回写 `handover_batch_id`（两侧互指）**。否决：违反 ADR 0032「`logistics-api` 只暴露读取面，其它模块不读写物流的表」的对称要求——那一侧同样不该被反向写。单向引用 + icbc 过滤候选，已经能表达全部需要的事实。
- **现场就定稿收购单**（现场量价即结算）。ADR 0031 已否决：随车秤的可核验性远不如场内磅。
- **待补档只拦开票、不拦付款**。否决：付款比开票更不可逆，而 AC 明说「付款与开票门禁拦住」。

**Consequences**

- icbc 编译依赖 `yudao-module-logistics-api`（读取面）；物流仍然不依赖 icbc（ADR 0032 的边界测试继续守）。两侧的判定在 icbc 侧闭环，物流可独立运行。
- 「现场参考量」只是提示：计量永远取有效磅次，数量字段取结算重量兜底。**任何地方都不把参考量当计量事实。**
- 司机端因此多一条只读权限：`icbc:goods-config:query`（交接登记要选权威品类，ADR 0028）。司机权限清单仍是「窄」的——没有收购登记、结算确认、付款、开票（ADR 0030 / 0033 的测试守着）。
- 一票一档的货物流多两类附件：**现场交接凭证**（司机拍的照片）与**运输凭证**（运输节点的照片），都由 icbc 按 `logistics_handover_id` 反查物流读取面取回。自送的货取不到就取不到，不报错也不造假。
