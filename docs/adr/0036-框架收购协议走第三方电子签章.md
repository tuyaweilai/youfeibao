# 框架收购协议走第三方电子签章，结算确认仍不签章

**状态**：已定（2026-09-21）

ADR 0024 否决了 CA / 电子签章，理由是「成本与接入周期不成比例，自然人侧普及率极低」。`#81` 又要为框架收购协议接入第三方电子合同。两个结论同时存在会让后来者困惑，所以在此划清边界：**0024 约束的是结算确认这一处落笔，本 ADR 约束的是框架收购协议**。

**决策**

1. **结算确认不签章**：ADR 0024 原样有效。它高频、当场发生，勾选 + 快照哈希已足够硬，而它是开票的硬前置、可完成性优先。
2. **框架收购协议上第三方电子签章**：一年一份、低频，且它是税总 5 号公告第十七条点名的**合同流证据**，签署形式值得单独投入。目标供应商是腾讯电子签（第三方应用集成）。
3. **两份文书、一个合同组、一次签署**：「反向发票合规告知函」与框架收购协议各自是独立文件，装进同一个**合同组**，签署方拿一个链接、一次实名、把两份一起签完。**同归合同流**，沿用现有证据类型 `FRAMEWORK_AGREEMENT`，不新增证据类型、不新增第六流（守住 ADR 0018）。
4. **不自建 CA / 数字证书 / UKey**：证书体系由第三方平台承载，我们只用它的服务。
5. **章是租户级的**：发起方只能是回收企业（腾讯电子签的接口约束，也与 ADR 0001 一致），回收企业在自己激活电子签时创建企业印章；**平台不代盖**。签署顺序为企业先盖章、自然人后签署。
6. **发起 ≠ 签完**：建档向导走到「签署已发起」即结束，协议状态落**待签署**，签署完成靠回调收敛。沿用现有门禁里的「生效协议」一项，**不新增门禁**。
7. **未开通即降级**：租户未完成电子签激活（无企业主体或印章）时签章不可用，协议落 `PAPER`（`signMethod` 已有该取值），其余流程不变。

**Considered Options**

- **结算确认也上电子签章**：否决。0024 的理由仍成立，且会把硬门禁压在最脆弱的环节上。
- **两份文书拼成一个 PDF**：否决。腾讯「用文件发起」的 `FileIds` 目前只支持单个文件，但更关键的是证据上两份文书要能分别引用；合同组两件事都满足，代价是各扣一份合同额度。
- **平台统一代盖企业章**：否决。腾讯电子签的发起方只能是子客企业（回收企业），而平台不是经营主体（ADR 0001），代盖既走不通也不合法。
- **告知函单独走触达留痕**：备选，不采用。若将来法务坚持「告知函只证明送达、不证明合意」，它应改走触达（ADR 0023），而不是挂进合同流。

**Consequences**

- 新增一条第三方出站依赖，以及一套**租户启用流程**：回收企业在后台点「开通电子签」→ 一次性控制台链接 → 企业认证 + 创建企业印章 → 显示已激活。未激活的租户走 `PAPER`。
- 后台需要两类配置：**平台级**（环境、`AppId`、`SecretId`/`SecretKey`、回调地址与验签、签署链接渠道、平台模板）与**租户级**（子客编号、激活状态、经办人编号、企业印章编号、合同额度）。
- 个人签署链接有有效期（腾讯默认 30 分钟），过期必须重新生成——「发了短信他过几天才点」时不能复用旧链接。
- ADR 0024 末尾补一句边界说明，指向本 ADR。
