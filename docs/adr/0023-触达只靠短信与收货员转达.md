# 自然人的触达只靠短信与收货员转达，不做推送

**状态**：已定（2026-09-19）

ADR 0018 让结算确认变成开票的硬前置，ADR 0017 让注册发生在确认那一步——两者合起来产生一个隐藏依赖：**他必须知道有一单在等他确认**，否则流程卡死在「等他自己想起来」。而当前的事实是：微信小程序 `appid` 为空（订阅消息不可用）；`yudao-module-icbc-biz` 尚未依赖 `yudao-module-system-api`，短信要走 `SmsSendApi` 得先加依赖；`system_sms_channel` / `system_sms_template` 虽在基础 SQL 里，但真实通道需要供应商接入与签名报备（有审核周期与费用）。

**决策**

1. **一期触达只有两条路**：短信（可配置开关），以及**收货员端一键把确认链接转达给他**。
2. 短信**只发三条**：结算单待确认 / 付款异常（失败、退汇、冲正）/ 发票已开出。内容带**一次性令牌链接**（复用 ADR 0017 保留的令牌路径），收短信的人**不需要注册**。
3. **短信开关默认关闭**，由租户或平台决定开不开（费用与到达率是运营成本，不是技术问题）。
4. 微信小程序的**订阅消息**作为后续渠道补充，定位是**绑定项**，不做账号迁移、不做双轨。
5. **不做 App 推送、不做公众号**。

**Considered Options**

- **只做拉取（等他下次打开）**。否决：硬门禁会因此卡死在无提醒状态，而收货员并不总能当场盯住他确认。
- **等小程序订阅消息再触达**。否决：小程序注册与备案有独立周期，不能把确认流程的可运行性押在它上面。

**Consequences**

- 短信只对**已注册或留过手机号**的人有效；首次交易、从未留号的场景只有「收货员当场把链接给他」这一条通路，因此**收货员端的一键转达是必需功能，不是便利功能**。
- ADR 0007「不设计依赖客户端推送的交互」继续有效，本决策只是把它落实到触达层。
- 短信模板内容属于对外口径，与 ADR 0021 一并受同一约束：只说可核验的事。
