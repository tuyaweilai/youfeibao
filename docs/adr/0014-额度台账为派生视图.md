# 出售者额度台账是派生视图，不另建汇总表

自然人出售者的反向开票额度（连续 12 个月滚动、上限 500 万元）必须**在票开出来之前**由平台自己拦住：工行没有事前校验接口，也没有统一的额度视图，跨平台累计更看不到（见 `docs/icbc/工行答复-2026-09-18.md` §四）。本 ADR 记录台账怎么存。

**决策**

- **不新建汇总/台账表**。台账（`NaturalPersonQuotaServiceImpl`）是**派生视图**：每次查询直接从各租户的 `icbc_invoice_order`（蓝票）与 `icbc_red_invoice`（红票）算出来。
- 口径写死在服务里，只有一处：
  - **已开票** = `invoice_status=已开票`，按**开票日期**落在窗口内（无开票日期时退回创建时间）；
  - **在途** = 预开票成功但尚未开票（含开票中）——它同样占额度，否则两笔并发的开票申请会各自认为「还装得下」；
  - **红冲** = 红票上传成功（`redOffsetStatus=07`）**且原蓝票也在窗口内**才扣；蓝票已滚出窗口的不扣（否则凭空多出余量）；
  - **已用额度 = 已开票 + 在途 − 红冲**，与 500 万比较；10 万元免征线只提醒、不拦截（超线是「按时代办申报缴款」，不是「不能开」）。
- **跨租户合并**在 `TenantUtils.executeIgnore` 下按身份证号把同一自然人在本平台各租户的收方档案找齐后汇总。
- 唯一落库的是**引导记录** `icbc_seller_quota_guidance`：超限被拒时留下一条「引导出售者办理经营主体登记」的可跟进、可结案记录（同一出售者同时只有一条未办结记录）。这不是额度缓存，是 workflow 产物。

**Considered Options**

- **物化一张 `icbc_seller_quota_ledger`（出售者 × 月）**：否决。它要在开票、红冲、取消、开票失败等多个状态跃迁点同步，任一处漏更新就永久漂移，而漂移的后果是「该拦的没拦」。派生视图每次重算，慢一点但永远与票据事实一致；量级上窗口内每人的票数是几十行，不是性能问题。
- **只在开票失败后由工行补缴兜底**：否决。工行的补缴是**事后**的，拦不住超额开票，等于把合规风险留给回收企业。
- **把额度算在租户维度**：否决。免征线与 500 万上限都是**自然人**的，按租户算会让同一个人在多租户下重复享受免税额。
- **查询时算 + 引导记录落库**：采纳。

**Consequences**

- 「已用额度」的定义只存在于一个服务里；要改口径（例如把在途排除在外）只改一处，所有入口（收购登记提示、开票申请硬校验、出售者公开查询）同时生效。
- 额度是**软上限**：这是平台自己的台账，不是税务/工行的权威数据；跨平台累计不可见，本平台之外的开票额平台看不到。
- 征收率目前取自品类配置（`icbc_goods_config.tax_rate`），开票时落到 `icbc_invoice_order.tax_rate`，台账据此把销售额按「减按 1%」与「放弃减按 3%」分列。若将来支持**按出售者声明**放弃减按，需要在建档里加字段并在预下单时覆盖品类税率——台账无需改动。
- 撤销的红字确认单不计入扣减（只有上传成功算），与「红票真正开出才算冲销」一致。
