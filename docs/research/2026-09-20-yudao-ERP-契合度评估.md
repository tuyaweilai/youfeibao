# yudao ERP 作为回收企业管理系统骨架的契合度评估

> 研究日期：2026-09-20
> 状态：技术评估（只读代码得出，未改动任何实现）
> 方法：逐文件读 `backend/yudao-module-erp/**` 与 `backend/yudao-module-icbc/**` 的 DO / Service / Controller，对照规划文档的 P0 需求。引用编号 `[E1]`… 对应文末清单。
> 对照基线：`docs/research/2026-09-20-回收企业采购收货入库结算功能规划.md`（M01–M10）、`docs/research/2026-09-20-回收企业业务与物流一体化规划.md`、`CONTEXT.md`、`docs/adr/0003/0004/0010/0018/0019/0021`。

## 0. 一句话结论

**【事实】** `yudao-module-erp` 是一套**完整的"通用贸易型 ERP"**：产品主数据 + 采购（订单/入库/退货）+ 销售（订单/出库/退货）+ 库存（余额/流水/调拨/盘点）+ 财务（收付款/结算账户）+ 两张统计口径。Java 侧 217 个源文件、23 个 Controller、33 个 DO（33 张表）、**前端页面 63 个文件也已经在仓库里**（`views/erp/**`、`api/erp/**`）。

**【推断】** 它接不住的是**回收行业特有的那几层**：场站/库区/库位/批次、毛皮净重与扣杂、磅次与拒收、结算确认与异议、运输与到场作业、可核验的付款与发票。这些恰好是本项目已经自建的 `icbc_*` 域（`icbc_acquisition` / `icbc_settlement` / `icbc_payment_order`）。所以真正的选择不是"用 ERP 替换 icbc"，而是**"ERP 补上我缺的采购履约 + 最小库存台账，其余保持 icbc 为事实源"**。

**【推断】引入成本的主项不是前端，而是**：① 33 张建表 SQL 在本仓库与本地库里都不存在；② ERP 与 icbc 是两套并存的权限体系；③ 库存里没有成本/暂估概念；④ 放开 pom 后系统租户会看到整棵 ERP 菜单（含销售、财务），需要显式收敛。

## 1. ERP 模块与表的实际盘面

### 1.1 域与文件清单 【事实】

### 1.2 建表 SQL 不在仓库，必须补建 33 张表 【事实 + 推断】

**【事实】**
- `grep -c 'CREATE TABLE.*erp_' backend/sql/` = 0；全仓库（含 `docs/`）都搜不到 ERP 建表 `[E2]`。
- 本地库实测：`SHOW TABLES LIKE 'erp%'` 空（连表都没有）`[E26]`。
- `backend/sql/mysql/README.md` 的导入清单里没有任何 `erp_*` 文件 `[E26]`。
- 只有一张**手写 SQL**：`ErpPurchaseStatisticsMapper.xml` / `ErpSaleStatisticsMapper.xml` `[E3]`；其余 Mapper 全是 MyBatis-Plus 的 `LambdaQueryWrapperX`，**没有任何 XML 建表/索引信息**。

**【推断】要补建的表清单与张数 = 33 张**，字段以 §4/§5/§6 逐表列出为准。索引可反推的只有唯一性约束（来自 Mapper 的 `selectByNo` / `selectOne` 用法 `[E3]`）：

| 表 | 可反推的唯一键 | 依据 |
|---|---|---|
| 全部单据主表（purchase/sale/stock in/out/move/check、finance payment/receipt） | `no` | `selectByNo(no)` 后判空 `[E3]` |
| `erp_product_unit` | `name` | `selectOne(getName, name)` `[E3]` |
| `erp_product_category` | `(parentId, name)` | `selectOne(parentId, name)` `[E3]` |
| `erp_stock` | `(productId, warehouseId)` | `selectByProductIdAndWarehouseId` `[E3]` |
| `erp_account` | `defaultStatus=true` 至多一条 | `selectOne(getDefaultStatus, true)` `[E3]` |

**【推断】非唯一索引、字段精度、字符集在代码里无法反推**，必须向 yudao 上游取原版 `erp.sql` 或按上表自拟。**注意**：`ErpPurchaseStatisticsMapper.xml` 手写了 `AND tenant_id = ...` `[E3]`，说明物理表**必须有 `tenant_id` 列**（见 §2）。

### 1.3 菜单种子已在 `ruoyi-vue-pro.sql` 【事实】

**【事实】** `system_menu` 里 ERP 菜单 **140 行**，id **2563–2702 连续无缺**，位于 `ruoyi-vue-pro.sql:1948–2087` `[E4]`。结构：

- 一级目录 **1 个**：`2563 ERP 系统`（`path=/erp`，无权限码）`[E4]`。
- 二级目录 **5 个**：`2564 产品管理`、`2583 库存管理`、`2602 采购管理`、`2617 销售管理`、`2645 财务管理`；外加 `2702 ERP 首页`（`component=erp/home/index.vue`，权限 `erp:statistics:query`）`[E4]`。
- 三级为具体页面（`type=2`，带 `component`）与按钮（`type=3`，带权限码）。
- **`erp:*` 权限码 112 条**；字典种子 `erp_audit_status`、`erp_stock_record_biz_type` 也在 `ruoyi-vue-pro.sql:776` 起 `[E5]`。

**【事实】ERP 菜单未被任何租户套餐或角色引用**：`system_tenant_package` 的两条种子（111/112）`menu_ids` 里没有 2563–2702 `[E4]`；`system_role_menu` 中落在 2563–2702 的行数为 **0** `[E24]`。见 §8。

### 1.4 前端：**已有，不用重写** 【事实】

**【事实】** 这是决定成本量级的关键一条，答案是**明确的"放开 pom 即可"**：

- `src/views/erp/**` **已存在**，共 **63 个文件**（含 `product/product/index.vue`、`stock/warehouse/index.vue`、`purchase/order/index.vue`、`finance/payment/index.vue`、`home/index.vue` 等）`[E6]`。
- `src/api/erp/**` **已存在**，共 **23 个文件**（product/finance/purchase/sale/statistics/stock 六组）`[E7]`。
- 菜单里 22 个 `component` 路径逐一核对，**全部能在 `src/views/` 下找到对应 `.vue`** `[E6]`。
- 路由是**动态的**：`src/utils/routerHelper.ts:7` 用 `import.meta.glob('../views/**/*.{vue,tsx}')` 按后端菜单的 `component` 字符串解析组件 `[E8]`；`src/router/modules/` 里没有任何写死的 `/erp` 路由 `[E8]`。

**【推断】结论：ERP 的引入成本是"放开 pom + 补 33 张表 + 配菜单/权限"，不是"重写前端"。** 前端页面虽在，但都是 yudao 原版的通用贸易页面，P0 要求的回收语义仍要改造（见 §9）。

**pom 状态** 【事实】：根 `pom.xml:31` 是 `<!-- <module>yudao-module-erp</module> -->`，`yudao-server/pom.xml:142` 是 `<!-- ... yudao-module-erp-biz ... -->`，注释原话为"ERP 相关模块。默认注释，保证编译速度" `[E9][E10]`。

## 2. 多租户支持

### 2.1 DO 继承关系 【事实 + 推断】

**【事实】33 个 ERP DO 全部 `extends BaseDO`，无一继承 `TenantBaseDO`，也没有任何类声明 `tenantId` 字段。**
- 例：`ErpPurchaseInDO extends BaseDO` `[E2]`、`ErpProductDO extends BaseDO` `[E2]`、`ErpSupplierDO extends BaseDO` `[E2]`。
- 反例（对比）：icbc 侧 `IcbcGoodsConfigDO extends TenantBaseDO` `[E13]`、`IcbcAcquisitionDO extends TenantBaseDO` `[E15]`、`IcbcSettlementDO extends TenantBaseDO` `[E16]`。
- `grep -rn TenantBaseDO yudao-module-erp/` = 无匹配 `[E2]`。

**【事实】但多租户过滤在 yudao 里是"按表名"，不是"按 DO 基类"**：`TenantDatabaseInterceptor.ignoreTable()` 只查 `ignore-tables` 名单，不在名单里的表一律被 MyBatis-Plus 拼上 `tenant_id` `[E11]`；`application.yaml` 的 `yudao.tenant.ignore-tables` 里没有任何 `erp_*` `[E12]`。

**【推断】** 因此：
1. 只要 ERP 表在运行期通过租户上下文被访问，就**必须有 `tenant_id` 列**，否则 SQL 报"未知列"。**补建 SQL 时每张 ERP 表都要加 `tenant_id bigint not null default 0`**（这是必须显式处理的一项）。
2. ERP 的**插入**也由 MyBatis-Plus 租户插件注入 `tenant_id`，所以"DO 不声明 tenantId"不等于"不支持多租户"，但 DO 读出来拿不到 `tenantId` 值。
3. `erp-biz/pom.xml` **并不直接依赖** `yudao-spring-boot-starter-biz-tenant` `[E1]`；运行时依赖其他模块把租户拦截器装上（全局 MyBatis-Plus 插件），所以它**实际上是被租户过滤的**——这正是"要显式补 `tenant_id`"的原因。

### 2.2 权限码与租户套餐 【事实 + 推断】

**【事实】ERP 用的是 yudao 默认的 `@ss.hasPermission('erp:*')`**（见 §1.1 各 Controller）`[E1]`，它依赖 `system_menu.permission` + `system_role_menu`。

**【事实】icbc 域刻意**不用**这套**：`RecyclingPermissionChecker` 的类注释明确写"为什么不用 yudao 默认的 `@ss.hasPermission`：那套依赖数据库里的菜单与角色-菜单关联，而回收企业的四个角色是一套固定的、跟代码一起演进的角色策略"，改为按 `RecyclingRoleEnum` 里的角色 code 判断 `[E18][E19]`。

**【推断】** 两者**可以对接但风格冲突**：
- 技术上可行：`tenant_package.menu_ids` 加进 `2563–2702` 即可让 `tenant_admin` 拿到 ERP 权限（`TenantServiceImpl:139` 在开租户时把 `menuIds` 写进 `system_role_menu`）`[E24]`。
- 但一旦接入，回收企业就会出现**两套权限来源**：icbc 看角色 code（与菜单无关），ERP 看菜单/角色-菜单。运维上要同时维护"角色 enum"和"套餐菜单清单"，**容易出现同一岗位在 icbc 有权限、在 ERP 没有权限（或反之）的裂缝**。这是引入 ERP 的一项隐性治理成本。

## 3. 品类主数据：`ErpProduct*` vs `icbc_goods_config`

### 3.1 字段级差异 【事实】

| 概念 | ERP `[E2]` | icbc `[E13][E14]` |
|---|---|---|
| 品类主表 | `ErpProductDO`：`id,name,barCode,categoryId,unitId,status,standard,remark,expiryDay,weight(kg),purchasePrice,salePrice,minPrice` | `IcbcGoodsConfigDO`：`id,name,unit(String),taxRate,taxMethod,mergedCode,status,remark` |
| 分类 | `ErpProductCategoryDO`：`id,parentId,name,code,sort,status` | **无独立分类表**（`name` 即品类） |
| 单位 | `ErpProductUnitDO`：`id,name,status`（外键表） | `unit` 是字符串 |
| 税 | **无税率/计税方法/税收分类编码** | `taxRate`（税率）、`taxMethod`（`SIMPLE`/`GENERAL`）、`mergedCode`（商品和服务税收分类合并编码） |
| 平台级编码 | 无 | `IcbcScrapCodeDO`：`id,name,mergedCode,unit,taxRate,status,remark`，`extends BaseDO` 且在 `ignore-tables` 内（平台级，跨租户）`[E14]` |
| 行业属性 | `standard`（规格）可当等级；无扣杂方式、无计价单位 | 无等级、无扣杂方式、无计价单位 |

**【事实】两边各有对方没有的字段**：ERP 有分类树、规格、多条价格（`purchasePrice/salePrice/minPrice`）；icbc 有税率、计税方法、税收分类编码。**没有一方能单独作为唯一权威。**

### 3.2 现场端从哪取品类、改动牵动谁 【事实】

**【事实】现场端（收货员 uni-app）**：`src/api/goodsConfig.ts:15` 调 `GET /icbc/goods-config/enabled-list` `[E20]`；`pages/acquisition/index.vue` 用它下拉选品类，提交 `goodsConfigId` `[E20]`。

**【事实】`icbc_goods_config` 的消费点共 4 处**（`grep` 结果）`[E21]`：
1. `AcquisitionServiceImpl`——建档时把 `name/unit/taxRate/taxMethod/mergedCode` **快照**进 `icbc_acquisition`（`AcquisitionServiceImpl.java:284-288`）`[E21]`；
2. `AppointmentServiceImpl`——`GET /icbc/seller/appointment/goods` 只回 `id/name/unit` `[E21]`；
3. `InvoiceOrderServiceImpl`——开票申请按 `mergedCode` 校验计税方法 `[E21]`；
4. `IcbcGoodsConfigController`——admin 的 `page/get/enabled-list` 与 `icbc:goods-config:*` 权限 `[E21]`。

**【推断】改主数据的牵动面**：若把权威迁到 ERP 产品表，现场端 1 个接口 + 自然人端 1 个接口 + 开票 1 处校验 + 收购快照逻辑都要改；**且 `ErpProductDO` 没有税率/计税方法/编码，迁移会丢字段**，必须先给 ERP 产品表加列。

### 3.3 建议（推断）

**【推断】权威应落在 icbc 侧，ERP 产品表只做"库存/金额维度"的镜像或干脆不引入品类。** 理由：
1. 品类已与**开票强耦合**（`mergedCode` + `taxMethod` 是工行预下单的必填语义，见 ADR 0003 的 `specificElements`），而 ERP 产品表**完全没有税务字段**；把权威挪走会削弱开票校验。
2. `icbc_goods_config` 已被现场端、自然人端、开票三线消费，迁移面大、收益小。
3. ERP 的库存/采购若要用品类，加一个 `icbcGoodsConfigId` 外键映射（或让 ERP 产品表与 `icbc_goods_config` 一对一同步）即可，**不必把 icbc 的品类换成 ERP 的产品**。

改造点：给 `erp_product` 加 `icbc_goods_config_id`（或反之给 `icbc_goods_config` 加 `erp_product_id`）做双向映射；**若只做最小库存台账，甚至可以让库存直接以 `goodsConfigId` 为维度，绕开 ERP 产品域**。

## 4. 采购域：`ErpPurchaseOrder` / `ErpPurchaseIn` / `ErpSupplier` vs 收购单 / 结算单

### 4.1 字段清单 【事实】

**`ErpPurchaseOrderDO`** `[E2]`：`id,no,status,supplierId,accountId,orderTime,totalCount,totalPrice,totalProductPrice,totalTaxPrice,discountPercent,discountPrice,depositPrice,fileUrl,remark,inCount,returnCount`
**`ErpPurchaseOrderItemDO`** `[E2]`：`id,orderId,productId,productUnitId,productPrice,count,totalPrice,taxPercent,taxPrice,remark,inCount,returnCount`

**`ErpPurchaseInDO`** `[E2]`：`id,no,status,supplierId,accountId,inTime,orderId,orderNo,totalCount,totalPrice,paymentPrice,totalProductPrice,totalTaxPrice,discountPercent,discountPrice,otherPrice,fileUrl,remark`
**`ErpPurchaseInItemDO`** `[E2]`：`id,inId,orderItemId,warehouseId,productId,productUnitId,productPrice,count,totalPrice,taxPercent,taxPrice,remark`

**对比现场事实载体 `IcbcAcquisitionDO`** `[E15]`（已有）：`acquisitionNo,clientRequestId,payeeId,partnerPayeeId,sellerName,sellerMobile,goodsConfigId,categoryName,unit,taxRate,taxMethod,mergedCode,specification,quantity,unitPrice,amount,grossWeight,tareWeight,netWeight,deduction,deductionMethod,settlementWeight,adjustmentAmount,adjustmentReason,quantityNote,settlementId,stationId,batchKey,cancelReason,driverName,driverMobile,weightTicketNo,weightTicketImageUrl,weightTicketPlateNo,vehiclePlateNo,plateMatched,vehicleFrontImageUrl,vehicleRearImageUrl,tradeAddress,tradeTime,settlementMethod,status,invoicePartnerOrderId,source,remark`。

**状态机** 【事实】：ERP 单据只有 `ErpAuditStatus` = `PROCESS(10 未审核)` / `APPROVE(20 已审核)` 两态 `[E1]`；`validatePurchaseOrder` 要求订单必须 `APPROVE` 才能创建入库 `[E22]`。

### 4.2 逐条对照 M03/M04/M05 【对照表】

| 规划要求（来源） | ERP 现状 | 判定 |
|---|---|---|
| 一单多品类 | 订单/入库均有 `items` 列表，**支持** `[E2]` | 直接复用 |
| 分批收货 | `orderItem.inCount` 累加，`updatePurchaseOrderInCount` 按 `selectOrderItemCountSumMapByInIds` 重算 `[E22]` | 改造复用（能累加，但口径只有一个） |
| 毛重/皮重/净重/扣杂 | **ERP 采购入库只有一个 `count`**，无任何重量明细字段 `[E2]` | 必须自建（`icbc_acquisition` 已承载） |
| 有效磅次 / 多磅次选择 | 无磅次对象 `[E2]` | 必须自建 |
| 拒收 / 部分接收 | 无（只有整单审核/作废）`[E1]` | 必须自建 |
| 结算重量与计价 | ERP 是 `totalPrice = 单价×count±税±优惠`，**没有"结算重量"这一口径** `[E2][E22]` | 必须自建（ADR 0019 的 `settlementWeight` 在 icbc） |
| 1000 吨订单的履约口径（计划/验收/入库/结算分列） | 只有 `totalCount`（计划）与 `inCount`（入库）两口径，**没有验收重量、结算重量** `[E2]` | 改造复用 + 必须补口径字段 |
| 合同关联 | 订单**没有** `contractId` 字段 `[E2]` | 必须自建 |
| 执行场站 | 订单**没有** `stationId` `[E2]` | 必须自建 |
| 起止日期 / 执行期限 | 只有单个 `orderTime`，**无开始/截止日期** `[E2]` | 必须补 |
| 订单状态（草稿/执行中/暂停/完成/关闭） | 只有 `未审核/已审核` `[E1]` | 改造复用 |
| 固定单价 / 按交货日价格表 | 只有 `productPrice` 一个静态价 `[E2]` | 必须自建 |
| 零散收购无订单 | ERP 强约束：采购入库**必须挂已审核订单**（`validatePurchaseOrder`）`[E22]` | **与规划冲突**，必须放开或另建旁路 |
| 分品类扣杂 / 混装拆分 | 无 `deduction`、无 `batchKey` `[E2]` | 必须自建 |

**【推断】关键冲突**：规划明确"支持无采购订单的零散收购"，而 ERP 的采购入库代码**硬校验订单已审核** `[E22]`。若把 `ErpPurchaseIn` 直接当收购/入库主载体，就必须改这段校验（改动虽小，但意味着 ERP 原生路径被破坏，后续升级要维护分叉）。

### 4.3 缺口清单 【事实汇总】

ERP 采购域**没有、必须新增**的字段/对象（相对 M05/M06）：
- 重量族：`grossWeight`、`tareWeight`、`netWeight`、`deduction`、`deductionMethod`、`settlementWeight`；
- 证据族：`driverName`、`driverMobile`、`vehiclePlateNo`、`weightTicketNo`、`weightTicketImageUrl`、`plateMatched`、车头/车尾照片；
- 关系族：`stationId`、`batchKey`、`contractId`、`settlementId`、`payeeId`（自然人出售者）；
- 状态族：拒收/部分接收、待入库/在库/隔离待处理、待结算/已确认；
- 口径族：验收重量、入库重量、结算重量、未履行量。

**【推断】这些字段 90% 已在 `IcbcAcquisitionDO`** `[E15]`，说明"必须自建"的其实是"必须继续用 icbc 的对象"，而不是"在 ERP 里重新加一遍"。**把同样字段加两遍会制造两个事实源**，与 ADR 0018/0019/0021 相悖。

### 4.4 `ErpSupplierDO` 能否承载"单位供货方" 【事实 + 推断】

**【事实】字段** `[E2]`：`id,name,contact,mobile,telephone,email,fax,remark,status,sort,taxNo,taxPercent,bankName,bankAccount,bankAddress`。

- ✅ **有税号**（`taxNo`）、**有开户行/账号/地址**（`bankName`/`bankAccount`/`bankAddress`）、有默认税率 `taxPercent`——"进项取票"最需要的主键有了。
- ❌ **没有主体类型**（企业/个体工商户/自然人）、没有营业执照/纳税人资格、没有地址（只有 `bankAddress`）、没有"是否一般纳税人"、没有发票抬头校验字段。
- ❌ 与 `icbc_payee_info`（自然人出售者）**没有关联字段**；`IcbcAcquisitionDO.payeeId` 指向的是 icbc 的档案 `[E15]`，不是 `erp_supplier`。

**【推断】** `ErpSupplierDO` **可以作为单位供货方的第一版载体**（P1），但需要补：主体类型、纳税人资格、地址、以及一个与自然人档案区分的标识；并且要明确"单位供货方的收购单仍走 icbc 链路、但对公付款与进项发票走 ERP/独立流程"（与规划 M02/M08 的 P1 描述一致）。**不要**把单位经办人塞进现有反向开票链路（规划 M02 明确禁止）。

## 5. 仓储域 vs 规划 M06

### 5.1 字段清单 【事实】

| 表 | 字段 `[E2]` |
|---|---|
| `ErpWarehouseDO` | `id,name,address,sort,remark,principal,warehousePrice,truckagePrice,status,defaultStatus` |
| `ErpStockDO` | `id,productId,warehouseId,count` |
| `ErpStockRecordDO` | `id,productId,warehouseId,count,totalCount,bizType,bizId,bizItemId,bizNo` |
| `ErpStockInDO` / `ErpStockInItemDO` | `id,no,supplierId,inTime,totalCount,totalPrice,status,remark,fileUrl` / `id,inId,warehouseId,productId,productUnitId,productPrice,count,totalPrice,remark` |
| `ErpStockOutDO` / `ErpStockOutItemDO` | `id,no,customerId,outTime,totalCount,totalPrice,status,remark,fileUrl` / 同构 |
| `ErpStockMoveDO` / `ErpStockMoveItemDO` | `id,no,moveTime,totalCount,totalPrice,status,remark,fileUrl` / `id,moveId,fromWarehouseId,toWarehouseId,productId,productUnitId,productPrice,count,totalPrice,remark` |
| `ErpStockCheckDO` / `ErpStockCheckItemDO` | `id,no,checkTime,totalCount,totalPrice,status,remark,fileUrl` / `id,checkId,warehouseId,productId,productUnitId,productPrice,stockCount,actualCount,count,totalPrice,remark` |

### 5.2 关键判定：**没有"库位"，也没有"批次"** 【事实】

**【事实】** `grep -rn "库位\|批次\|成本\|暂估\|batch\|location" yudao-module-erp/**/*.java` = **零匹配** `[E2]`。

- 层级只到 **仓库**：`ErpWarehouseDO` 是一层平铺，没有 `parentId`、没有 `stationId`、没有库区/库位表 `[E2]`。
- 没有任何"批次/磅次/收货批次"对象，`erp_stock` 与 `erp_stock_record` 的粒度都只是 `(product, warehouse)` `[E2]`。
- 仓库**不关联场站**：`ErpWarehouseDO` 无 `stationId` `[E2]`；而 `icbc_station` 是独立表 `[E2]`。

**【推断】规划 M06 的 `场站 → 仓库/堆场 → 库区/库位 → 批次` 四级在 ERP 里只能落地两级（场站靠 `icbc_station`，仓库/堆场靠 `erp_warehouse`）；库区/库位与批次必须自建。** 最小改法是给 `erp_warehouse` 加 `stationId`，再新增"库位"和"批次"两张表（或给 `erp_stock` 的唯键从 `(product, warehouse)` 扩为 `(product, warehouse, location, batch)`）。

### 5.3 库存怎么算 【事实】

**【事实】** 余额表 + 流水表，**余额由流水增量维护、不是重算**：
1. `ErpStockRecordServiceImpl.createStockRecord` 先 `stockService.updateStockCountIncrement(...)` 改余额，再插入 `ErpStockRecordDO`（并把最新余额写进 `totalCount` 做快照）`[E23]`。
2. `updateStockCountIncrement` 用 `setSql("count = count + ?")` 原子自增；余额不存在时先插入 0 行；`NEGATIVE_STOCK_COUNT_ENABLE=false`，不允许负库存 `[E23]`。
3. 采购入库的库存变动发生在 **`updatePurchaseInStatus` 审核通过时**（`PURCHASE_IN` / 取消时 `PURCHASE_IN_CANCEL` 负数冲回），同一模式用于其余出入库/调拨/盘点 `[E22][E23]`。
4. `ErpStockRecordBizTypeEnum` 覆盖 `10/11 其它入、20/21 其它出、30–33 调拨、40–43 盘盈盘亏、50/51 销售出库、60/61 销售退货、70/71 采购入库、80/81 采购退货` `[E1]`——**没有"收货入库"这一类**，只有"采购入库/其它入库"。

**【推断】** `erp_stock` + `erp_stock_record` **可以作为 M06 的"最小库存流水"**（规划 M06 也正好写了"只有入库记录时页面应称累计入库"的兜底），但要满足 M06 验收"库存余额能由期初与全部出入流水重算"，还需补：期初、库位/批次维度、以及把"待验收/待入库/在库/隔离待处理"等状态放进去（ERP 只有单据的未审核/已审核）。

### 5.4 成本/金额口径 【事实 + 推断】

**【事实】库存余额与流水里没有任何单价/金额字段**：
- `ErpStockDO` 只有 `count`；`ErpStockRecordDO` 只有 `count` / `totalCount` `[E2]`。
- 单价/金额只出现在**单据**上：`erp_stock_in_item.productPrice/totalPrice`、`erp_stock_out_item`、`erp_stock_move_item`、`erp_stock_check_item` 等 `[E2]`。
- 采购入库的金额口径是 `totalPrice = totalProductPrice + totalTaxPrice − discountPrice + otherPrice`，由 `calculateTotalPrice` 现算并落库 `[E22]`。

**【推断】判断**：
1. ERP 库存里的"单价/金额"**只是单据行的成交价，不是库存成本**——余额表根本不持有成本，也就没有移动加权/先进先出。**"结算前为暂估"在 ERP 模型里没有落点**。
2. 与 **ADR 0021（金额与状态只讲可核验的事）**：ERP 的 `totalPrice` 是"单据存在即有金额"，**不含任何可核验状态**（无来源版本、无确认标记），若直接拿来给自然人看会违反 ADR 0021。需要额外加"金额来源与确认状态"字段才可用。
3. 与 **ADR 0019（结算重量为唯一计价基准）**：ERP 用 `count` 当计价数量，且**采购入库强制从订单取价**，与"结算重量×单价+调整项"是两套公式；若两套并存且都写金额，就是**两个金额事实**。**规划 M06 的"结算前暂估/结算后调整"需要自建成本表**（或干脆不做成本，只做数量台账）。

## 6. 财务域 vs 现有付款链路

### 6.1 字段清单 【事实】

- **`ErpAccountDO`** `[E2]`：`id,name,no,remark,status,sort,defaultStatus`——**只是一个"账户名称标签"**（如"银行账户/现金"），**没有开户行、没有卡号、没有账户主体**。
- **`ErpFinancePaymentDO`** `[E2]`：`id,no,status,paymentTime,financeUserId,supplierId,accountId,totalPrice,discountPrice,paymentPrice,remark`
  - **`ErpFinancePaymentItemDO`**：`paymentId,bizType,bizId,bizNo,totalPrice,paidPrice,paymentPrice,remark`（`bizType` 正是 `ErpBizTypeEnum`，可挂采购入库/退货等）
- **`ErpFinanceReceiptDO`** `[E2]`：`id,no,status,receiptTime,financeUserId,customerId,accountId,totalPrice,discountPrice,receiptPrice,remark`（+ item 同构）

**【事实】ERP 付款单里完全没有银行字段**：没有银行卡号、没有回单号、没有 `payStatus`、没有工行单号、没有 `actuallyReceivedAmount`。它是"企业内部记了一笔付款决定/核销"。

### 6.2 与 ADR 0010 / `icbc_payment_order` 的关系 【事实 + 推断】

**【事实】现有真实付款链路在 icbc**：`PaymentOrderDO` 带 `acquisitionId`、`invoiceOrderId`、`icbcOrderNo`、`payeeNo`、`payerNo`、`paymentAmount`、`payStatus`、`paymentSerialNo`、`actuallyReceivedAmount`、`receiptNo`、`receiptTime`、`sellerReceivedConfirmedAt`、`redirectUrl`、`errorCode/errorMsg` 等 `[E17]`——即 ADR 0010 的"工行公对私直付到本人银行卡 + 回单归档"。

**【推断】两者只能**互斥**，不能并存为两个金额事实**：
- 若同时启用 `ErpFinancePaymentDO` 与 `icbc_payment_order`，同一笔货款会出现两条"付款"记录——一条是 ERP 的内部核销（no 银行状态），一条是工行的真实执行（有 `payStatus`）。这会直接违反 ADR 0021 第 3 条"付款、开票、税费三条状态线分别显示"的可核验性，也违反 ADR 0010 的"唯一资金通路"。
- **建议：一期直接关掉 ERP 财务域（付款单/收款单/结算账户三项菜单 + 权限），付款一律走 `icbc_payment_order`。** 若将来单位供货方需要对公付款（P1），再单独设计，不要复用 ERP 付款单当事实源。
- `ErpAccountDO` 与 `icbc_payer_info`（付方档案，含子商户/对公账户）也是两回事：前者无银行信息，不能替代后者。

## 7. 统计域 vs 规划 M10

### 7.1 实际能出什么 【事实】

**【事实】** `ErpPurchaseStatisticsController` / `ErpSaleStatisticsController` 各只有 **2 个接口** `[E7]`：
- `GET /erp/purchase-statistics/summary` → `{todayPrice, yesterdayPrice, monthPrice, yearPrice}`（**四个金额**）
- `GET /erp/purchase-statistics/time-summary?count=6` → 近 N 个月的 `{time, price}` 数组
- 口径由 `ErpPurchaseStatisticsMapper.xml` 定义：`SUM(erp_purchase_in.total_price) − SUM(erp_purchase_return.total_price)`，按 `in_time` 区间 `[E3]`；销售侧对称。

**【推断】它能表达的只有"采购金额/销售金额的时间序列"，没有数量、没有明细维度、没有下钻。** 前端 `views/erp/home/index.vue` 就是 8 张金额卡片 + 2 张月度折线 `[E6]`。

### 7.2 对照 M10 报表清单 【落差表】

| M10 报表 | ERP 现状 | 落差 |
|---|---|---|
| 工作台：今日到场/待称重/待验收/待入库/待结算确认/异议/付款失败/票务失败 | ERP 首页只有 8 个金额卡片 `[E6]` | **完全缺失**，需自建（数据散在 icbc） |
| 采购履约表（计划量/实际履约量/余额/到期日/进度/超量过期异常） | 只有 `totalCount`+`inCount`，无到期日、无履约口径、无超量异常 `[E2]` | 仅两个数可复用，其余自建 |
| 收购台账（出售者/场站/方式/各重量口径/金额/单据） | **不在 ERP 统计里**（在 icbc 的 acquisition 查询） | 必须自建，数据源在 icbc |
| 入库台账及库存表（入出流水/在库/库位/批次/库龄/暂估已确认成本） | 有 `erp_stock` + `erp_stock_record` 分页查询 `[E3]`，可做"累计入库/在库数量" | **无库位、无批次、无库龄、无成本**；自建项多 |
| 结算付款表（结算金额/办理进度/回单/失败原因/未办理时长） | 无 | 自建（数据在 icbc settlement/payment） |
| 异常表（磅差/超采购量/超入库量/重复关联/长期未确认/资料缺失） | 无 | 自建 |
| P1 经营分析（品类/场站/方式/出售者/运输费用） | 无 | 自建 |

**【推断】M10 的 P0 报表 ERP 覆盖率极低（约 1/7 的一半）。** ERP 统计域的代码量（2 个 ServiceImpl + 2 个 XML）说明它从来不是为这类报表设计的。

## 8. 销售域能不能一期直接关掉

### 8.1 sale 域与"销项正向开票暂不做"的关系 【事实 + 推断】

**【事实】ERP 的 sale 域是"销售订单/出库/退货/客户 + 出库扣库存"**，由 `ErpStockRecordBizTypeEnum.SALE_OUT(50)` 驱动库存 `[E1]`；它**不产生任何发票、不与工行交互**，也没有"用废企业"的概念。

**【推断】** 它与 ADR 0003 预留的"正向开票"**不是同一件事**：ADR 0003 说的是发票方向与数据模型（`businessType 0005`、`invoiceNormal`），ERP 的 sale 域只是"发货+出库+收款"的库存/财务闭环。规划里"销项正向开票暂不做"指的是**不给用废企业开票**；ERP sale 域若启用，会额外带来"销售出库扣库存 + 客户 + 销售收款"这些**当前业务不存在**的对象与菜单，**与 ADR 0004「只做工具不做交易撮合、只覆盖 回收企业 ← 自然人出售者」的范围直接冲突**。

**【推断】结论：sale 域一期应直接关掉**（不打开菜单、不分配权限、不建或建而不用）。同理，`finance` 域的付款/收款也应关掉（见 §6）。

### 8.2 放开 pom 后菜单/权限会不会连带给租户看到 【事实 + 推断】

**【事实】**
- **系统租户 / 超管会自动看到全部菜单**：`PermissionServiceImpl.getRoleMenuListByRoleId` 对 `super_admin` 直接返回 `menuService.getMenuList()` 全量 `[E24]`。所以本地用 `admin`（tenant 1，`super_admin`）登录，一旦放开 pom，**整棵 ERP 菜单（含销售管理、财务管理、库存全部）立刻可见**——这就是"空菜单/脏菜单"风险的来源。
- **回收企业租户不会自动看到**：`tenant_admin` 的菜单来自 `system_tenant_package.menu_ids`（开租户时写入 `system_role_menu`，`TenantServiceImpl:139`）`[E24]`；而 ERP 菜单 2563–2702 **不在任何套餐、也没有任何 role_menu** `[E4][E24]`。所以普通租户默认看不到、也调不动（`@ss.hasPermission` 会拒）。
- 即使菜单不可见，**API 仍然存在**：每个 Controller 的 `@PreAuthorize('@ss.hasPermission(...)')` 在无对应角色菜单时返回无权限 `[E1]`——但前提是**表已建好**；表不存在时前端一访问就是 500（`[E26]` 本地库无表）。

**【推断】怎么关**：
1. **给系统租户单独收敛**：不要指望"不给套餐"就能让 `admin` 看不见；要么改超管菜单返回逻辑（不建议动框架），要么接受"仅系统租户可见"，并在产品上明确"本地/平台租户的 ERP 菜单不是回收企业功能"。
2. **回收企业租户**：套餐 `menu_ids` 只挑必要的（产品/采购订单/采购入库/仓库/库存/库存明细），**排除 sale、finance-payment、finance-receipt、statistics 的销售侧**。
3. 若彻底不想让 sale 域存在，可**不把 sale 相关 DO/Mapper 的建表放进 SQL**，并**不分配对应菜单**（Controller 仍会加载，但调用时报无权限/表不存在）；更干净的做法是从 server pom 里排除、或在 `yudao-server` 的组件扫描上排除 `sale`/`finance` 包（需要确认框架是否支持细粒度排除）——**这一点读代码无法定论，需原型验证**（见 §10）。
4. `ErpSaleOrderController` 的权限码用的是 `erp:sale-out:*`（复制粘贴遗留）`[E1]`，若真要启用 sale 域，这是一个必须先修的 bug。

## 9. 结论

### 9.1 M01–M10 P0 × 判定总表

| 规划 | 判定 | 依据 | 改造量级 |
|---|---|---|---|
| **M01 企业/场站/基础资料** | 改造复用 | 企业/人员权限走 yudao `system`；场站已有 `icbc_station` `[E2]`；仓库只有一层 `erp_warehouse` `[E2]`；品类/单位/编码分列在 ERP 与 icbc（§3） | 中 |
| **M02 出售者与交易对方** | 自然人直接复用；单位供货方改造复用 | `icbc_payee_info`/`icbc_natural_person` 已有 `[E2]`；`ErpSupplierDO` 有 `taxNo`/开户行但无主体类型与资质 `[E2]` | 小（自然人）/ 中（单位） |
| **M03 合同与采购订单** | 合同必须自建；采购订单改造复用 | 无合同对象；`ErpPurchaseOrder(+Item)` 有 `totalCount/inCount` 但没有合同/场站/起止日期/多口径履约 `[E2]` | 中 |
| **M04 回收预约与作业安排** | 必须自建 | ERP 无预约/到场/门岗/车次/磅房/质检对象 `[E2]`；`icbc_appointment` 只覆盖到站预约（ADR 0020） | 大 |
| **M05 现场收货/称重/质检** | 必须自建（沿用 icbc） | ERP 入库只有 `count`，无毛皮净重/扣杂/磅次/司机车牌/拒收 `[E2]`；`IcbcAcquisitionDO` 已承载 `[E15]` | 大（但已在 icbc 建成） |

### 9.2 引入 ERP 的真实成本清单 【事实 + 推断】

1. **补 33 张建表 SQL**（含索引、`tenant_id` 列）——仓库与本地库现在都没有 `[E2][E26]`。**这是最确定、最先要做的一项。**
2. **放开 pom**：根 `pom.xml:31` + `yudao-server/pom.xml:142` `[E9][E10]`。
3. **补前端？不用**——`views/erp/**`(63) 与 `api/erp/**`(23) 已在仓库 `[E6][E7]`；但要按 P0 语义改造（真前端成本是改造，不是新建）。
4. **补成本口径**：`erp_stock`/`erp_stock_record` 无成本字段，`erp_*_item.productPrice/totalPrice` 是成交价不是库存成本 `[E2][E22]`；"暂估/已确认成本"要新建表或字段（§5.4）。
5. **关掉哪些域**：`sale`（ADR 0004 冲突）、`finance` 的付款单/收款单（两个金额事实，§6）；`statistics` 的销售侧同理。
6. **菜单与权限收敛**：
   - 系统租户 `super_admin` 会看到全部 ERP 菜单（`PermissionServiceImpl:190` `[E24]`）——需要产品上接受或另行收敛；
   - 回收企业套餐 `menu_ids` 只挑必要项（ERP 菜单 id 2563–2702 内 `[E4]`）；
   - 治理两套权限体系（`@ss.hasPermission` vs `@icbc.hasPermission`，§2.2）`[E18]`。
7. **修 ERP 自身的遗留瑕疵**：`ErpSaleOrderController` 权限码写成 `erp:sale-out:*` `[E1]`；表名单复数不一致 `[E2]`；无任何 ERP 单元测试（`yudao-module-erp` 下 `src/test` 为空）`[E1]`。

### 9.3 接缝建议 【推断】

**（1）收购单与 `ErpPurchaseIn` / `ErpStockIn` 的关系：单向派生，谁写谁分开。**

```
收购事实（唯一源头）                            ┌→ 结算/确认/付款/开票（icbc，已有）
icbc_acquisition  ──┬─ 计价：settlementWeight ───┘
                    └─ 实物：入库动作（仓管确认）──→ erp_stock_in(+item) → erp_stock_record → erp_stock
```

- **`icbc_acquisition` 是事实源，`ErpStockIn`/`erp_stock_record` 是实物入库的派生记录**。不要让 ERP 反向写收购金额，也不要让收购单直接写库存余额。
- 关联方式：给 `erp_stock_in_item`（或 `erp_stock_in`）加 `acquisitionId` / `acquisitionItemId` 外键，或复用现有的 `bizType`/`bizId` 机制（`ErpStockRecordDO` 已有 `bizType/bizId/bizItemId/bizNo` `[E2]`，可扩一个 `icbc_acquisition` 业务类型）。
- **`ErpPurchaseIn` 建议不要作为主载体**：它硬绑 `erp_purchase_order`（必须已审核）`[E22]`，与"零散收购无订单"冲突；如果要用，只能作为"有采购订单的到货"记录，另加旁路。**更省事的是跳过 `ErpPurchaseIn`，只用 `ErpStockIn`+`stock_record` 做库存台账**。
- **幂等**：入库动作要按 `acquisitionId` 做唯一约束，避免重复审核重复加库存（规划 M06 验收项；ERP 现有的 `updateByIdAndStatus` 乐观更新能防重复审核，但派生入口需自己保证）`[E22]`。

**（2）"结算重量 vs 库存重量"两个口径并存不打架。**

- **结算重量**：只存在 `icbc_acquisition.settlement_weight`，是**计价基准**（ADR 0019），只影响金额/发票，**不影响库存** `[E15]`。
- **库存重量**：存在 `erp_stock_record.count`，是**实物数量**。扣杂**不自动扣库存**——除非真的有分拣/损耗事实，那时才走 `stock_check`（盘亏）或 `stock_out`（报损）。
- 二者并存的方式：**同一张收购单同时带两个数字**（`settlementWeight` 与"入库实物量"），差额进"异常表"（规划 M10 的磅差/差异项）。这与物流规划 §7 的示例完全一致（毛重 50 − 皮重 15 = 净重 35，扣杂 1 → 结算 34，但实物库存仍是 35）。
- **禁止**把 `settlementWeight` 直接写进 `erp_stock`，也**禁止**用库存数量反推结算金额——这正是 ADR 0021 要防的"讲不可核验的事"。

### 9.4 不确定项（读代码无法定论，必须原型或问人）

1. **ERP 表的真实 DDL 与 `tenant_id`**：物理列、字段精度、索引、字符集都只能靠"统计 XML 手写 `tenant_id`"推断 `[E3][E11]`。**需取 yudao 上游 `erp.sql` 或自拟 DDL 后跑一次冒烟。**
2. **ERP 与本仓库改造过的 framework 是否兼容**：本仓库把 `system_dict_data/system_dict_type/system_error_code` 加进了 `ignore-tables` `[E12]`，且 framework 版本可能与 ERP 源码来自不同版本；**放开 pom 后能否一次编译/启动通过，需要实际编译验证**（本次未改动、未编译）。
3. **菜单/权限如何给回收企业分配**：ERP 走 `tenant_package.menu_ids`，icbc 走 `RecyclingRoleEnum` `[E18][E19][E24]`；两者如何映射到"管理员/采购/仓管/财务"四个岗位，**没有现成种子，需要产品决策**。
4. **sale/finance 域的物理关闭方式**：不建表、不分配菜单、还是从组件扫描中排除包——**框架是否支持按包排除，需原型验证**（§8.2）。
5. **品类主数据权威落哪一侧**：本条是**产品/架构决策**而非代码事实（§3.3 给的是推断性建议），需要一次 ADR 或票据定案。
6. **库位/批次的建模落点**：扩展 `erp_warehouse`（加层级）还是新建 `icbc_*` 库位/批次表，取决于"库存归 ERP 还是归 icbc"这一更上位的决策。
7. **结算重量与库存重量差异的最终处理规则**：规划 M06 与物流规划 §7 都只给了"示例假设值"，**尚未形成 ADR**；差异该进异常表、还是核销、还是回改结算，需要业务定案。
8. **成本核算是否要做**：M06 写"成本字段展示来源与确认状态""正式成本核算策略另行定义"，ERP 又没有成本模型（§5.4）；做与不做直接决定 M06 的改造量级。
