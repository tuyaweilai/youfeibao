## 0. 一句话结论

**【事实】** 工行这套接口是**完整的开票 + 缴税 + 支付能力**，通过 `gw.open.icbc.com.cn` 开放。你的平台是**「合作方」（appId）**，回收企业是**「子商户 / 付方」**，出售者是**「收方」**。

**【推断】你不需要碰乐企。** 接口里没有一处要求平台持有乐企直连资质，`invoiceChannel` 的取值（`乐企平台：LQPT；电子发票服务平台：DPPT；税控系统：SKXT`）证明**通道由工行侧选择**。§2.4 里那些门槛（实缴 1000 万、1 亿流水、纳税信用 A）**不构成你的前置条件**。

**【推断】但这也划定了工行的边界，而边界之外恰好就是你的产品。** 佐证在 §7 的映射表：工行管**发票流**和**资金流**，**完全不碰合同流、货物流、以及全部证据链归集**，也不做资质准入与 500 万额度校验。**那正是平台要建的部分。**

## 2. 角色模型

**【事实】接口里出现的角色：**

| 角色 | 字段 | 说明 |
|---|---|---|
| **合作方 / 平台** | `appId`（通用参数 `app_id`） | 你。在工行 API 开放平台注册生成 |
| **付方平台外部编号** | `appIdSub` | `businessType=0004/0005` 时**必输**；`[I6]` |
| **子商户** | `outVendorId` | 企业授权接口里 `archiveType=01` 时必输 `[I4]` |
| **外部用户编号** | `outUserId` | `[I1]`："发起收方入驻请求的**用户**编号" |
| **合作方订单 ID** | `outOrderId` | 平台侧唯一 |
| **合作方交易单号** | `corpSerno` | `[I1]` |
| **开票请求流水号** | `outInvoiceId` | 换开、下载时使用 |
| **红冲流水号** | `outRedOffsetId` | 红冲与撤销 |

**【事实】两类机构编号，别混** `[I12]`：

- **聚富通 appId** —— 调接口用（`api` 路径里的那些）
- **cams APPID（合作方机构编号）** —— 调个金接口（`api` 路径中**没有** `jft` 的）时填 `corpNo`。**入参 `corpNo` 必须用 cams 的 APPID，用错会导致用户影像上传报错。**

## 3. 三条业务流

### 3.1 自然人收方入驻 `[I1]` `[I2]`

> ⚠️ **2026-09-21 作废**：本节描述的「页面接口 + 电子钱包开户」流程已不再采用。收方入驻改走数据接口 `edpreceive/add`（`businessType=0004`），依据见 [ADR 0035](../adr/0035-收方入驻走数据接口不用页面与电子钱包.md) 与 `docs/icbc/收方入驻/`。本节其余内容保留为 2026-09-18 当天的研究记录，不改。

**【事实】一次页面调用搞定「入驻 + 电子钱包开户」**，内部串了 4 个数据接口，无需单独对接。

流程：影像上传 → 钱包信息填写（银行卡号等）→ 手机号短信验证 → 开通电子钱包 → 收方入驻。

**【事实】开户与入驻是两条独立的成败线**，四种组合：

| 开户 | 入驻 | 页面结果 |
|---|---|---|
| 成功 | 成功 | 注册成功页，**展示电子账户账号** |
| 失败 | 成功 | 填写联系信息页，留电话待后续再开户 |
| 成功 | 失败 | 收方信息补录页，重填再入驻 |
| 失败 | 失败 | 注册失败页，点击跳回合作方地址重发起 |

**【事实】开户成功 = 入驻个人一类卡 + 电子账户；开户失败 = 只入驻一类卡。**

**【事实】两种对接模式：**

- **标准模式**：工行页面收集全部信息
- **预填信息模式**：合作方自行收集银行卡号、手机号预填。**仅在跳过开户影像上传步骤时才允许上送预填信息。**

**【事实】三种活体检测**，需与分行确认本项目用哪种：

1. **动态活体** —— 仅 APP 渠道，需在合作方 APP 集成**聚富通 SDK**，`trxChannel` 上送 `01`/`02`
2. **静态活体** —— 支持 APP / 小程序 / 公众号 / 生活号
3. **无需活体检测** —— 支持 APP / 小程序 / 公众号 / 生活号

**【事实】`trxChannel` 字典** `[I1]`：`01`-安卓 APP、`02`-iOS APP、`03`-H5、`04`-微信公众号、`05`-微信小程序、`06`-支付宝场景号。

**【事实】`businessType` 字典** `[I1]`：`0004`-再生资源（反向开票）、`0005`-农产品收购、`0006`-开票业务。

**【事实】人工审核是硬环节** `[I1]`：

- 收方入驻需**分行审核人员在运营中心审核通过**才算成功
- **限时免审白名单**：在申请**十天内**、且在限额内，可做**一笔**交易。不满足免审条件或已做过一笔，就不能交易，**必须等审核通过**
- **收方修改也要审核**，且审核期间按修改前信息交易；`[I1]` 明确"仅能修改银行卡号、是否他行卡、行名行号、证件签发日期、证件截止日期"

> **【推断】这条对产品的冲击最大：** 自然人**第一次**卖废品时，如果不在免审白名单内，**当场拿不到钱**（要等分行审核）。这是致命的体验断裂。**必须在原型阶段验证**"白名单 + 单笔限额"到底怎么配、能不能按回收企业批量开白、审核时效多长。见 §8 的 R1。

**【事实】收方删除无需审核，但要求付方、平台、收方状态正常且开启智慧清分**。

### 3.2 反向开票主流程 `[I5]` `[I6]` `[I7]` `[I3]`

**【事实】四步：**

```
① 开票信息预下单 (UI) ──▶ 返回「自然人确认页面」
                            ↓ 自然人确认
② 开票信息预查询 (数据) ── 查 confirmStatus
                            ↓
③ 开票付方支付 (UI) ──── 生成「企业支付页面」
                            ↓
④ 发票下载 (数据) ────── 拿票
```

**【事实】第 ① 步是 UI 页面接口**，用 `client.buildPostForm(request)` 生成**自动提交表单**，浏览器自动 POST 到工行网关。**不能当 REST API 直接调。**

**【事实】"自然人确认"是流程内建的一环** —— `[I5]` 功能说明就写着"返回自然人确认页面"，并有 `invoiceJumpUrl`（自然人确认成功返回页面地址）。`confirmStatus`：`00` 未确认 / `01` 自然人确认完成 / `02` 全部确认完成。

**【推断】这正好落实 `[S1]` 第十二条**"首次向出售者反向开票时应征得其同意并保留证明材料"——**工行把'征得同意'做成了页面流程**，平台不用自建签署。

**【事实】企业授权接口是独立一层** `[I4]`：拿税务可信二维码，**使用单位的法定代表人或财务负责人（已在税务系统报备）用税务 APP 扫码完成实人认证并录入授权有效期**。`archiveType`：`00`-平台档案、`01`-子商户档案（后者必输 `outVendorId`）。

> **【推断】这是"平台 → 回收企业 → 税务"三重授权链的关键。** `[S1]` 第十二条管的是"自然人同意"，这层管的是"回收企业授权平台代其开票"，两者不同。留意 `[I4]` 用词——**"使用单位"**，正是 `[S5]`《乐企联用规范指引》的原词。**说明工行这套接口在乐企体系里就是「直连单位 → 使用单位」那一层。**

### 3.3 冲红与取消 `[I8]` `[I9]` `[I10]` `[I11]`

**【事实】三个不同的操作，别混：**

| 操作 | 接口 | 适用 |
|---|---|---|
| **红字冲销开票** | UI `/ui/jft/ui/red/invoice/offset/V1` | 退货或开票有误，开红票冲蓝票 |
| **红字冲销确认单撤销** | 数据 `/api/jft/api/red/invoice/offset/revoke/V1` | 撤销已申请的红冲确认单 |
| **发票取消** | 数据 `/api/jft/api/invoice/reversal/V1` | **仅限"预开票成功但未支付"** |

**【事实】红冲原因字典** `redOffsetReason`：`01` 开票有误（**必须全额红冲，明细单价/金额/数量必须与蓝票一致**）/ `02` 销货退回 / `03` 服务中止 / `04` 销售折让。

**【推断】对应 `[S1]` 第十条**的"红字发票需与原蓝字发票一一对应"。接口层的对应靠 `outRedOffsetId` + `outOrderId` + 明细 `blueDetailNumber`。

**【事实】发票下载支持红票、红蓝标识、按开票请求流水号选择下载；PDF 解析支持"本地保存"和"网页下载"两种方式** `[I11]`。

## 4. 异步通知：9 种事件 `[I13]`

**【事实】报文外层**：`{ "notifyData": "", "signData": "" }`，接收变量名 `biz_content`；`notifyData` 是 **base64 编码的 JSON**；`signData` 可忽略。

**【事实】`notifyType` 字典**（这是集成的骨架）：

| 值 | 事件 | 主要伴随字段 |
|---|---|---|
| `01` | 预下单异常信息 | `invoiceStatus` |
| `02` | b2b 支付 | `payStatus`、`payAmount`、`actuallyReceivedAmount` |
| `03` | 开票 | `invoiceStatus`、`invoiceLevyItemResponse`、`invoiceDetailResponse` |
| `04` | 缴税 | `taxStatus`、`taxRealAmount`、`tradeTime` |
| `05` | 发票上传 | `uploadStatus` |
| `06` | 发票取消 | `invoiceStatus` |
| `07` | 红票申请 | `redOffsetStatus` |
| `08` | 红票上传 | `uploadStatus`、`redOffsetStatus` |
| `09` | 红票撤销 | `redOffsetStatus` |

**【事实】通知里出现的状态机**（产品要逐个建模，不能只存一个"成功/失败"）：

- `invoiceStatus`：`00` 初始 / `01` 预开票中 / `02` 预开票成功 / `03` 预开票失败 / `04` 预开票取消
- `payStatus`：`-1` 待通知 / `00` 初始 / `01` 处理中 / `02` 成功 / `03` 失败 / `04` 订单关闭 / `05` 冲正 / `06` 已退汇 / `07` 他行已扣款本行未入账 / `12` 已支付待签收（票据支付）/ `25` 部分成功
- `taxStatus`：`00` 初始 / `01` 开票查询中 / `02` 缴税中 / `03` 缴税查询中 / `04` **缴税成功** / `05` 缴税失败 / `97` **缴税异常，缴税金额不一致** / `98` 缴税异常未知 / `99` 无需缴税
- `uploadStatus`：`00` 未上传 / `01` 处理中 / `02` 已受理 / `03` 上传中 / `04` 上传成功 / `05` 上传失败
- `redOffsetStatus`：`00` 初始 / `01` 申请中 / `02` 申请成功 / `03` 申请失败 / `04` 上传处理中 / `05` 上传已受理 / `06` 上传中 / `07` 上传成功 / `08` 上传失败 / `09` 撤销中 / `10` 撤销成功 / `11` 撤销失败
- `confirmStatus`：`00` 未确认 / `01` 自然人确认完成 / `02` 全部确认完成

**【事实】`taxPaymentMethod`**：`0`-自然人自行办理 / `1`-企业委托扣缴。→ 对应 `[S1]` 第十一条的代办税费义务。

> **【推断】四个独立状态机（开票 / 支付 / 缴税 / 上传）＋ 一个确认状态，是这个系统最真实的复杂度所在。** 平台必须为每张票维护这五条状态线，并处理它们的**任意交错**。这才是"证据链"系统的技术核心，不是表单。

| `specificElements` 特定要素 | `16` 农产品收购、`24` **报废产品收购** | `[S1]` 第五条 |
| `buyerInvTypeCode` 收购发票类型代码 | `01` 农产品收购发票、`04` **报废产品收购发票** | `[S1]` 第五条 |
| `isSellerPersonProduct` | `Y` 销售自己使用过的报废产品（报废车普票）/ `N` 销售收购的报废产品 | `[S1]` 第一条 **出售者定义** |
| `iitProject` 个税项目 | `1` 财产转让所得 / `2` **经营所得** | `[S1]` 第十四条 |
| `invoiceType` | `01` 专票 / `02` 普票 | `[S1]` 第八条 |
| `preferentialType` 优惠政策标识 | `01` 简易征收 / `08` 按 3% 简易征收 / `03` 免税 … | `[S1]` 第八条、第十三条 |
| `unuseReduceTaxCode` 减按征税类型代码 | `54` 前期已开 3% 需冲红 / `55` **放弃享受减按 1%**；**税率传 3 时必输** | `[S1]` 第十三条 3% 减按 1% |
| `goodsInfo.mergedCode` | 商品和服务税收分类**合并**编码 | `[S1]` 第六条 |
| `areaCode` | 省级税务机关代码 | 应税行为发生地 |

**【事实】补缴是按 1% 和 3% 分开列的** `[I13]`：`specialInvoiceAmount1`（待补缴专票累计金额 **1%**）、`specialInvoiceAmount3`（**3%**）、`plainInvoiceAmount1`（待补缴普票累计金额 **1%**），加 `repayAmount`（待补缴累计金额）、`isNeedRepay`。

**【事实】`supplementaryTax` 补缴税费标志"目前固定传 Y"** `[I5]`。

> **【推断】这解释了同月跨企业开票的合并计算**（`[S1]` 第十三条）：自然人当月在多处卖废品，平台 A 和平台 B 各自开票时会**重复享受月 10 万免征**，税务局事后发现要**补缴**。工行的"补缴"机制就是给这个兜底的——**但补缴是事后补，不是事前拦。事前拦截（额度实时校验）接口里没有。**见 §7。

**【事实】融资维度是内建的：**

- `[I5]` 有 `loanApplyNo` 融资申请编号（长度 32→60）
- `[I6]` 返回 `repaidPriAndIntAmount` 融资贷款还款总金额、`loanRepaymentStatus` 还款结果、`loanRepaymentTime`、`repaymentList`
- `payMethod` 字典含 `16` 融资支付；`payMode` 含 `25` 融资支付、`42` **新经营快贷**

**【推断】** 工行的商业意图很清楚：**开票 + 支付 + 融资**。订单数据天然是授信依据。**这是竞品抄不了的，也是"只做工具"路线的潜在变现口。**

## 6. 对接工程约束（会直接影响架构）

**【事实】认证与报文：**

```java
new DefaultIcbcClient(APP_ID, "RSA2", MY_PRIVATE_KEY, "UTF-8",
                      "json", APIGW_PUBLIC_KEY, "AES", encryptKey, "", "")
new UiIcbcClient(APP_ID, "RSA2", MY_PRIVATE_KEY, IcbcConstants.CHARSET_UTF8)
```

- 通用参数：`app_id`、`msg_id`（APP 级唯一）、`format`、`charset`、`encrypt_type`（**现仅支持 AES**）、`sign_type`（`CA` / `RSA`-RSAWithSha1 / `RSA2`-RSAWithSha256，缺省 `RSA`）、`sign`、`timestamp`、`ca`、`biz_content`
- **敏感信息用 `camsPublicKey`（工行 SM2 公钥）加密** `[I12]`
- 所有 URL **仅支持 HTTPS**

**【事实】幂等与重试是硬约束** `[I5]` 收尾"特别注意事项"原文：

> 当返回 `-500041`、`-500042` 或其他未知异常时，**切勿重复提交**！请使用指令提交接口对应的**查询接口**查询指令的最新状态后再做处理。

- 预下单有 `isRedo`（是否重复下单），`Y` 时只有 `appId`、`outOrderId` 必输 —— **这是官方的幂等入口**
- 红冲有 `isRedo`，用于"重复发起红冲流水"

**【事实】限流**：`500031` 速率超限、`500032` 并发超限。

**【事实】沙箱限制**：`app_id` 前缀必须加 `sandboxie_`；**沙箱不支持 UI 类型 API**（`500052`）。

> **【推断】这条很痛：** 反向开票主流程第一步（预下单）和第三步（付方支付）都是 UI 接口，**沙箱跑不了**。联调只能上生产，或者等分行给测试环境。**排期上要留出这个风险。**

**【事实】准备流程全部由分行操作，是项目制不是自助式** `[I12]`：

1. 分行申请 APPID 并维护接口权限
2. 分行新增并下载**拆分证书**，做实名签认证
3. 分行在**个金系统**做钱包建档
4. 分行在**运营中心**做聚富通建档

**【事实】常见故障** `[I12]`：`400019` 授权验证失败 = **分行没在 API 内管里给这个 appid 配接口权限**；`400016` app 公钥未维护；`400017` 签名验证失败。

> **【推断】"给 appid 配接口权限"是逐接口人工配置。**每加一个接口都要找分行。**这意味着需求变更的交付周期被别人控制**，架构上要把工行调用隔离在一个 adapter 层（`/codebase-design` 的 seam），并假设**某些能力可能拿不到授权**。

**【事实】`merBusiModel` 平台经营模式** `[I5]`：`01`-**平台自营**、`02`-**非平台自营**，默认 `01`。该字段仅存在于预下单接口，共 3 处：第 2 页版本升级说明（2025-04-27 新增）、第 8 页反向开票主流程请求参数、第 10 页公对公结算请求参数。**非必输**。

**【推断】工作取值 `02 非平台自营`，且必须显式上送**（默认 `01` 与本项目原则相左）。理由：该字段的语义是**经营模式**，不是开票主体——平台不承担这笔买卖的经营权利义务，收购主体是回收企业。但这依赖一个未验证的读法（「自营」= 平台自身是交易的经营主体）。若「自营」实指「平台自身持有直连资质并代开」，取值需反过来重算。见 §8 的 R2。

**【事实】`payChannel` 支付渠道** `[I5]`：`01` e 企付、`02` 场景结算、`04` **公对公结算**、`05` **公对私结算**。`outVendorId`/`outUserId` 在 `05` 时填法不同。另有 `payBusinessFlag`：`00` 普通支付、`01` **先付后退**。

**【事实】`invoiceNormal`：工行也支持正向开票** `[I5]`（2025-06 版本新增），`payChannel` 需上送 `04`。含购买方自然人标识 `buyerPersonType`、自然人证件三件套、经办人信息、以及不动产租赁/建筑服务/旅客运输的专项明细。

> **【推断】这意味着你可以一次打通整条链：** 回收企业反向开票收进（对自然人），再正向开票卖出（对用废企业）。`[S6]` 政策点名的"全国性、功能性平台"就是这个形态。**这是一期取舍点，见 §8 的 Q3。**

## 7. 关键缺口：工行不管什么

**【推断】把 `[S1]`（税总 5 号公告）逐条映射到接口，缺口一目了然：**

| `[S1]` 条款 | 工行接口落点 | 谁来做 |
|---|---|---|
| 一 出售者 / 500 万 | 收方入驻 + `businessType=0004` | 工行（**但仅入驻，非额度**） |
| **二 三项资质准入** | **无** | **平台** |
| **三 超 500 万拒绝开票** | **无**（只有事后补缴） | **平台** |
| 四 提交《反向开票申请表》 | 无（线下） | 回收企业 + 工行 + 税务 |
| 五 标注"报废产品收购" | `buyerInvTypeCode=04`、`specificElements=24` | 工行 |
| 六 报废产品类编码 | `goodsInfo.mergedCode` | 平台上送 |
| 七 调整发票额度 | 无 | 线下 |
| 八 计税方法决定票种 | `invoiceType` + `preferentialType` | 平台判断，工行执行 |
| 十 红字发票一一对应 | 红字冲销 + 确认单撤销 + `blueDetailNumber` | 工行 |
| 十一 代办税费申报缴款 | `taxStatus` + `notifyType=04` + `supplementaryTax` | 工行 |
| 十二 首次征得同意 | 自然人确认页面 + `confirmStatus`；企业授权接口 | 工行 |
| 十三 月 10 万免征 / 3% 减按 1% | `unuseReduceTaxCode`；补缴按 1%/3% 分列 | 平台算，工行执行 |
| 十四 0.5% 个税预缴 | `iitProject=2` + `invoiceLevyItemResponse` | 工行 |
| 十五 / 十六 抵扣与税前扣除 | 发票下载 | 工行 |
| **十七 保存五流证据 + 收购台账** | **完全没有** | **平台** |
| **十八 业务真实性责任** | **完全没有** | **平台** |
| `[S4]` 第七/九条 公安备案、出售人实名登记 | 无 | **平台** |
| `[S5]` 货物流 / 资金流数据报送 | 部分（资金由工行） | **平台** |

**【推断】结论清晰：**

> **工行 = 发票流 + 资金流 + 自然人实名。**
> **平台 = 合同流 + 货物流 + 信息流（台账）+ 全部证据链归集 + 主体资质准入 + 额度风控。**

这就是产品的边界，而且是**有法定依据的边界**（`[S1]` 第十七条、第十八条完全落在平台头上）。竞品开灵强调的"五流证据星链图""齐备率可视"不是包装，**是他们抢下了工行不碰的那一半**。

## 9. 对 Q1 的修订答案

**原问题**：谁做「直连单位」？自建乐企直连资质，还是借道工行？

**【推断】修订后的答案：这个问题的框架本身错了。**

`[I4]` 的「企业授权与发票管理接口」里已经出现「**使用单位**」这个词——那是 `[S5]`《乐企联用规范指引》的原词。这说明**工行就是那个直连单位，而且它把"邀请使用单位"这件事做成了接口**（拿二维码 → 使用单位法代/财务负责人用税务 APP 扫码实人认证）。`[I5]` 的 `invoiceChannel` 字典（`LQPT`/`DPPT`/`SKXT`）进一步证明**通道选择在工行侧**。

**所以真正的问题不是"谁做直连单位"，而是：**

1. **每个回收企业要不要在工行开「子商户档案」（`archiveType=01`）？** —— 这决定接入是"平台一个 appId 带全部"还是"一企业一档案"。
2. **开票档案由工行侧建还是平台侧发起？谁维护？**
3. **`businessType=0006 开票业务`（`archiveType` 不传子商户）是不是给"平台自营"留的口子？** 而 `0004` 才是我们这种"平台 + 子商户"模式？

**建议（待你确认）**：`businessType=0004 再生资源` + `archiveType=01 子商户档案` + `merBusiModel=02 非平台自营`，即**一回收企业一子商户档案**。待 R2、R6 向工行确认后定案。

## 11. 历史仓库审计：`tuyaweilai/tuya-saas-java`

> 2026-09-18，为判定 `merBusiModel` 取值而审计。仓库为 **private**；最后一次提交 `7caad07 feat(icbc): 增加工行接口手动HTTP调用方式和相关文档`，最后推送 2025-06-12。

### 11.1 结论：**它答不了 `merBusiModel`，因为当时这个字段还不存在**

**【事实】三条证据：**

1. `merBusiModel`（及「平台经营模式」）在整个仓库中**零出现**。
2. 仓库里的预下单文档是 **V1 1.0.2，版本记录止于 2024-11-08**；而 `merBusiModel` 是 **2025-04-27 版本才新增**的，即 `docs/icbc/` 里那份 **V1 1.0.4**。**字段在他们对接时尚未存在于接口中。**
3. 更关键 —— **预下单调用从未实现**。`InvoiceOrderServiceImpl.callIcbcPreOrderApi()` 的完整实现是：

```java
// 暂时返回模拟的跳转URL，后续集成真实的工行接口
String baseUrl = "https://gw.open.icbc.com.cn/ui/jft/ui/invoice/pre/order/V1";
return baseUrl + "?outOrderId=" + request.getOutOrderId();
```

**【推断】所谓"和接口打通过"，不成立。** 真正使用 SDK 客户端的只有 `generatePaymentForm`、`testInvoiceQuery`、`testUserQuery`、`testSignature` 四处；而 `IcbcProperties` 里配置的网关是 `https://www.youfeibao.net`（不是 `gw.open.icbc.com.cn`），该域名解析到 `198.18.0.47` —— **RFC 2544 基准测试保留段，典型的本地代理 fake-IP**，不是可用的公网网关。所以反向开票的**主链路（预下单 → 自然人确认 → 支付 → 开票）从未跑通过**。

**⇒ `merBusiModel` 仍然是 R2，只能问工行。** 唯一可说的：字段默认 `01`，取值 `01` 平台自营 / `02` 非平台自营，且在预下单报文里是**可选**字段。

**① 三份我们缺的接口文档**（已复制进 `docs/icbc/`，见 `[I14]`–`[I16]`）。其中 `[I14]` 直接解决了 §2 的角色映射争议。

- 付方支付状态查询：`/api/jft/api/payment/queryPaymentStatus/V1`（`I12` 未列出；但既然 `payStatus` 有 11 个状态，必然需要查询接口）

**③ 一个值得借鉴的数据模型**（`doc/icbc/工行反向发票数据库设计.sql`、`数据库表结构说明.md`）：

| 表 | 用途 |
|---|---|
| `icbc_payee_info` | 收方（自然人）：`payee_no`、`partner_payee_id`、姓名、身份证号、手机号、银行卡号、开户行、审核状态 |
| `icbc_payer_info` | 付方（企业）：`payer_no`、`partner_payer_id`、企业名、纳税人识别号、法人、联系人、银行账号、审核状态 |
| `icbc_invoice_order` / `order_item` | 开票订单与明细 |
| `icbc_callback_notify` | 异步通知（含处理状态，可重放） |
| `icbc_api_log` | 接口调用日志 |

**【推断】两处值得直接继承：**

1. **「工行侧编号」与「合作方侧编号」成对建模**（`payee_no` / `partner_payee_id`），这是对接任何银行/税务接口的正确做法，也与本平台多租户需求天然契合。
2. **回调单独落表并带处理状态**（`CallbackProcessStatusEnum`）—— 对应 `[I13]` 的 9 种 `notifyType` 与多状态机，是必需的，不是可选的。

**【推断】一处必须改的**：其 `InvoicePreOrderReqVO` 把 `outUserId`/`outVendorId` 按 `[I5]` 的错误说明建模（见 §2），**照抄会把付方与收方建反**。

**【事实】可复用的固定取值**（其 VO 默认值与校验正则）：

| 字段 | 值 |
|---|---|
| `specificElements` | `24` 报废产品收购（正则限 `^(16\|24)$`） |
| `buyerInvTypeCode` | `04` 报废产品收购发票（正则限 `^(01\|04)$`） |
| `supplementaryTax` | `Y`（补缴，与 `[I5]` 「目前固定传 Y」一致） |
| `isSellerPersonProduct` | `N` 销售收购的报废产品 |
| `isRedo` | `N` |
| `payChannel` | `02` 场景结算（其正则只允许 `^(01\|02)$`，**比 `[I5]` 文档窄** —— 后者含 `04` 公对公 / `05` 公对私） |
| `currency` | `001` |
| `payJumpUrl` / `invoiceNotifyUrl` / `mac` | 必输 |

### 11.3 顺带的安全提醒

**【事实】** 该仓库把 `appId`、RSA 私钥、AES 密钥、SM2 公钥/私钥**明文写在 `IcbcProperties.java` 默认值和 `application-icbc-test.yml` / `application-local.yaml` 里**。仓库是 private 所以未外泄，但：

- 新项目**不要复制这些值**，密钥一律走环境变量/密钥管理；
- 如果那套密钥是真实测试或生产凭据，建议向工行申请重签；
- 若该 private 仓库将来转公开或加人，先做历史清理。
