# 工行答复记录 · 2026-09-18

> 对应 `to-questionnaire-工行-技术类.md` 与 `to-questionnaire-工行-业务类.md`。以下为行方答复，**可以据此编码**。
> 来源：工行答复 + `docs/icbc/` 下新补的四份实人认证文档。

## 一、付方 / 收方 / 外部用户编号

**【事实】`appIdSub`（付方平台外部编号）与 `outVendorId`（子商户编号）**等同**。**
→ 字段映射定案（推翻 `[I5]` 预下单文档里互换的那套说明）：

| 字段 | 含义 |
|---|---|
| `appId` | 平台（合作方）编号，唯一且不变 |
| `appIdSub` ≡ `outVendorId` | **回收企业**（付方平台 / 子商户） |
| `outUserId` | **自然人出售者**（外部用户编号） |

**【事实】`outUserId` 先经工行实名认证取得。** 平台先发起**实人认证**，认证通过后才可用同一个 `outUserId` 走收方入驻与开票。

> ⚠️ 文档细节待留意：`融e聚实人认证H5页面接口V1` 里 `outUserId` 是**必输入参**（示例 `123456789`），而结果查询接口把它列为**返回字段**。实际含义是「平台生成的编号，经实人认证锚定后才有效」，编码时按此理解，若联调发现相反请回改。

**【事实】再生资源场景固定上送 `accountKind=02`（个人）+ `receiverType=03`（自然人）。**

**【事实】`payChannel` 上送 `05 公对私结算`。**

> ⚠️ 这条改了我们此前的假设：历史仓库的 `InvoicePreOrderReqVO` 把 `payChannel` 默认成 `02 场景结算` 并把正则限为 `^(01|02)$`。**`payChannel` 同时出现在预下单报文里**，所以它不只影响付款，也影响开票申请。

## 二、平台经营模式 `merBusiModel`

**【事实】上送什么取值都不会有其它后果。** 位置一栏保留我们的工作取值 `02 非平台自营`，但它不触发不同流程。

## 三、开票档案

**【事实】**
- `appId` 是平台 id，唯一且不变。
- **子商户就是回收企业**，按开票主体来。
- `archiveType` 的 `00` 与 `01` **不影响业务**；按逻辑用 **`01` 子商户档案**。
- **`businessType` 只能上送 `0004`。** `0005` 农产品收购、`0006` 开票业务本项目不适用。
- 一个 `appId` 下挂子商户档案**没有数量限制**。
- **子商户档案之间互相看不到数据。**

## 四、500 万额度与风控

**【事实】超 500 万只能靠开票失败感知——没有事前校验接口。**
→ **平台必须自建连续 12 个月滚动额度台账**，并在开票申请前自行拦截。跨平台累计不可见，本平台内的跨租户累计是我们自己的责任。

**【事实】工行侧没有统一的额度视图，我们查不到。**

**【事实】没有针对自然人出售者的黑名单 / 涉案 / 异常名单校验接口。**
→ **黑名单与异常名单平台自建。** 这也意味着竞品宣称的"黑名单校验"不来自银行。

**【事实】收方入驻时行内校验按接口要求执行，且我们能提前知道拒绝原因。**
→ 拒绝原因可前置展示给收货员，建档失败不必靠猜。

## 五、新补的实人认证接口（此前不在材料里）

| 接口 | 路径 | 类型 |
|---|---|---|
| 实人认证 H5 页面 | `/ui/jft/ui/user/faceH5/submit/V1` | UI 页面 |
| 实人认证结果查询 | `/api/jft/api/user/faceH5/query/V1` | 数据 |
| 实人认证结果通知 | 回调 `{appId, transNode, outUserId, verifyResult}` | 异步通知 |

**【事实】H5 页面入参**：`appId`、`authScene`（**`01` 反向开票**）、`outUserId`、`transNo`（合作方交易单号）、`callbackUrl`（不可带参数）、`jumpUrl`（可带参数）、`failJumpUrl`、`custName`、`certNo`（**目前仅支持身份证**）、`mobile`（用于发验证短信）。

**【事实】结果**：查询返回 `authResult`（`00` 初始 / `01` 认证中 / …）与 `failReason`；通知返回 `verifyResult`（通过 `1` / 未通过 `0`）。

**⇒ 出售者建档的步骤顺序是：**

```
采集姓名 + 身份证 + 手机号
   → 实人认证 H5（authScene=01）
   → 结果查询 / 通知
   → 收方入驻 + 电子钱包开户
   → 签署框架收购协议 + 首次授权
```

## 五、发票文件与交付

**【事实】发票下载接口只返回 PDF。**

→ 这不只是"格式少一种"。规格与 `ADR-0003` 里假设过"下游抵扣需要 OFD/XML"，竞品开灵科技对外提供 **PDF / OFD / XML 三种**。**工行侧只有 PDF。**

→ 需要确认的一件事：如果**用废企业的 ERP 需要 XML 或 OFD 才能自动抵扣入账**，平台没有来源。税务数字账户本身可下三种格式，但那是另一条通道，不在工行融 e 聚的范围内。**实施 `#11` 前先问清下游到底要什么格式**——如果只要 PDF，这条无关紧要；如果要 XML，产品承诺得改。

## 六、融资能力

**【事实】不涉及。**

→ 规格的 Out of Scope 原本写的是"一期只做透传与展示"，**现在连透传与展示也不做**。`loanApplyNo`（融资申请编号）、`repaidPriAndIntAmount`（融资贷款还款总金额）、`payMode=42 新经营快贷` 等字段仅按接口要求原样上送/接收，平台不解析、不展示、不做业务。

→ 也意味着**商业模式只剩按票计费一条**，原先设想的"融资分润"作为二期变现路径不成立。`#16` 计费的边界因此更干净。

## 七、业务：自然人首次交易能否当场结算（**原 R1，最高优先级**）

**【事实】正常情况下能当场拿到钱。收方入驻提交后**自动审核、秒过**。**

**【事实】免审状态的单笔限额暂时不用考虑。**

### 这条解除了什么

规格 `#1` 的 Further Notes 第 1 条预警过：若首次交易必须等分行人工审核，则「收购现场当场结清」不成立，用户故事 25、31、32 与整条开票链路都要拆成两段式。**该风险解除，规格不需要为此改动。**

票据 `#6`（出售者建档）的四种成败组合**保持不变**，但**不需要"等待审核"这类界面状态**——建档在秒级内完成，收货员可以一直站在废品堆前把这一单走完。

### 实施时要注意的一处不一致

**审核仍是异步的**（走回调通知），只是行内自动秒过。所以：

- **状态机要保留**：待审核 → 通过 / 拒绝，以及对应的异步通知处理与重放能力。不要因为"秒过"就把状态删掉，否则通知先到或后到时会出错。
- **界面要简化**：不设计"等待审核结果"的等待页、不设计"审核未通过请留联系方式"的主路径（该字段仍保留，作为异常兜底）。

一句话：**保留状态，去掉等待。**

### 业务问卷中仍未答的
